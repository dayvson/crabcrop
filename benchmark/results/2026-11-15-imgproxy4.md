# Benchmark results: 2026-11-15, imgproxy 4 run

crabcrop vs Thumbor vs imgproxy, measured with the harness in
this directory (`benchmark/bench.py`, setup by
`benchmark/setup.sh`). This run is a companion to the
2026-11-15 results beside it: same day, same fixtures, same
operations, same method, same crabcrop 0.13.0. The one change
is the imgproxy pin, which moves from 3.31.4 to 4.0.24, the
current imgproxy release, so the comparison also exists
against the imgproxy a new deployment would install today.
(imgproxy has no v5, v6, or v7 line; v4 is the current major
line, and 4.0.24, published 2026-11-12, is its latest
release.) The earlier files stay untouched as the historical
record; this file is the series entry for the new pin. The
headline is cold latency, as in the earlier write-up: the
first request for each source, which is the work a deployment
actually pays before any cache or CDN in front of it can
help. Warm figures are recorded in a shorter section near
the end. Raw data: `2026-11-15-imgproxy4.json` beside this
file. Method, URL mappings, and configuration are documented
in `benchmark/README.md` and `benchmark/configs/`; this
document records the environment, the numbers, and the
limits.

How this run was produced, and where it differs from the
2026-11-15 run beside it:

- Same repetition scheme: the comparison ran four times for
  crabcrop (two full runs, two crabcrop-only runs) and twice
  in full for Thumbor and imgproxy. Every table cell is the
  median across those runs; the raw JSON preserves each
  individual run under `runs`. All four runs were kept; the
  load average during them was about 0.4 to 1.3 on 4 cores.
  The cache scenarios were not rerun: they measure crabcrop
  alone, nothing in them depends on the imgproxy pin, and
  today's results stand in `2026-11-15-cache.json`.
- imgproxy 4.0.24 was built from its release tag with
  Go 1.27.4, the toolchain its go.mod requires (the harness
  pin for Go moves from 1.26.5 to 1.27.4 with it). Two build
  details differ from the 3.31.4 build. The main package is
  `./cli` in 4.x, not the module root. And Go 1.27's external
  link refuses the unresolved private dependencies of the
  shared libvips (libexif, OpenEXR, libspng, and the rest of
  `Requires.private` in `vips.pc`), so the build passes
  `-Wl,--allow-shlib-undefined`, which restores the link
  semantics the 3.31.4 binary was built with under Go 1.26;
  those libraries resolve at runtime through libvips's own
  dependency list, exactly as they do for 3.31.4.
- The extracted libvips module symlink described in the
  November 6 notes was lost again when this VM was replaced
  and was restored before the runs, as it was then (without
  it, imgproxy reports JPEG XL and AVIF as unsupported
  formats). With it restored, the unsupported pattern below
  matches the 3.31.4 run exactly; the 4.0.24 binary was
  smoke tested on resize, WebP, and JPEG XL before the
  measured runs.
- crabcrop was rebuilt from the v0.13.0 tag for this run.
  Its output bytes are identical to the earlier run in every
  cell, which cross-checks the rebuild.
- The imgproxy fidelity caveat from October stands, with
  new numbers: this is an official source build against
  libvips 8.15.1, while the official Docker image for
  4.0.24 builds from the imgproxy-base image (v4.0.15),
  which carries its own newer libvips built from source, so
  imgproxy numbers are imgproxy 4.0.24 on libvips 8.15.1,
  not the Docker image.

## Reading the cold results, including the losses

1. The standings do not move with the new pin. crabcrop is
   fastest or tied on eight of the ten cold operations
   against imgproxy 4.0.24, the same eight as against
   3.31.4: resize (18.6 against 19.5, a tie inside any
   honest noise band), WebP at all three quality points,
   JPEG at both quality points, and the two rows only
   crabcrop can serve here (grayscale, AVIF).
2. Crop-fill still belongs to imgproxy (13.4 against 19.0),
   for the same reason as before: libvips scales and crops
   in one demand-driven pass. The gap is 1.4x, about where
   the 3.31.4 run put it (1.5x).
3. JPEG XL still belongs to imgproxy, and the row narrowed
   from the other side: imgproxy 4.0.24 measures 45.8
   against 3.31.4's 38.4, while crabcrop is unchanged
   inside noise (53.8 against 55.2). Nothing in the byte
   counts moved (17,963 for both imgproxy builds, 11,445
   for crabcrop), so on this host the v4 encoder path costs
   more time for the same output. Two full runs per build
   is a thin base for a 19 percent delta; it is recorded as
   measured, and the loss stands either way.
4. The rest of imgproxy 4.0.24 reads the same or a little
   slower than 3.31.4 on this host (resize 19.5 against
   18.9, crop-fill 13.4 against 12.4, WebP q80 67.5 against
   64.1, JPEG q60 18.2 against 17.9, WebP q60 62.7 against
   61.0; JPEG q95 and WebP q95 are level). Each delta is a
   two-run median against a two-run median, so treat
   anything under about 10 percent as noise; the pattern
   across rows, not any single row, is the observation.
   Both builds sit on the same libvips 8.15.1, so this is
   imgproxy's own processing path that changed, not the
   encoder library under it.
5. Output bytes: imgproxy 4.0.24 produces byte-identical
   output sizes to 3.31.4 in every shared cell, and
   crabcrop and Thumbor match the earlier run cell for
   cell, which cross-checks the comparison again. At the
   same nominal quality the three encoders still produce
   different sizes in both directions; the settings are
   matched by parameter, not by measured quality, exactly
   as in the earlier runs.

## Warm latency (secondary)

In production a CDN usually sits in front of any of these
systems, so a built-in result cache mostly serves the
traffic the CDN lets through; cold performance is the
number that decides what a deployment pays. The warm
figures are kept for series continuity. The cache
scenarios measure crabcrop alone and were not rerun for
this pin change; they are in `2026-11-15-cache.json`
beside the earlier write-up.

Warm p50 (immediate repeat) is 0.2 to 0.4 ms for crabcrop
on every operation, unchanged. Thumbor repeats cost what
its cold requests cost (no result cache in this
configuration); imgproxy repeats likewise. Warm resize
throughput at 8 workers: crabcrop median 1,874 req/s
(four runs: 1,839, 1,909, 1,759, 2,119), Thumbor 25.8,
imgproxy 56.0. All three sit inside the host-variance
bands the earlier runs of this series recorded, and no
change is claimed in either direction.

## Method notes and limits

- Same method as the earlier runs: local origin, cold is
  the first request per source, warm is the immediate
  repeat, one 8-worker warm-throughput pass on resize,
  services measured alone and sequentially, fresh
  connection per request, 25 samples per operation per
  run. Tables report medians across repeated runs.
- All three run with signature verification effectively
  open (crabcrop and Thumbor unsafe mode, imgproxy without
  key or salt). This measures processing, not HMAC.
- Configurations are the committed files in
  `benchmark/configs/`, unchanged for this run; imgproxy
  4.0.24 accepts the same environment settings the harness
  already used, including `IMGPROXY_WORKERS=4` and the
  loopback source allowance. Thumbor runs at its defaults
  (no result storage).
- This host is shared. The reported runs were made in a
  quiet window and all were kept; medians across runs are
  the mitigation, and small deltas should be treated as
  noise anyway. Rankings are the robust part of a run on
  this host; absolute latencies move with the host.
- Single host topology: client, origin, and services share
  one small VM and its loopback. Absolute numbers include
  loopback and client overhead. Rankings can move on
  bigger hardware or with multi-process deployments.
- The series now carries two imgproxy pins for the same
  crabcrop release: 3.31.4 in `2026-11-15.md` and 4.0.24
  here. Future refreshes should measure the current
  imgproxy release of their day and say so, the way this
  file does.
