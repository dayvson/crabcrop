# Benchmark results: 2026-10-31

crabcrop vs Thumbor vs imgproxy, measured with the harness in
this directory (`benchmark/bench.py`, setup by
`benchmark/setup.sh`). Raw data: `2026-10-31.json` beside this
file. Method, URL mappings, and configuration are documented in
`benchmark/README.md` and `benchmark/configs/`; this document
records the environment, the numbers, and the limits.

imgproxy is measured here for the first time. The October 22
and 23 runs could not include it (Docker-only distribution, no
Docker on this host, no Go or libvips installed). It is included
now as an official source build; see the fidelity caveat under
Versions.

Versions notes:

- imgproxy 3.31.4 is pinned instead of the newer 4.0.x line
  because 4.0.x needs Go 1.27 and a newer libvips than Ubuntu
  24.04 ships. The 3.31.4 tree CI-tests libvips 8.14, 8.15,
  and 8.16 (see `.github/ci-docker` in its source), so the apt
  libvips 8.15.1 on this host is inside its supported range.
- Fidelity caveat: this imgproxy is an official source build
  (the same code the Docker image ships), compiled against the
  distribution libvips 8.15.1. The official Docker image for
  this release builds on the imgproxy-base image v3.15.9,
  which carries its own newer libvips built from source. The
  libvips versions differ, so encoder behavior (exact bytes,
  and possibly speed for some formats) could differ slightly
  from the official image. Treat the imgproxy numbers as
  imgproxy 3.31.4 on libvips 8.15.1, not as the Docker image.
- On this host, libvips gets AVIF through libheif 1.23.3,
  which is installed with decoder plugins only (dav1d,
  ffmpegdec) and no AV1 encoder plugin. That decides the
  imgproxy AVIF row below; the official image does encode
  AVIF. The Ubuntu aomenc plugin package for libheif 1.17
  was tried and is ignored by libheif 1.23.3
  (`heif-enc --list-encoders` shows no AVIF encoder either
  way), so the row is recorded as unsupported here rather
  than left ambiguous.

## Reading the results, including the losses

1. imgproxy is the fastest cold on the plain JPEG work.
   Resize 16.9 ms against crabcrop 30.4 and Thumbor 41.7;
   crop-fill 11.8 against 57.1 and 71.9; both JPEG sweep
   rows are imgproxy wins too. The crop-fill gap is the
   largest single loss in the table for crabcrop: libvips
   scales and crops in one demand-driven pass, and it shows.
2. crabcrop wins cold where the work is not plain JPEG.
   Grayscale 25.8 against Thumbor 38.3 (imgproxy cannot do
   it in OSS). JPEG XL 32.8 against imgproxy 39.5, with
   smaller output (13,175 against 17,963 bytes). AVIF is a
   crabcrop-only row in this run. WebP q80 is effectively a
   three-way tie on latency (65.5, 80.4, 62.6: imgproxy
   first, crabcrop second) and a tie on bytes (about
   12.0 KB each), which is a change from October: the
   libwebp encode swap since then closed the old pure-Rust
   WebP speed gap (149 ms cold in the October 23 run).
3. crabcrop warm is a different category. Its in-memory
   result cache answers every operation in 0.2 to 0.3 ms,
   and warm resize throughput is 2066.8 req/s against
   imgproxy 61.0 and Thumbor 25.8. Neither imgproxy nor
   Thumbor caches results in the configurations measured
   (both treat a CDN in front as the caching layer), so
   their warm numbers are their cold numbers. That is a
   topology difference, stated plainly: put a CDN in front
   of any of the three and the warm row mostly disappears;
   without one, only crabcrop serves repeats for free.
4. Output bytes at the same nominal quality still differ
   by encoder, in both directions. crabcrop is largest on
   grayscale JPEG (20,275 against Thumbor 17,657) and JPEG
   q60 (18,602 against 16,464 and 15,849). imgproxy is
   largest on JPEG q95 by a wide margin (81,335 against
   62,716 and 57,802) and on JPEG XL. imgproxy is smallest
   on both headline JPEG rows (24,060 resize, 10,490 crop).
   WebP bytes are at parity at all three quality points.
5. Consistency with October: crabcrop and Thumbor cold
   numbers land close to the October 23 run (resize 30.4
   and 41.7 against 29.1 and 43.1 then; warm throughput
   2066.8 and 25.8 against 1843 and 25.9), which is the
   expected cross-check for the harness itself.

## Method notes and limits

- Same method as October: local origin, cold is the first
  request per source, warm is the immediate repeat, one
  8-worker warm-throughput pass on resize, services measured
  alone and sequentially, fresh connection per request,
  statistics from 25 samples per operation.
- One harness fix since October: warmup requests use a
  throwaway 17x17 size, so no measured cold URL is
  pre-warmed. October disclosed that blemish; it is gone.
- All three run with signature verification effectively
  open (crabcrop and Thumbor unsafe mode, imgproxy without
  key or salt). This measures processing, not HMAC.
- Configurations are the committed files in
  `benchmark/configs/`. Thumbor runs at its defaults (no
  result storage). imgproxy runs with `IMGPROXY_WORKERS=4`
  per its docs sizing guidance and with loopback sources
  allowed so it can fetch the local origin at all.
- Environment deviations from a clean `setup.sh` run on
  this host, recorded for honesty: the VM carries a locally
  built libheif 1.23.3 whose package state conflicts with
  the apt libheif-dev package, so the libvips 8.15.1
  headers and libraries were assembled into a local prefix
  from the same apt packages `setup.sh` installs, and
  imgproxy was compiled against that prefix. The libvips
  version, packages, and imgproxy source are exactly the
  pinned ones; only the install layout differed. The
  crabcrop build also used a pre-existing local dav1d
  1.5.0 pkg-config entry on this host; `setup.sh` installs
  the distribution libdav1d-dev instead, which serves the
  same purpose on a clean machine.
- A background Rust compile from unrelated work on this
  shared VM was finishing during the first minute of the
  run. The crabcrop cold numbers still land within about
  1 ms of the idle-host October numbers on the shared
  rows, so the effect is inside the noise the October run
  already showed, but it is recorded here rather than
  hidden.
- Single host topology: client, origin, and services share
  one small VM and its loopback. Absolute numbers include
  loopback and client overhead. Rankings can move on
  bigger hardware or with multi-process deployments
  (Thumbor in particular is usually run multi-process,
  which would raise its throughput row, not its latency).
- One run, 25 samples per cell. Treat small deltas as
  noise; the tables keep p95 and mean beside p50 so the
  spread is visible.
