# Benchmark results: 2026-11-06

crabcrop vs Thumbor vs imgproxy, measured with the harness in
this directory (`benchmark/bench.py`, setup by
`benchmark/setup.sh`). This run refreshes the 2026-10-31
results against crabcrop 0.9.9 (the October run measured
0.9.5) with the same method, and adds two crabcrop cache
scenarios the comparison set does not reach: cache behavior
under churn, and memory accounting for the result cache
(`benchmark/bench_cache.py`). Raw data: `2026-11-06.json`
(comparison) and `2026-11-06-cache.json` (cache scenarios)
beside this file. Method, URL mappings, and configuration are
documented in `benchmark/README.md` and
`benchmark/configs/`; this document records the environment,
the numbers, and the limits.

How this run was produced, and where it differs from October:

- The comparison ran four times for crabcrop (two full runs,
  two crabcrop-only runs) and twice in full for Thumbor and
  imgproxy. Every table cell is the median across those runs,
  not a single run as in October; the raw JSON preserves each
  individual run under `runs`. The cache scenarios ran three
  times; the cache tables use the final run, and the text
  gives the across-run range for the headline figures. Two
  complete cache runs are in the raw JSON.
- The Thumbor venv and the imgproxy binary are the exact
  builds the October run used, reused bit for bit (the
  imgproxy binary's checksum matches the October artifact,
  and the venv reports Thumbor 7.8.0). The pins are unchanged
  since October, so rebuilding them would have produced the
  same artifacts; crabcrop alone was rebuilt, from the
  v0.9.9 tag.
- One harness change was forced by the release itself:
  0.9.9 refuses non-public sources by default, so the
  harness now starts crabcrop with
  `CRABCROP_ALLOWED_SOURCES=127.0.0.1` to allowlist the
  loopback origin (committed in `configs/crabcrop.env` and
  in `bench.py`). Nothing else about the crabcrop
  configuration changed.
- The extracted libvips looks for its format modules under
  `/usr/lib/x86_64-linux-gnu/vips-modules-8.15`; a symlink
  from there to the prefix's module directory restores the
  layout the October run measured with. Without it,
  imgproxy reports JPEG XL and AVIF as unsupported formats.
  With it, JPEG XL encodes and AVIF fails exactly as it did
  in October (see the unsupported table).
- The 0.9.9 build used the distribution libdav1d 1.4.1
  (October used a local 1.5.0 pkg-config entry). dav1d only
  decodes AVIF sources; every fixture is a JPEG and AVIF
  encoding is rav1e, so no measured path touches it.
- The imgproxy fidelity caveat from October stands: this is
  an official source build against libvips 8.15.1, while
  the official Docker image carries its own newer libvips,
  so imgproxy numbers are imgproxy 3.31.4 on libvips
  8.15.1, not the Docker image.

## Cache behavior under churn (new, crabcrop only)

`bench_cache.py` rotates 1,200 distinct resize URLs (25
sources at 48 widths, 10,078,080 bytes of output in total)
against a 4 MiB result cache budget, so the working set is
about 2.4 times what the cache can hold and every pass turns
the cache over. Hits are counted from the `Cache-Status`
response header; the server's own `/metrics` counters agreed
with the client counts exactly in every run (for example
150 hits and 7,353 misses in the final run). Thumbor and
imgproxy run with no result cache in the comparison
configurations, so there is no equivalent scenario for them.

| Measurement | Result |
|---|---|
| Fill pass, 1,200 misses | mean 17.8 ms, p50 17.2 ms |
| Probe after fill, first 50 URLs | 0 of 50 still cached |
| Probe after fill, last 50 URLs | 50 of 50 cached, p50 0.2 ms |
| Sequential rotation, pass 1 | 4.2% hits, miss mean 17.8 ms |
| Sequential rotation, passes 2 and 3 | 0% hits, miss means 17.5 ms |
| Rotation at 8 workers, 2 passes | 0% hits, 72.6 req/s, miss mean about 110 ms (queueing on 4 cores) |
| Same 1,200 URLs, cache disabled | miss mean 17.8 ms |
| 50 per-key purges of resident entries | mean 0.2 ms each, 50 removed |
| Recheck after purge | purged keys 0 of 50 hits, unpurged control keys 50 of 50 hits |

Reading: under a sequential scan larger than the budget,
the byte-bounded LRU holds only the most recent roughly
500 entries (the budget divided by the 8.4 KB average
output), and repeat passes get nothing. That is the known
LRU scan pattern, recorded rather than dressed up. The
cost of the turnover itself is a different story: a miss
under constant eviction costs the same as a miss with the
cache switched off entirely (miss means of 17.5 to 18.1 ms
across the three runs, against 17.5 to 17.8 ms with the
cache disabled), so insert and evict work is inside the
noise, at most a few tenths of a millisecond per miss.
Churn does not make misses slower; it makes hits rare.
Purges stay cheap while this goes on: 0.2 ms per key, and
the group purge in the memory section below removed 3,000
entries in 3.6 to 3.8 ms.

## Memory accounting (new, crabcrop only)

The cache budget (`CRABCROP_CACHE_MAX_MB`) bounds payload
bytes only. These scenarios fill a fresh server with known
payloads and compare process RSS growth against the payload
total, so the memory held by keys, group names, and the
cache's indexes is measured. RSS is the server process's
VmRSS, read after a settle pause.

| Fill | Entries | Payload | RSS growth beyond payload, per entry |
|---|---|---|---|
| Small renders (100 to 219 px wide JPEGs, about 3.7 KB average), no groups | 3,000 | 11,147,154 B | 1.6 to 1.9 KB (three runs: 1,781, 1,624, 1,948 B) |
| Small renders through one preset, every entry in group `thumb` | 3,000 | 10,893,144 B | 1.71 to 1.73 KB (three runs: 1,706, 1,728, 1,717 B) |
| Large renders (1600 px wide WebP, about 33 KB average), second batch of 100 | 100 | 3,341,894 B | 2.0 to 4.8 KB (upper bound, see below) |

What the per-entry figure is made of: the canonical key is
stored twice (the entry map and the last-access stamp map),
plus the stamp itself, the stored ETag (34 bytes of text),
the group list, and allocator size-class rounding on every
allocation, the payload included. A group name adds nothing
measurable on top: the grouped and ungrouped fills land in
the same band, so groups are not where the memory goes.

The large-entry figure is a bound, not a point estimate.
At 100 entries the bookkeeping total is a few hundred KB,
under this host's RSS noise floor (shared pages move by
megabytes under memory pressure; one early bare
before/after reading at 50 entries came out negative), so
the large fill is measured as a second batch's growth over
a first batch inside one server, and still carries
residual allocator growth. Even taking the top of the
range, bookkeeping is at most about 15% on top of a 33 KB
payload, against about 50% on top of a 3.7 KB payload. The
pattern is the point: the overhead is per entry, not per
byte, so it is the entry count that sizes it.

Budget plateau: one server with a 4 MiB budget was driven
with the 3,000 small renders (11.1 MB of payload, about
2.7 budgets' worth), then driven again with the same set.

| Point | RSS |
|---|---|
| Idle after warmup | 28.5 MB |
| Cache full (about 1,130 entries resident) | about 37.4 MB |
| End of the second full rotation | 40.5 MB |
| Growth over the last 1,000 requests of that rotation | about 0.15 MB |

The resident entry count is provably capped (after the
drive, the first 100 URLs score 0 hits and the last 100
score 100 hits), and the steady index cost matches the
per-entry measurement: about 1,130 entries at about
1.75 KB is about 2 MB, which with the 4 MiB of payload
accounts for most of the rise from idle. The rest is
allocator high-water behavior under constant turnover,
and it stops growing: the second rotation's growth decays
to about 0.15 MB per 1,000 requests at the end. Total
footprint under permanent churn at this budget is about
1.4 times the idle footprint.

Purge bookkeeping: 4,500 purges of never-stored targets
(3,000 per-key, 1,500 per-group) raised RSS by only 24 to
32 KB in total across the three runs. The purge guard's
tombstone maps are capped per kind (1,024 entries), so
purge history cannot accumulate without bound. A group
purge of 3,000 live entries took 3.6 to 3.8 ms; RSS after
it did not drop (the allocator keeps the arenas), which is
normal allocator behavior, not retained entries: the
purged group's keys all miss afterwards.

Sizing rule this supports: at capacity, the memory tier
costs the payload budget plus roughly 1.75 KB per resident
entry. A deployment that sizes RAM from the budget alone
undercounts by that per-entry term, which matters when
entries are small and numerous (a 256 MiB budget filled
with 3.7 KB renders holds about 72,000 entries and about
126 MB of bookkeeping on top of the budget) and is minor
when entries are large.

## Reading the results, including the losses

1. Every output byte count is identical to October, for
   all three systems and all ten operations. The encoders
   did not change behavior between 0.9.5 and 0.9.9, and
   two independently assembled runs of the harness agree
   byte for byte: the comparison itself is cross-checked.
2. crabcrop cold resize is faster than the October
   figures: median p50 22.6 ms against 30.4, mean 23.1
   against 30.1. Three of the four runs sit at 22.6 to
   22.7; the fourth reads 28.3. Two candidate explanations,
   both recorded rather than resolved: resize work landed
   between the two releases, and October's own notes
   disclose a background compile running during its first
   minute, when crabcrop is the system measured first.
   The safe claim is that resize did not regress and is
   probably faster.
3. Every other crabcrop cold row is within noise of
   October: crop 58.5 against 57.1, WebP q80 64.4 against
   65.5, grayscale 25.3 against 25.8, AVIF 112.4 against
   109.7, JPEG XL 34.0 against 32.8, the sweeps likewise.
   No cold regression anywhere in the set.
4. The losses are the same losses. imgproxy is still
   fastest cold on plain JPEG work, and crop-fill is still
   the largest single gap (crabcrop 58.5 ms against
   imgproxy 12.1): libvips scales and crops in one
   demand-driven pass, and nothing between 0.9.5 and
   0.9.9 changed that.
5. Warm is unchanged. crabcrop still answers repeats in
   0.2 to 0.3 ms from its in-memory cache. Warm resize
   throughput medians 1,918 req/s against October's single
   run of 2,067; today's four runs span 1,846 to 2,185,
   which contains the October figure, so no change is
   claimed in either direction. The topology caveat from
   October stands: neither competitor caches results in
   these configurations, and a CDN in front of any of the
   three mostly erases the warm row.
6. Output bytes at the same nominal quality still differ
   by encoder, in both directions, exactly as in October
   (the numbers are literally the same; see point 1).

## Method notes and limits

- Same method as October: local origin, cold is the first
  request per source, warm is the immediate repeat, one
  8-worker warm-throughput pass on resize, services
  measured alone and sequentially, fresh connection per
  request, 25 samples per operation per run. New this
  time: runs were repeated and the tables report medians
  across runs instead of one run's samples.
- All three run with signature verification effectively
  open (crabcrop and Thumbor unsafe mode, imgproxy without
  key or salt). This measures processing, not HMAC.
- Configurations are the committed files in
  `benchmark/configs/`, plus the one allowlist line noted
  above. Thumbor runs at its defaults (no result storage).
  imgproxy runs with `IMGPROXY_WORKERS=4` per its docs
  sizing guidance and with loopback sources allowed so it
  can fetch the local origin at all.
- This host is shared, and other tenants were active
  during the runs (load average between about 0.8 and 1.7
  on 4 cores, and the host is memory-tight, which is what
  makes raw RSS noisy at small scales; the memory section
  explains how each figure deals with that). Medians
  across runs are the mitigation; treat small deltas as
  noise anyway.
- Single host topology: client, origin, and services
  share one small VM and its loopback. Absolute numbers
  include loopback and client overhead. Rankings can move
  on bigger hardware or with multi-process deployments.
- The cache scenarios measure crabcrop alone, on
  loopback, with the default disk and shared tiers off:
  they describe the in-memory tier's behavior, which is
  the tier the budget configures.
