# Changelog

All notable changes to crabcrop are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and crabcrop uses [Semantic Versioning](https://semver.org/) with one version number across every artifact (server binaries, container images, the `crabcrop-url` crate, the TypeScript and Python SDKs, the MCP server, and the Helm chart). See RELEASING.md for how a release is made.

## [Unreleased]

### Changed

- This release starts a new cache epoch. Changes below alter the bytes served for URLs that already exist (video output with a 16383 px side, some PDF pages near the 16383 px raster limit, and sources with a 16384 px side and no sizing step in the URL, which are now refused, issue #528; a `DPR` or `Sec-CH-DPR` client hint past 1 that took a 16384 px source side through unchanged now steps down to a factor whose output fits 16383 px, so `8192x1` on a 16384x2 source with `DPR: 2` serves 12288x2 instead of 16384x2, issue #529; JPEG XL output from the jixel 0.5.5 encoder, which writes smaller files at slightly lower fidelity at the same quality setting, PR #493), so the rendering version in the configuration fingerprint moves from 3 to 4 and the default configuration no longer prints the 0.10.0 fingerprint, `4ea5a14db70a1f23`. The first start on this version begins a new epoch: entries written by 0.10.0 and earlier stay in the disk and shared tiers under their old keys, unreachable, until they age out, and during a rolling upgrade old and new replicas read and write separate entries instead of serving each other's renders. Expect a cold cache after the upgrade.

- Every output stays within 16383 px per axis (issue #528). A source with a 16384 px side, which decodes, kept that side through a chain with no sizing step: a WebP output failed with `500 image encoding failed`, whether `format(webp)` named it or `Accept` negotiated it, and every other format served 16384 px, past the documented limit. Such a request now answers `400 unsupported_operation` in every format, with a message that asks for a resize or crop, and `/explain` reports it as `over_dimension`; a chain that brings the side within the limit renders as before. Video output no longer pads a 16383 px side up to 16384 for H.264 and VP9: that side crops its last row or column to 16382 instead. A PDF page's render scale is clamped to the 16383 px output limit instead of the 16384 px decode cap, with a pixel of margin for the probe's rounding, so a page that rendered at the old cap is served without a resize, unless its media box is larger than the crop box the probe measures.

- A `DPR` or `Sec-CH-DPR` client hint no longer fails a request: when the hinted factor alone pushes a size past 16383 px on an axis or past the 100 million pixel budget, the image is served at the largest of 1, 1.5, 2 and 3 that fits, instead of answering `400` (issue #529). Before, `/unsafe/6000x1/<source>` with `DPR: 3` and `/unsafe/8000x8000/<source>` with `DPR: 1.5` failed on high-density screens only, while the same URL rendered on a desktop. A `dpr(...)` in the URL, a preset or `CRABCROP_DEFAULT_OPS` is never stepped down and keeps its `400`, and so does a URL past the limits at factor 1. A hinted factor past 1 never serves a side past 16383 px, even one a 16384 px source already had: `8192x1` on a 16384x2 source with `DPR: 2` served 16384x2 and now steps down to 1.5 and serves 12288x2. The factor is settled from the source's header before the decode where the header shows the sizes, so a hint costs one render there, and an animated output past the budget across its frames is refused after its first frame instead of after a budget's worth of frames. A stepped-down render is cached under the hinted factor, so it never answers the URL without the hint. `/explain` now reads the DPR hint and forecasts the factor the image request applies, as `forecast.dpr`, `dpr_from` and `dpr_hint`.

- The cargo group bump moves the JPEG XL encoder `jixel` from 0.5.2 to 0.5.5, `fast-ssim2` from 0.9.0 to 0.9.1, and `ureq` from 3.5.0 to 3.5.1 (PR #493; `c2pa` 0.91.11 from the same group already landed). At the default quality the new encoder writes JPEG XL files 11 to 19 percent smaller at slightly lower fidelity: across a seven image sample, PSNR moves down 0.02 to 0.55 dB and SSIMULACRA2 down 3.3 to 5.7 points on the photographic images, while quality 90 stays close to neutral. The tradeoff was measured before landing and is taken deliberately. This changes the bytes served for existing `format(jxl)` URLs, and the upgrade corpus entry `format-jxl` is re-baselined for this reason.

- The boot line `crabcrop listening on port N` names the port the server bound (issue #536). It printed the configured port, so `PORT=0`, which binds a free port, printed port 0; it now prints the port the system picked. For a fixed port the line is unchanged.

- HEIC sources decode with oxideav-h265 0.0.16, the version the SPS pre-check in `src/heic.rs` and the fuzz harness already ran. The lockfile also carried 0.0.15, which oxideav-heif decoded with, and `fuzz/Cargo.lock` had drifted from the root lock; now one version decodes, pre-checks and fuzzes. The decoded pixels of every HEIC test fixture are unchanged, and some HEIF stills that 0.0.15 refused now decode. `scripts/check_locks.py`, run in CI, fails when a decoder is locked at two versions or when the two lockfiles disagree on a package both carry. The release workflow no longer adopts a GitHub Release that is already published, as it silently adopted v0.10.0's, published by hand before the gates ran: the job stops and says how to recover, RELEASING.md names the workflow as the only way to publish, and the `ADOPT_PUBLISHED_RELEASE` repository variable set to 1 overrides the refusal for one re-run (issue #552).

- Test and CI reliability. A failed check in the disk-read test that blocks on a FIFO no longer hangs the suite: the test lets the held read go on every exit path and puts a deadline on each request and on the wait for the read, and every job in `rust.yml` and `functional.yml` has a `timeout-minutes` (issue #543).

## [0.10.0] - 2026-11-08

### Added

- `CRABCROP_SOURCE_MAX_MB` and `CRABCROP_SOURCE_TIMEOUT_SECS` set the source fetch cap and timeout (issue #471). Both were fixed at 10 MB and 10 seconds, and they bound video and PDF sources too, so a deployment could not serve `frame:` from longer clips or `page:` from larger PDFs. The defaults are unchanged. The cap takes 1 to 1024 and the timeout 1 to 600; any other value, an empty one included, stops boot with an error naming the variable. The upload cap (`CRABCROP_UPLOAD_MAX_MB`) defaults to the fetch cap and may not pass it. The default source buffer budget is four fetch caps per processing lane permit, so raising the cap raises the budget too: set `CRABCROP_SOURCE_BUFFER_MAX_MB` yourself to keep memory where it was. Boot prints a `source fetch:` line with the cap, the timeout, and the budget. It also warns on stderr when `HTTPS_PROXY`, `HTTP_PROXY`, or `ALL_PROXY` (either case) is set while hostname sources are pinned, which is the default (private-address blocking on, no `CRABCROP_ALLOWED_SOURCES`): pinned fetches connect directly, so they fail where egress goes only through a proxy. The warning names the variables, never their values. To fetch through the proxy, list the source hosts in `CRABCROP_ALLOWED_SOURCES`.

### Changed

- This release starts a new cache epoch. Several fixes below change the bytes served for URLs that already exist (interlaced PNG output from 16-bit sources, issue #464; focal forms carried through the steps before a crop, and `trim` on animations, issue #465; redaction of sources with transparency, and large blurs on opaque RGBA sources, issue #444; metadata written back under `preserve` and `keep_profile`, issue #445; face, objects, and zoomed `focalpoint:` crops, issue #478; SVG documents that nest a gzip-compressed SVG image, issue #443), so the rendering version in the configuration fingerprint moves from 2 to 3 and the default configuration no longer prints the 0.9.11 fingerprint, `5ebb58197f92d959`. The first start on this version begins a new epoch: entries written by 0.9.11 and earlier stay in the disk and shared tiers under their old keys, unreachable, until they age out, and during a rolling upgrade old and new replicas read and write separate entries instead of serving each other's renders. Expect a cold cache after the upgrade.

- Meta mode is off by default (issue #453). When you upgrade, set `CRABCROP_META_MODE=1` on any deployment that uses meta responses (`Accept: application/json` on an image URL), the `crabcrop meta` verb, or the MCP server's `fetch_meta` tool; without it those requests answer `403 meta_disabled`. Meta responses skip every cache tier, so while meta was on, anyone holding a signed URL could make the server fetch the source, render it, and run the annotation models again on every request. 0.9.11 added the switch but left it on. The switch takes the usual boolean spellings, and boot prints `meta mode: on` when it is on. With meta off, a meta request is refused before any fetch or render, and the message names the switch. The refusal now carries the meta document's `Cache-Control: private, no-store` and `Vary` headers, so a CDN that caches error responses cannot serve it in place of the image. The same `Accept` header also selects the JSON error envelope, so while meta is off, a JSON request that passes the signature, grammar, and expiry checks answers `403 meta_disabled` rather than its own error code.

- Three settings that used to boot now stop boot, so check them before upgrading (issue #469): `CRABCROP_DEFAULT_OPS` carrying `exp:` or `maxage:`, which the server dropped without a word, so every response kept the one-year lifetime; default operations that alone run past the 100-operation cap, under which every request failed; and a preset in `CRABCROP_PRESETS_FILE` whose filters take it past 100 operations, which the boot check missed because it counted segments, not filters. The cap itself is now checked right after parsing, before any source fetch, on the image and `/explain` routes. Only the engine counted before, on an image already fetched and decoded, so an over-cap URL cost a fetch and a decode before its `400`, and `/explain` answered `200`. The count is taken after `preset:` references expand and with `CRABCROP_DEFAULT_OPS` merged in, and each filter in a `filters:` segment counts once. The refusal keeps the engine's `400 unsupported_operation` and its message. Because the check now runs first, a URL that is over the cap and also expired, or also names a bad root, answers with the cap error.

- `crabcrop` starts the server only when it runs with no arguments (issue #470). A custom launch that passes the server binary an argument (container args, a systemd `ExecStart`, a wrapper script) must drop it, because the binary now exits 1 instead of serving. The shipped images and deploy recipes pass none, and a test holds them to that. Every argument but the internal SVG worker flag now goes to the CLI, and one it does not know, a flag included (`crabcrop --verison`, `crabcrop --port=8080`), exits 1 with `unknown verb` and the usage on stderr. Before, a first argument that began with a dash, other than `--help`, `-h`, `--version`, and `-V`, fell through to the server start, so with a secret set a typo bound the port and served. The server reads its configuration only from the environment. `crabcrop --help` gains a Flags section that lists every flag, with the environment variable for `--base`, `--secret`, and `--key-id`.

- Source bytes held in memory share one process-wide budget (issue #403). A cache miss used to load its whole source, up to the fetch cap, and every watermark before any gate admitted it, and then copied the source for the render, so a burst of distinct misses could hold gigabytes while most of those requests were shed with `503` anyway. Each source, watermark, fallback, and upload body is now charged to the budget as it arrives, and it stays charged until the render or upload that uses it finishes. An origin that answers and then stalls holds only the bytes it sent. A request that cannot get budget within 5 seconds answers `503 server_busy` with `Retry-After: 1`, as a full gate does. `CRABCROP_SOURCE_BUFFER_MAX_MB` sets the budget, from the fetch cap to 65536. The default is four fetch caps per processing lane permit (one permit per core plus the slow-lane permits): at the default 10 MB cap, 80 MB on one core and 200 MB on four. A host that buffers many large sources at once may see new `503` sheds. `/metrics` reports `crabcrop_source_buffer_bytes` against `crabcrop_source_buffer_capacity_bytes`; if requests shed while the two sit level, raise the budget. Rendered bytes are unchanged.

- Bad source URLs, unreadable uploads, and timestamp authority outages answer with their own status and code (issue #467). Alerts and log parsing keyed on the old statuses or the old upload outcome need updating. A source URL that does not parse, names a scheme the server does not fetch, or is a malformed bucket or file locator (`s3://` with no bucket or key, a file path with a NUL) answers `400 invalid_source` instead of `502 source_fetch_failed`, and never falls back to `CRABCROP_FALLBACK_IMAGE`, since the fault is the URL's own. A redirect to such a URL is the origin's answer and stays `502`. Watermark URLs and the `/explain` route answer the same, and so does a segment kind this server does not know, which it reads as source text. An upload body that cannot be read to its end (aborted, or with malformed chunked framing) answers `400 upload_unreadable` instead of `413 upload_too_large`, and the upload log outcome `rejected:oversize-or-unreadable` splits into `rejected:oversize` and `rejected:unreadable`. On a server with no upload destination, a `PUT /upload/...` answers `404 uploads_not_configured`, a documented code that was never sent before, and a `GET` there answers `405` with `Allow: PUT`. A C2PA timestamp authority that stalls, refuses the connection, or answers with something that is not a timestamp makes the request answer `503 provenance_unavailable` with `Retry-After: 30` instead of `500 encode_failed`.

- A `CRABCROP_GCS_ENDPOINT` that is not an `http` or `https` URL is now a startup error, as the S3 endpoint already was (issue #455). It used to boot and fail every `gs://` fetch, so correct it before upgrading. A shared result store (`CRABCROP_RESULT_BUCKET`) or upload bucket (`CRABCROP_UPLOAD_BUCKET`) whose HTTP client cannot be built, for example on a host with no CA certificates, panicked at boot; boot now exits 1 with `cannot build the shared result store client` or `cannot build the upload store client`, followed by the cause. Secrets also print as `[redacted]` in Debug output. The signing keys, the AWS and GCS secret keys and session token, the cache entry key, and the metrics token lived in types that derived `Debug`, so any `{:?}`, `dbg!`, or panic message that formatted one would print the secret. The server never formats them, but the types are public in the library target.

- The Next.js and Hydrogen integrations check sizes the way the Astro, Nuxt, and SvelteKit ones do (issue #460). Upgrade `@crabcrop/url` together with the integration files: all five now import `MAX_DIMENSION` from it, which 0.9.11 does not export. A fraction rounds to whole pixels, a value that is not a size (0, negative, or not a number) is left out so the source's own size is served, and a value past the 16383 px cap throws. Both loaders used to put the value into the URL unchecked, so a negative width came back flipped (`-5x0`) and an over-cap width as a URL the server refuses. A missing base now throws too: Hydrogen at `createCrabcropLoader`, and Next.js when the loader is called with `NEXT_PUBLIC_CRABCROP_BASE` unset. Both used to return a relative `/unsafe/...` URL; a site that relied on it sets the base to its own origin. `@crabcrop/url` also exports the `FormatOptions` and `PerFormatQualityFormat` types its builders already used.

- The URL builders refuse the characters a browser rewrites in a path: `"` `<` `>` `\` `^` `` ` `` `{` `|` `}` (issue #472). Code that passed one of them in a source or operation now gets an error and must percent-encode it instead (`x{y}.jpg` becomes `x%7By%7D.jpg`), which an HTTP origin decodes. The server verifies the raw path, but a page's `<img src>` or `fetch()` turns `\` into `/` and percent-encodes the rest, so a URL signed over one of them worked from curl and answered `403` in a browser. The Rust crate, the TypeScript and Python SDKs, the playground, and the WordPress plugin refuse them in operations and sources, for signed, unsafe, and sealed URLs, and so do the framework loaders and the MCP server's `sign_url`, which build on the TypeScript SDK. The error names the percent-encoding to use, and the WordPress plugin keeps the original image URL. The TypeScript typed builders also write 32-bit-float arguments as the server parses and prints them (`focalPoint(0.1 + 0.2, 0.4, 2)` now writes `focalpoint:0.3x0.4:2`, where it wrote `0.30000000000000004`; convolution kernels keep their 64-bit spelling), refuse a `blur`, `gamma`, `sharpen`, focal zoom, or object-crop scale that is zero or infinite as a 32-bit float, and trim class names. `spec/test-vectors.json` gains refusal vectors.

- Release runs check the approval gate and CI before they build, and adopt a release that already exists (issue #457). A new preflight job stops a tag run unless the `release` environment has a Required reviewers rule and the tagged commit passed `rust.yml` on main. The host job updates an existing release for the tag instead of failing on it, which every tag run from v0.9.8 to v0.9.11 did on its first attempt. The one-off `mcp-publish-v010.yml` workflow is gone.

- A step that works out an output size past 16383 px on an axis is refused with `400 unsupported_operation`, as a written size past the limit already is (issue #521). Before, `16383x1/0x2` rendered 32766x2, and so did a fit-in, a crop followed by a resize, `dpr()`, a pad canvas or a rotated canvas that grew a side past the limit; with WebP output these failed with `500` instead. Every URL that rendered within the limit renders the same bytes. `/explain` reports the refusal as `over_dimension`, and its forecast now follows the engine for SVG sources (their raster size), `no_upscale` caps, `rotate(...)` and trims.

- Releases wait for the real-model AI tests (issue #414). These tests run the AI code against the real ONNX Runtime and models. They ran only weekly and by hand, and nothing waited for them, so v0.9.10 shipped AI changes that had never run against real models. Every tag run now calls `ai-models.yml`. The job that creates the GitHub Release runs only when it passes, and the image and registry jobs wait for that job, so a failed model download blocks the release until the failed jobs are re-run. The workflow also runs on pull requests and main pushes that touch `src/ai.rs`, `src/tokenizer.rs`, or the fixture photo the tests read. The CLIP live test now compares the tokenizer's output with reference token ids and checks that the top label describes the fixture photo, so a phrase-label regression like the one in issue #404 fails it.

- The release version tooling reads one list of version sites (issue #486). `scripts/bump_version.py` and `scripts/check_versions.py` each kept their own list, and both missed pins: a bump left 33 mentions of the old version in 13 files (the README image lines, `values-production.yaml`, the crate entries in both Cargo lockfiles, every `package-lock.json`, and test fixtures) while the check still passed. Both scripts now read `scripts/version_sites.py`, which also covers the playground package and, on a minor bump, the server's `crabcrop-url` requirement. Each site states how many pins it holds, and a different count fails the check and stops the bump before it writes anything. The bump moves the lockfiles too, so RELEASING.md step 2 drops `cargo update -w` and tests with `--locked`, and a gate test bumps a copy of the tree and fails on any old version left behind.

- The engine's two longest functions, `apply_operations` and `process_preferred`, are split into one function per pipeline stage (issue #417). The server and engine unit tests move into `src/server/tests.rs` and `src/engine/tests.rs` (PR #440). The environment variable manual at the top of `src/main.rs` gives way to a pointer to docs/configuration.md, and doc comments that earlier code moves had left on the wrong items are back on the items they describe (PR #441). The meta helpers lose an `ai_gated` parameter that was always false, and the cache key loses a fallback that never ran (issue #456). Behavior and rendered bytes are unchanged.

- Test and CI reliability. CI fails on a broken intra-doc link (PR #441). Property tests cover the URL grammar, signing and sealing, and crop windows; each property runs 64 cases, and `PROPTEST_CASES` runs more (issue #478). The unit tests that stand a script in for FFmpeg, pdftocairo, or pdfinfo now write it from a child process, which ends an intermittent `Text file busy` failure when test threads spawn tools in parallel (issue #523).

- ThumbHash strings are the same bytes on every platform (issue #458). The encoder now takes its cosines from the portable `libm` crate instead of the system math library, whose last bit differs between glibc and Apple's libm. A coefficient that lands exactly on a rounding tie can therefore come out one step different from before on Linux, which changes that image's `thumbhash` in meta responses. Meta responses are never cached, so no stored entry is affected.

- Shared-tier purges are paced and coalesced (issue #462). A purge reads entry headers 16 at a time instead of one by one, purge requests share a budget of 32 reads in flight, and at most two background walks run at once. A purge whose target is already being walked joins that walk instead of listing the bucket again, and one re-list afterwards removes copies rendered in between. A walk that the bucket fails part way (a listing, read or delete with no answer) no longer ends its purge: the tombstone stays in force until a later purge of the same target completes a walk, and each failure counts in `crabcrop_cache_tier_errors_total`.

- The server drains for at most `CRABCROP_SHUTDOWN_GRACE_SECS` after `SIGTERM` or Ctrl-C, 8 seconds by default, then exits (issue #463). It stops accepting connections, lets the requests in flight finish, and waits for the shared-tier writes they left behind; a second signal ends the drain at once. Before, shutdown had no deadline, and background shared-tier writes died with the process. The Helm chart passes the new `shutdownGraceSeconds` value as `CRABCROP_SHUTDOWN_GRACE_SECS` and sets the pod's `terminationGracePeriodSeconds` to it plus 5 seconds. Shared-tier writes are bounded too: at most 64 run at once, and a render's write-through that finds no free slot is skipped and counted as `crabcrop_cache_shared_puts_skipped_total` on `/metrics`, next to `crabcrop_cache_shared_puts_in_flight` and `crabcrop_cache_shared_puts_capacity`. A cache entry's group write-back is never skipped.

### Removed

- Source formats crabcrop never documented are no longer decoded (issue #466). The image crate's default features compiled decoders for OpenEXR, Radiance HDR, QOI, PNM (PBM, PGM, PPM, PAM), DDS, TGA, and farbfeld, and the generic decode picks a decoder from the source bytes alone, so every one of them but TGA rendered though no doc promised it. They now fail with `502 decode_failed` as sources and `415 upload_not_an_image` as uploads; convert any such sources still in use. The decoded set is JPEG, PNG, WebP, GIF, JPEG XL, TIFF, AVIF (in builds with AVIF decoding), HEIC/HEIF, SVG, and BMP and ICO, which were decoded before and are now documented. A HEIF file decodes only when every image it is built from is HEVC-coded; one that would need another codec, such as an AV1 item behind a generic `mif1` brand, fails with `502` before decoding starts. Unlike every other upload format, the removed formats had no file extension binding, so a QOI file could be stored as `promo.html`; every accepted upload is now bound to its format's extensions, and a name with no extension is still accepted. Uploads already stored in a removed format, under any extension, stay in the upload store, so a deployment that accepted uploads may want to review it. The build also drops ort's default features: OpenSSL and ndarray are no longer build dependencies, and ONNX Runtime errors now reach stderr through its own logger (`ORT_LOG` sets the level) instead of being discarded.

### Fixed

- Shared-tier purges leave a tombstone in the bucket and judge each copy by when its render began (issues #446, #461). In 0.9.11, while a purge's background scan ran, the receiving server treated every disk or bucket copy the purge covered as purged, including copies rendered after the purge began, so each request deleted and re-rendered a fresh copy, and the scan deleted it again and counted it. The running-purge record also lived only in memory: a restart mid-scan lost it, and bucket copies the scan had not reached served again on every replica. Every persisted copy now records when its render began, and a purge writes an authenticated tombstone under `purges/` in `CRABCROP_RESULT_PREFIX` before it touches any tier. Each replica reads the tombstones at boot, before it serves, and every 5 seconds after. A bucket that does not answer holds boot for up to the store client's 10-second request timeout; the server then starts and retries the read every 5 seconds. While a tombstone lives, a disk or bucket copy it covers is a miss only if it was written before the purge began; later copies serve and cache normally, and the scan leaves them in place and does not count them. The scan deletes a bucket copy only if it is still the copy it read (`If-Match`), and repeats the delete without the condition on a store that answers `501`. A tombstone expires 15 minutes after its scan ends. Keep replica clocks within 5 seconds of each other; a copy another replica renders in the first 5 seconds after a purge is not cached. The cache entry format becomes `CRABDISK6`, which earlier releases cannot read: rolled back, one deletes the new entries from its disk tier at boot. During a mixed-version rollout, send purges to upgraded replicas, because an earlier replica writes no tombstone and its scan skips the new entries. A purge still does not reach another replica's memory or disk tier: a disk copy there that nobody requests before the tombstone expires can serve again afterwards. Send the purge to each replica when it must take effect everywhere (issue #351).

- SVG sources are parsed and rendered in a separate worker process (issue #447). The server ran the SVG renderer in its own process, and some documents get past the structural bounds anyway: a 130-byte path whose arc radii flatten into billions of segments made one request allocate until the server process died, with every request in flight. For each SVG the server now starts its own binary as a worker, which caps its own CPU time and, on Linux, its address space at 4 GiB, and is killed at the request's processing deadline (`CRABCROP_PROCESS_TIMEOUT_SECS`). A worker that crashes or runs out of memory fails its own request with `502 decode_failed`, one still rendering at the deadline fails with `504 processing_timeout`, and the server and every other request carry on. Upload validation and the SVG size probe behind `/explain` use a worker too; that probe gives up after 5 seconds and reports no size. Rendered bytes are unchanged. Each SVG costs one process start, about 9 ms on a debug build, plus a system font scan when the document has text. The worker reads documents up to 64 MiB, so with `CRABCROP_SOURCE_MAX_MB` raised past 64 a larger SVG fails with `502`.

- SVG sources are bounded before the renderer builds anything (issue #443). The renderer converts a referenced element again each time it follows a reference (`feImage`, masks, clip paths, markers, patterns, `<use>`), so a few kilobytes of chained references expanded exponentially, and the 100,000-node limit was checked only after the tree was built, too late to stop the allocation that exhausted memory and aborted the process. A reference cycle overflowed the stack, and an `href` cycle between gradients, patterns, or filters kept a blocking thread spinning without end. The node limit and the 256 MiB decode budget are now checked from the document's structure first, counting each element, each character of text, and each embedded payload once for each time it is drawn or copied. References may nest at most 128 levels deep, a reference cycle is refused, and SVG images nested in the document share its bounds. A document past any bound fails with `502 decode_failed`, and a reference chain that would expand exponentially fails in milliseconds. Documents that rendered before render the same bytes, except that a gzip-compressed (svgz) nested SVG image is no longer drawn, and a document is now refused when its references nest past 128 levels or the structural count puts it past a bound.

- AVIF sources whose container declares more than it holds fail before the container is parsed (issue #522). The AVIF container parser sets memory aside for the size a box declares before it reads the box, ahead of every crabcrop decode limit, so a file of a few hundred bytes could make it reserve close to 1 GiB. On a default Linux host that reservation is virtual, but it fails where virtual memory is capped, such as a container with overcommit disabled. A check before the parser now refuses a box that declares more bytes than the file, or the box around it, holds, and an item count its box has no room for. A refused source answers `502 decode_failed`, or `415 upload_not_an_image` for an upload, as an undecodable source did before, and the server log names the box. Well-formed AVIF files decode to the same pixels as before.

- Redaction replaces the pixels it covers instead of blending over them (issue #444). `blurfaces`, `pixelatefaces`, `blurclass`, `pixelateclass`, `blur_region`, and `pixelate_region` composited the redacted patch over the original, so wherever the patch's alpha was below 255 the original color came through: all of it at alpha 0, a third at alpha 128. Face detection reads color only and JPEG output drops alpha, so a face stored at alpha 0 was found, redacted, and served intact. The redacted pixels, alpha included, now take the place of the originals. An area of uniform alpha keeps that alpha exactly, so an opaque image stays opaque, and a silhouette's soft edge still mixes the two by the mask's strength. This changes the bytes served for existing redaction URLs of sources with transparency. It also changes them for large blurs on opaque RGBA sources (faces of 118 px or more, class and region boxes of 150 px or more), where the old blend let about 1% of the original back in (up to 2 levels before encoding). Sources without an alpha channel render as before.

- Metadata written back into an output is bounded (issue #445). Under `CRABCROP_METADATA=preserve`, a PNG source's compressed XMP packet was written back uncompressed, so a 29 KB source could render to a 16 MiB PNG. Under `keep_profile`, a compressed profile went into a JPEG output raw, up to 4 MiB. A PNG output now stores the XMP packet compressed when the source did, and an XMP packet over 256 KiB is dropped (it was read up to 16 MiB). Only a well-formed ICC profile of at most 256 KiB, with a header size that matches its length and the `acsp` signature, is embedded in JPEG or PNG output. Under `keep_profile`, any other profile is converted to sRGB instead of leaving untagged pixels in a space nothing labels. One source's metadata now inflates within 4.25 MiB instead of 20 MiB. This changes the bytes served for existing URLs on `preserve` deployments whose PNG source stored its XMP compressed or carried more than 256 KiB of it, and for `keep_profile` URLs whose source profile is malformed or over 256 KiB.

- `@crabcrop/url` works in browser bundles (issue #381). The SDK imported `node:crypto` and used `Buffer`, so a client bundle that included it failed to build under Vite 7, webpack 5, and esbuild, and a Vite 8 bundle threw `Buffer is not defined` when the page loaded. This broke the client side of the Nuxt, SvelteKit, Hydrogen, and Next.js integrations. A `browser` import condition now selects a built-in TypeScript implementation of SHA-256, HMAC-SHA-256, and AES-256-GCM, which is also the default for runtimes that are neither a browser nor Node; Node keeps `node:crypto`. The API stays synchronous, and signatures and sealed tokens are byte-identical on both. The Nuxt provider also failed with a real `@nuxt/image`: it read its options from the wrong argument, and it had no default export, so `@nuxt/image` 2 failed the build. It now works with `@nuxt/image` 1.8 or later. The provider is copied, not installed, so copy the new `frameworks/nuxt/crabcrop.ts` into your project.

- A resize or fit-in side written as a zero of more than one digit (`00x100`, `100x00`, `fit-in:00x100`) answers `400 unsupported_operation` (issue #464). The grammar reads such a side as an exact zero, not the proportional `0`, and the engine then answered `500`, rendered a 1-pixel side when DPR or fit-in rounded the zero up, or hid it behind a later size in the chain. A lone `0` keeps its meaning. The `/explain` forecast reports the refusal in a new `zero_side` field, with null dimensions and pixel count, instead of forecasting `0x100`. In the same change, floating-point TIFF sources render to PNG, AVIF, and lossless WebP (`quality(100)`) instead of failing with `500`; their samples are clamped to the 0 to 1 range and encode like a 16-bit source. Lossless WebP output from 16-bit PNG sources failed the same way and now encodes. Interlaced PNG output (`format(png,interlace)`) from a 16-bit source wrote each sample's two bytes in the host's order, swapped on little-endian machines; it now writes them big-endian, as PNG requires. This last fix changes the bytes served for existing URLs.

- `focal:` and `focalpoint:` follow the image through the steps between their segment and the crop (issue #465). A focal form reached the crop in the coordinates of the image at its own segment, whatever ran in between, so a resize, `crop-rect`, or pad before the crop put the window in the wrong place: on a 2000x1000 source, `focal:600x0:700x100/500x0/crop:100x100` centered well to the right of the rectangle. A resize or `fit-in` now scales the form, a resize flip mirrors it, a `crop-rect` or `trim` cuts it (any part the cut removes lands on the cut's nearest edge), and a `pad` places it on the canvas. Filters that only paint in place (watermark, overlay, text, border, removebg) keep it while the frame size is unchanged, and a filter that moves pixels another way (`rotate`, `flip`, `upscale`, `studio`) drops it, so the crop falls back to its own alignment. In the same change, `trim` on an animation cuts one window for every frame, the smallest box that holds what each frame's own trim would keep. Each frame used to be trimmed on its own, so GIF frames came out at different sizes on a screen sized by the first frame, animated WebP output failed with `500`, and video output failed with `400`. Both fixes change the bytes served for existing URLs.

- Face, objects, and zoomed `focalpoint:` crops no longer cut a window one pixel off (issue #478). The face and objects crops capped their region at the frame instead of the fill window, so a region clamped to a fractional fill size rounded one pixel past it, wider than any other crop of the same aspect. A `focalpoint:` crop with a zoom above 1 divided the already rounded-down fill window by the zoom and rounded again, which could leave it more than a pixel off the target aspect. Both now stay within the fill window and within a pixel of the target aspect. Output dimensions are unchanged, because the window is resized to the requested size, but this changes the bytes served for existing URLs with such crops. New property tests found both faults.

- `/explain` forecasts from the server's default operations and no longer overflows (issue #468). The image request runs `CRABCROP_DEFAULT_OPS` merged ahead of the URL's own operations, but the forecast walked only the URL's, so under a default `filters:format(webp)` it forecast the source format while the image was served as WebP. The forecast and the source admission now use the merged list, as the canonical form already did, so a default `frame:` also admits a video source to explain; the report's operation list stays the URL's own. The JSON `forecast.format_from` gains a third value, `default`, next to `operation` and `source`, and the HTML says the format comes from the server's default operations. The forecast arithmetic also overflowed on a `crop-rect` with corners near 2^32 followed by `upscale`: a debug build panicked and dropped the connection, and a release build could wrap the pixel count to 0 and report it under the budget. Sizes and pixel counts now saturate, and a saturated count reports over the budget.

- A `TMPDIR` that names no directory no longer fails every PDF page render, and every external tool's failure log quotes the end of its stderr (issue #481). The frame extractor, the PDF tools, and the video encoder each had their own copy of the tool runner, and the copies had drifted; they now share one. The PDF tools set the temporary directory as their working directory even when it did not exist, so every page render failed at spawn with a `502`; a tool now runs where the server runs when the directory is missing, and frame extraction still needs it to stage its source. The encoder, which ran in the server's working directory, now runs in the temporary directory like the other tools. Failure logs quote the last 500 characters of the whole stderr stream: the encoder quoted the first 500, and the frame and PDF tools quoted the end of what they had captured, which missed the error when stderr ran past their capture cap. Otherwise, timeouts, output caps, and rendered bytes are unchanged.

- Documentation corrections (PRs #441, #448). `CRABCROP_PROCESS_TIMEOUT_SECS` does not cut gate waits short: each gate keeps its own fixed wait (5 seconds for the stills lane, 10 for the others), and a wait that runs out answers `503` even past the limit. A failed face or class detection answers `502 inference_bad_output` or `500 inference_failed`, where the AI guide said `500` alone. An OCR request is never cached; the meta and AI guides said it caches the image entry. A size-shaped segment that fails to parse (`300xabc`, `16384x10`) is a `400 invalid_size`, as the server answers, where the signing spec called it source text. The client API lists in docs/clients.md include key-ID signing, sealing, and upload signatures. The WordPress plugin README no longer says a down or misconfigured instance falls back to the original URL, because the plugin never contacts the instance. Running the TypeScript SDK or the MCP server from source needs Node 22.18 or newer. docs/configuration.md, now the only configuration reference, also states that `CRABCROP_WIDTH_STEP` accepts 1 to 2000, that the S3 and GCS key pairs are set together or not at all, that AWS credentials are read once at startup, and that a partial segmentation, CLIP, or OCR model set is a startup error.

- The TypeScript SDK's `explainUrl` and `ops.cropObjects`, and the playground's explainer, fold repeated `objects(...)` class names ASCII-only, as the server does (issue #482). `É` and `é` (or `K` and the Kelvin sign) are two classes, so a list that reaches 33 distinct classes that way is now refused instead of passing the SDK and failing on the server with `400 invalid_crop`, and a shorter list keeps both spellings, as the server's canonical form does. The playground's explainer is now a generated build of the SDK's own, so its `studio(...)` description matches the SDK's.

### Security

- The Nuxt provider keeps the signing secret out of the client bundle (issue #381). It used to take the secret as a provider option, and `@nuxt/image` writes provider options verbatim into a generated module that client code imports, so a secret set there shipped to every browser, even though the provider signed only on the server. The provider now reads the secret from private runtime config (`runtimeConfig.crabcropSecret`, set with `NUXT_CRABCROP_SECRET`), and it throws if it finds a `secret` provider option. If you set the secret as a provider option, treat it as public: rotate it on the server, and set the new one in runtime config.

- The MCP server's `purge_result` sends its POST only to `/purge/` under `CRABCROP_BASE` (issue #459). The tool checked only the origin of a per-call `base` and then joined it to the path as a string, so a `base` on the configured origin that carried a path, query, or fragment could send the POST anywhere on that host and return the answer to whoever controlled the tool arguments. A tab or newline inside a `..` segment also passed the dot-segment check, because the URL parser drops those characters; the check now drops them first, so such a segment is refused before anything is sent. The request URL is now built from `CRABCROP_BASE` alone, which may carry a path for a server mounted under a prefix. A per-call `base` is only checked, and must equal `CRABCROP_BASE` apart from trailing slashes. A `?` or `#` in the purge path is sent percent-encoded inside the path. `CRABCROP_BASE` must be an `http` or `https` URL with no userinfo, query, or fragment, or the tool refuses before sending anything. `sign_url` and `fetch_meta` are unchanged.

- A sealed URL's responses no longer carry `Cache-Group`, and the `/metrics` token check no longer leaks the token's length (issue #454). The header listed the preset names read from inside the token, so anyone who fetched a sealed URL could read the presets it was meant to hide. crabcrop's own `purge-group` still reaches sealed entries, because group membership is recorded on the cache entry and never read back from the header. The CDN group purge bridges that copy this header into edge tags (the Cloudflare Worker, Fastly, BunnyCDN, and CloudFront recipes) no longer tag sealed responses, so purge sealed URLs at the CDN by URL. The token check used to return early when the presented token's length differed; both tokens are now hashed before the constant-time comparison. The `Bearer` scheme name is also accepted in any letter case, as RFC 9110 allows; the token itself stays case-sensitive.

## [0.9.11] - 2026-11-07

### Added

- A configuration switch for meta mode (issue #390). Meta mode answered any `Accept: application/json` request on a signed URL with an uncached full render plus up to five annotation inferences, and a deployment had no way to turn it off. `CRABCROP_META_MODE` now controls it, parsed with the usual boolean spellings and on by default for compatibility; with it off, a meta request answers `403 meta_disabled`. Renders are unaffected.

- Cache tier failures are logged and counted (issue #367). The disk and shared tiers used to drop their failures silently, so a dead tier could go unnoticed for weeks. Each failure is now logged as it happens and counted on `/metrics` as `crabcrop_cache_tier_errors_total`, with `tier="disk"` and `tier="shared"` series for the configured tiers. The tiers stay best-effort: a failed write is still a dropped write, never a failed request. The disk tier also probes its directory with a scratch file when it opens, so an unwritable result directory fails at boot with a clear message.

- `crabcrop --version` and `crabcrop -V` print the version and exit. Both used to fall through to the server start, binding the port (and failing without a secret) instead of answering.

- The release pipeline publishes the MCP server package, `@crabcrop/mcp`, to npm next to the other registry packages, behind the same `release` environment approval (issue #382).

- Fuzz targets for image decoding, source metadata, and operation chains (issue #387). The fuzz package covered only the URL parser and the sealed-token opener; three targets now run the decoders and the SVG sanitizer, metadata extraction and re-injection, and a parsed request's filter segments against a synthetic image. The local gate's smoke sweep exercises their seed corpora without cargo-fuzz.

### Changed

- This release starts a new cache epoch (issue #412). Several fixes below change the bytes served for URLs that already exist (sharpen, `keep_profile` on WebP, AVIF, and JPEG XL output, animated sources under format negotiation, animated smart crops, detection-driven filters after a geometric step, arbitrary-angle rotations whose canvas was one pixel off, and `pixelatefaces` mosaics for faces under 20 px), so the rendering version in the configuration fingerprint moves from 1 to 2 and the default configuration no longer prints the 0.9.10 fingerprint, `7b993291c4880a4d`. The first start on this version begins a new epoch: entries written by 0.9.10 and earlier stay in the disk and shared tiers under their old keys, unreachable, until they age out, and during a rolling upgrade old and new replicas read and write separate entries instead of serving each other's renders. A new gate check, `scripts/check_rendering_version.py`, fails when an upgrade corpus entry has been re-baselined since the last release tag without a rendering version bump, and RELEASING.md gains the matching step.

- `objects(...)` class lists are capped at 32 distinct classes while they are parsed (issues #391, #408). The parser used to deduplicate a long list against the growing set before checking the cap, a quadratic scan on the request path. The cap now applies inside the loop, so the kept set never grows past 32 and each name costs at most a cap-sized scan. Repeats fold and cost nothing, and a list that names a 33rd distinct class is refused with `400 invalid_crop`, the 0.9.10 verdict; the TypeScript explainer, the playground and the `cropObjects` builder count distinct classes the same way.

- A shared-tier purge scans a bounded number of entries inside the request (issue #368). The purge endpoints used to list the whole bucket prefix and read every entry header before answering, so their cost grew with the cache rather than with the matches. They now read at most 128 headers inline and hand the remainder to a background task that finishes the walk and logs its own count; the count in the response reports what the request itself removed.

- A request that has waited out three failed leaders runs the fetch itself (issue #375). Under request coalescing, a waiter whose leaders kept failing without storing a result (a failing origin, a fallback render) answered `503 server_busy` after its third wait, masking the origin's real answer. It now runs the miss path and ends with whatever that produces, as metadata requests already did.

- A smart crop takes the AI gate only when a model runs (issue #379). On a deployment with no face or focal provider configured, a smart crop uses the built-in saliency statistic and runs no inference, but it still took an AI gate permit and could be shed with `503 server_busy` behind real AI work. It now takes the gate only when a face or focal provider participates.

- The face model is probed at load like the other providers (issue #380). Any parseable ONNX file configured as `CRABCROP_FACE_MODEL` used to boot as loaded and fail with a 500 on the first face request; a model that cannot run a probe detection is now a startup error naming the face probe.

- Disk cache I/O runs off the async runtime workers (issue #347). The disk tier's lookups, writes, and purge walks were synchronous filesystem calls on the request path, so a slow disk stalled every request its worker carried. Each disk sequence now runs behind one bounded blocking boundary, in the same order as before, and a started disk-hit chain or purge completes even when the client disconnects. Cache semantics and the on-disk format are unchanged.

- Metadata responses are built from typed structures (issue #346). The JSON body is now serialized from one typed struct per section instead of assembled from format strings, byte-identical for finite values. A non-finite reading (a NaN or infinite container duration, PDF page size, or scene measure) is now omitted from its record, the same shape as a field the source does not report; before, a NaN container duration was written into the response as `NaN`, which is not valid JSON.

- Pinned source clients are reused (issue #369). The pinned fetch path built a fresh HTTP client, TLS configuration included, for every redirect hop. Clients are now cached per validated host and address pair, so a chain that revisits a pair, and later fetches to it, reuse the connection pool; the pair is the whole key, so a client is never used for a pin the policy did not validate.

- CLIP label tokenization changed for multi-word labels (issue #377). The pre-tokenizer now attaches a space to the piece that follows it instead of emitting each space as its own piece, which changes the token ids of every multi-word label and so shifts the zero-shot `tags` and moderation `signals` scores of phrase labels. A follow-up (issue #404) dropped the stray space token the pre-tokenizer still emitted between words, so phrase labels now tokenize as the reference does for ASCII and precomposed accented letters; a few Unicode letter classes still split approximately. Meta responses are never cached, so no stored entry is affected.

- Release and CI coverage (issues #383, #385, #386). CI now runs the whole workspace's tests, checks the root package at its declared MSRV, checks version consistency, and runs the functional suite on pushes to main as well as on pull requests. The version tooling covers the deploy image pins (the Helm values, the kustomize base and AI component, and the platform guides), so `scripts/bump_version.py` moves them and `scripts/check_versions.py` fails on a drifted one. In the release pipeline, registry publishes wait for the GitHub Release job, and a prerelease version pushes only its own image tags, leaving `latest` alone.

- The server and engine sources are split by responsibility (issue #345): request coalescing in `src/server/process.rs`, metadata responses in `src/server/meta.rs`, encoders in `src/engine/encode.rs`, and pipeline state in `src/engine/state.rs`. Behavior is unchanged.

- Width client hints no longer upscale raster sources past their own size, the DPR hint included, and hinted widths stop at 3840 (issue #403). One URL could split into a cache entry per quantization step up to the dimension cap; every hint past 3840 now shares the 3840 entry. This changes the bytes served for existing URLs requested with a hint wider than the source or wider than 3840.

- Removing duplicate cache-group preset names takes linear time (issue #409). The scan ran on the request path before expansion rejected unknown names and de-duplicated against the kept list, so thousands of distinct `preset:` segments cost quadratic CPU per request. A hash set tracks the names already kept; the response is unchanged.

- Animated GIF sources rendered to WebP, whether `format(webp)` names it or `Accept` negotiates it, take the animation gate and the slow lane like animated WebP sources (issue #405). They used to run ungated on the stills lane because the gate predicate predated frames surviving a GIF to WebP conversion. Rendered bytes are unchanged; only scheduling changes.

- The framework integration READMEs no longer recommend running `CRABCROP_ALLOW_UNSAFE=1` without `CRABCROP_ONLY_PRESETS=1` (issue #416); each now describes signed URLs for production, presets-only mode, and unsafe mode as local development only.

- The crate now builds a library target next to the binary (issue #417). The library is internal and carries no API stability promise; it exists so the fuzz harness and the integration tests import the server's own modules instead of copies and stand-ins, and the decode fuzz target runs the server's own decode path and limits. The shipped binaries and the bytes they serve are unchanged.

- `pixelatefaces` redacts faces of any size (issue #401). Each face becomes a mosaic of averaged cells, at most 8 across and never under 2 px; faces under 20 px across used to come back unchanged. This changes the bytes served for existing `pixelatefaces` URLs whose faces are under 20 px.

- npm prereleases publish under the `next` dist-tag (issue #413), so a release candidate such as 0.10.0-rc.1 no longer becomes what `npm install @crabcrop/url` or `npx -y @crabcrop/mcp` installs; only a plain release moves `latest`, the same rule the container images already followed.

### Fixed

- Sharpening no longer frames the image in black (issue #378). The 3x3 convolution behind `sharpen` zeroed its border, so every sharpened output had a 1 px black frame and an image under 3 px on either axis came out entirely black. Border pixels now replicate the nearest edge pixel, the rule `convolve` already documents; interior pixels are unchanged. This changes the bytes served for every existing URL that sharpens, and the upgrade corpus entries `sharpen` and `chain-multi-filter` are re-baselined for this reason.

- `keep_profile` converts to sRGB when the output cannot carry the profile (issue #374). It skipped the conversion and relied on embedding the source profile, but only JPEG and PNG output embed one, so a wide-gamut source rendered to WebP, AVIF, or JPEG XL kept its source-space pixels untagged and displayed with wrong colors. The conversion now resolves the output format the way the pipeline does (explicit format, then the negotiated one, then the source format) and converts for anything but JPEG and PNG, as the filter docs already said. This changes the bytes served for existing `keep_profile` URLs with wide-gamut sources and those output formats.

- Format negotiation keeps animated frames (issue #370). Only a negotiated JPEG XL was guarded, so an `Accept` naming AVIF flattened an animated GIF or WebP to its first frame, and a negotiated WebP flattened a GIF. A negotiated GIF or WebP now carries the animation across and a negotiated AVIF or JPEG XL falls back to the source format; an explicit `format(...)` still converts, first frame only, as documented. This changes the bytes served for existing URLs of animated sources whose clients negotiate.

- An animated smart crop decides its window once (issue #376). The focal analysis re-ran on every frame, so the window jumped as the content moved and the analysis cost was paid per frame. The first frame now decides and later frames of the same size replay its window. This changes the bytes served for existing smart crop URLs of animated sources.

- Detection results are re-measured after a step that moves content (issue #373). The face, detection, and segment memos were keyed on image dimensions, so a dimension-preserving step between two detection consumers (a flip, a same-size rotation, a crop padded back to size) reused boxes measured before it, and a redaction landed where the object no longer was. The memos are now dropped after every sizing, crop, or pad operation and after any filter that does not preserve pixel positions; photometric chains still share one inference. This changes the bytes served for existing URLs with such chains.

- Malformed and hostile inputs no longer crash or escape a budget. A PNG `iTXt` chunk shorter than its fields no longer panics metadata extraction (issue #372). A focal rectangle left outside the frame by an earlier resize is clamped into it instead of panicking (issue #371). An overlay scaled to an extreme aspect is charged against the output pixel budget before it is allocated, and the blend checks the render deadline (issue #358). The CLIP and ViT preprocessors clamp the long side of an extreme-aspect input at 4096 px, and a SAM mask plane over the output pixel budget is refused as a bad model output (issue #359). Embedded `<image>` rasters in an SVG, including those in groups and nested SVG documents, are charged against the decode budget at their own dimensions (issue #360). The PDF probe reads page facts only from the structured part of the `pdfinfo` report, so a forged size in the document title no longer steers the raster clamp (issue #363).

- External tools run under one deadline per request and kernel resource limits (issue #362). The frame extractor and the PDF renderer used to grant each probe and attempt its own full timeout, so one request could run several timeouts back to back while holding a lane permit. Each now computes one deadline for all its invocations, and every child gets an address-space cap (8 GiB) and a CPU-time cap a few seconds past the wall-clock budget.

- Frame extraction reads only the validated input, from a seekable staged copy (issues #361, #411). The decoder program now runs with a protocol whitelist of `fd` and a format whitelist of the accepted containers, reading a regular file staged on its stdin, so a manifest inside the byte stream (DASH, HLS) can no longer point it at files or network targets the source policy never checked, and an MP4 whose index sits at the end of the file, FFmpeg's default layout, reads instead of failing. `CRABCROP_VIDEO_DECODER` needs FFmpeg 6.0 or newer, the first with the fd protocol; an older decoder's refusal names the requirement.

- The private-address check classifies the remaining special-purpose IPv6 ranges (issue #364). NAT64 (`64:ff9b::/96`) and Teredo (`2001::/32`) embeddings are decoded and judged by the IPv4 rules, and local-use NAT64, site-local, benchmarking, and discard-only ranges are refused outright.

- Uploads are stored with their sniffed `Content-Type` (issue #366). Upload objects were written with no content type, so on a store that defaults headerless objects to a binary type (the documented AWS behavior) every upload succeeded with a reference that then failed to load.

- C2PA signing bounds the timestamp authority call (issues #365, #397). Building the signer with a bounded HTTP agent was not enough, because the SDK's signer sent the timestamp request through its own untimed default; the request now goes through the timed agent too (5 seconds to connect, 15 seconds for the whole call), boot asks the authority once with the settled algorithm instead of once per candidate algorithm, and a failure the authority causes names it. The call follows no redirect, so configure the authority's final URL.

- The TypeScript and playground explainers recognize sealed URLs (issue #388). A valid `s1.` token, bare or key-id prefixed, used to fall into the malformed-signature verdicts although the server accepts it; it now explains as kind `sealed`, and marker-shaped imitations report the uniform `403` refusal the server gives.

- Deploy recipes match the server. The Helm values and kustomize manifests defaulted to image 0.1.0, the first release, and now pin the current release (issue #383). The multi-replica overlay no longer mounts one ReadWriteOnce result volume from three replicas, which left all but one pod unschedulable; it disables the disk tier and relies on the shared bucket tier, and the chart sets `fsGroup: 65534` so a mounted volume is writable by the image's user (issue #384). The ECS and Helm recipes and the configuration docs now say AWS credentials come from `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `AWS_SESSION_TOKEN` in the environment; the server consults no credential chain, so a task or pod role alone is not picked up (issue #389).

- A request made while a shared-tier purge is still scanning in the background no longer serves or restores the purged entry (issue #400). The purge tombstone only caught writes that began before the purge, so a lookup that started after it could serve a bucket copy the background walk had not reached yet and promote it into the local tiers, where the walk never looks. Until the scan ends, the receiving server treats any disk or bucket copy the purge covers as a miss and deletes it.

- Arbitrary-angle rotations now size their canvas from the same reduced angle the pixel budget check uses (issue #415), fixing a one-pixel mismatch for some negative fractional angles. The op_chain fuzz target checks each filter's predicted canvas instead of a keep-or-swap rule that was never true.

- Concurrent requests for one URL whose result is not stored now share the first request's response (issue #407). Origin errors, busy sheds, fallback images, and renders with caches turned off used to send every waiter back to the origin after three failed rounds of waiting; waiters now receive the leader's response with their own conditional headers applied, and meta requests share errors the same way. A response rendered before a purge is never shared into a request that arrived after it.

- External tool CPU limits scale with the cores the server may use (issue #406), so multi-threaded FFmpeg runs that fit the wall-clock timeout, such as far seeks in long 4K clips, are no longer killed early.

- Video frame probes read facts only from lines a source cannot forge (issue #402). The duration comes from the report's single indented `Duration:` line, and a second one refuses the report; stream facts are read through a fresh random `-dump_separator` passed on each probe, which text planted in a source's metadata cannot know. Planted lines shaped like a duration or a stream can no longer steer frame selection or meta responses.

- Segmentation decodes are bounded at the encoder's 1024 px scale and read only each box's region (issue #410), so one box no longer costs hundreds of MB to GBs on large images.

- Documentation corrections. The purge guarantee now states that another replica's own disk tier, like its memory tier, is not reached by a purge sent to one replica (issue #351). Nine migration guide rows that described shipped features as missing (`dpr`, progressive JPEG, chroma subsampling, compass gravities, imgproxy focal points) now name the matching options. The test that keeps the documented error codes complete derives the code set from the sources instead of a second hand-kept list.

- SVG embedded rasters are charged wherever the renderer draws them (issue #398). Embedded images inside patterns, masks, clip paths, and filter `feImage` sources now count against the 256 MiB decode budget at their decoded size, once for each time they are drawn, and pattern, mask, and clip-path contents count toward the 100,000-node expansion limit. A 16000x16000 payload that was refused as a plain `<image>` previously decoded at full size when wrapped in one of those constructs.

- PNG metadata inflation is bounded per source (issue #399). Only the first ICC profile, EXIF, and XMP chunk is read, repeats are skipped unread, and every inflate draws on one shared 20 MiB budget, so a small PNG can no longer carry hundreds of chunks that each inflate to its own cap. An XMP packet past its cap is dropped instead of copied in truncated form, and under the default `strip` policy the EXIF, XMP, and Photoshop segments are not inflated at all.

- The container recipes start with a writable disk result tier (issue #396). The images create `/var/cache/crabcrop` owned by `nobody` and the kustomize base sets `fsGroup: 65534`, so the compose production stack and the kustomize full overlay boot with the disk tier live instead of exiting on an unwritable directory; a compose `results` volume that already holds root-owned files needs the one-off chown in deploy/compose/README.md.

- The server builds for macOS again (#442). The external tool kernel limits called `prlimit`, which exists only on Linux, so both darwin legs of the first v0.9.11 release run failed; the limits now apply on Linux and Android only, as docs/media.md describes, and CI checks a macOS build on every push and pull request.

## [0.9.10] - 2026-11-06

### Changed

- Configuration is fingerprinted by content, not by path. Every file-backed resource (AI models, the tokenizer, label files, the OCR dictionary, the overlay font, external encoder and renderer programs, and the C2PA certificate) is identified by a digest of its contents, and the detection and CLIP thresholds are fingerprinted at their effective values, so replacing a file under the same path produces fresh cache entries instead of reusing renders made from the old contents. A rendering version constant joins the fingerprint, so a deliberate output change can start a fresh epoch on purpose. The first start on this version begins a new cache epoch; entries written by earlier versions age out unreachable.

- ETags are derived from the bytes actually served. Each response's ETag is a quoted SHA-256 digest, truncated to 128 bits, of the exact bytes sent, computed when the entry is rendered and stored with it in every cache tier, so a conditional request is answered 304 only when the stored bytes still match. Entries written by the previous on-disk format keep working and gain their ETag when they are read.

- Operational failures carry stable error codes. When a client asks for JSON, a failure now answers in the same error envelope the URL grammar already used, with one of 37 codes covering source loading, decoding and encoding, capacity sheds, timeouts, uploads, purges, and metrics access, so tooling can branch on the code instead of the message text. Statuses and plain-text bodies are unchanged.

- The purge guarantee is stated exactly in the deployment docs. A purge is guaranteed for the process that receives it and for the configured disk and shared stores; it does not invalidate the memory tier of other replicas, which keep serving an entry until they evict it or restart. The deployment and endpoint docs now say so in place of a broader claim, with the operational consequence spelled out: send the purge to each replica, or run a single replica, when a purge must take effect everywhere at once.

### Fixed

- Cache group membership propagates across tiers, and purges close the write race. Membership learned on a hit is written back to the disk and shared tiers, so a group purge still finds the entry after a restart. Every purge records a tombstone before touching any tier, so a render that started before the purge cannot write the purged entry back into a tier when it finishes.

- Non-finite AI scores are rejected instead of serialized. A model that returns a NaN or infinite score now fails its metadata section with a bad-output error, instead of the value being written into a JSON response, where it is not valid JSON.

- Execution permits are held until timed-out work finishes. The processing, slow-lane, video, and animation permits now travel with the job they admit and are released when the job ends, not when the response wait times out, and the metadata helpers account for their gate slots the same way. Caller-visible behavior is unchanged: the same deadlines produce the same timeouts, and the same requests shed under load.

- The workflow copies in docs match the live workflows again, and the local gate keeps them that way. Two of the copies had fallen behind (stale action versions, a missing NASM install step); all four are now byte-identical to the workflows they mirror, `scripts/test_all.sh` opens with a check that fails the gate on any drift, and its Node dependency installs run `npm ci` against the committed lockfiles instead of reusing whatever `node_modules` is present.

- Operation behavior is checked across surfaces against one shared corpus. `spec/` now carries 704 operation vectors plus 99 builder cases, generated by a script the gate re-runs, and read by the Rust, TypeScript, and playground suites. Writing it caught real drift in the JavaScript explainers and the TypeScript builders (source detection on a malformed size segment, border width 0, the blur sigma cap, the `frame:` and `page:` segments, and the canonical `format(jpeg)` spelling); all are fixed to match the server.

- The published benchmarks are refreshed. `benchmark/results/2026-11-06.md` re-measures the comparison set against the v0.9.9 tag with the same harness as the October run (output byte counts identical on all ten operations), and adds two scenario families the old set lacked: cache churn under a rotating workload, where turnover costs at most a few tenths of a millisecond per miss, and memory accounting, which puts the memory tier's cost at its configured budget plus roughly 1.75 KB per resident entry.

## [0.9.9] - 2026-11-05

### Changed

- Source checking is on by default, and the server boots with it. A fresh install configured with only a secret now starts and serves; the earlier startup posture check is gone. Sources that resolve to loopback, private, link-local, or other non-public addresses are refused, unless the host is on the source allowlist: an allowlist match exempts a host from the address check, and connection pinning is scoped to hosts that are not allowlisted. `CRABCROP_ALLOW_ANY_SOURCE` remains available as the deliberate opt-out that turns the address check off entirely. A source the policy refuses is answered with a fixed short message.

- One fetch budget covers the whole redirect chain. Following a redirect used to restart the fetch timeout at every hop, so a chain of slow sources could hold a request open for a multiple of the configured budget. The budget now spans the chain from the first request to the final response, and a chain that outlives it is answered 504.

- AI work shares the request deadline. One deadline is stamped when a request starts and is shared by the AI concurrency gate and the inference behind it: a request whose budget runs out while it waits gives up its place instead of starting work that can no longer finish in time, and metadata annotations that cannot complete inside the budget report themselves unavailable with a `timed_out` reason instead of answering late.

### Fixed

- Cloud storage sources honor the source policy. `s3://` and `gs://` sources are checked against the same bucket allowlist as every other source before anything is fetched; a bucket that is not allowlisted is refused, the same answer an unlisted upload target gets.

- `/explain` bounds its probe. Explaining a URL used to download up to 10 MiB of the source before answering. It now reads a bounded head probe of 256 KiB and answers from that, and a source whose size cannot be learned from the probe is reported as null instead of being fetched to be measured.

- Animated decoding honors the decode byte budget. Animated WebP and GIF sources used to decode outside the configured byte budget, so a many-frame source could allocate several times the limit before anything refused it. Frames now count against the budget as they decode, and a source that would exceed it is refused with 502.

- Long single operations honor the request deadline. The deadline used to be checked between `filters:` segments, so one expensive segment could run well past it and keep working after the client had its answer. Segments now check the deadline as they go, and an operation that reaches it stops instead of running on detached.

- Metadata responses carry file names, not filesystem paths. The model fields in metadata responses (`moderation.model`, `embedding_model`, `aesthetic.head`, `ocr.model`) report the model's file name rather than the absolute path it was loaded from.

- The local gate runs its cargo commands with `--locked` (`build`, `test`, and the fuzz smoke test in `scripts/test_all.sh`), matching the lockfile rule the repository already states for CI.

## [0.9.8] - 2026-11-04

### Added

- Exposure in stops (issue #317). A new `exposure(stops)` filter performs the EV-style linear-light multiply the adjustment family was missing: each channel value is decoded to linear light, multiplied by `2^stops`, and encoded back, with -10 to 10 stops accepted and 0 unchanged. A stop multiplies rather than shifts, so it behaves the same at every brightness, where `brighten` adds a fixed amount and lifts black along with everything else. The scale is stated in the open because it is not a percent: it is the photographic stop, the unit exposure is set in on a camera, so a value from a photo editor carries over as written. Black stays black at every setting and alpha is untouched. The TypeScript SDK gains an `exposure` builder, and the imgix migration guide's exposure row now converts.

- Highlights and shadows (issue #317). A new `highlights_shadows(highlights,shadows)` filter adjusts the two ends of the tonal scale independently, one percent argument per end in the adjustment family's usual -100 to 100, where `contrast` moves both ends together. Each pixel moves by a single offset shared by its three channels, weighted by the pixel's luminance: the shadows weight is (1 - Y)^2 and the highlights weight is Y^2, so the shadows argument moves black most and cannot move white, the highlights argument is the mirror, and the largest shift either end can produce is a quarter of full scale. The TypeScript SDK gains a `highlightsShadows` builder, and the imgix migration guide's shadow and highlight rows now convert.

- Vibrance (issue #317). A new `vibrance(percent)` filter is the gentler sibling of `saturation`: where saturation scales every pixel's distance from its luma by one factor, vibrance weights the change by how unsaturated each pixel already is, with the factor 1 + (percent / 100) x (1 - s) for the pixel's HSV saturation s. Muted colors gain the most, already-vivid colors barely move (a fully saturated pixel does not move at all), and negative percents drain the muted colors first, which is what makes the filter the skin-tone-friendly member of the family. The scale is the adjustment family's percent, -100 to 100 with 0 unchanged. The TypeScript SDK gains a `vibrance` builder, and the imgix migration guide's vibrance row now converts directly.

- Auto-enhance (issue #317). A new `enhance` filter is the mild one-click correction the family was missing: a per-channel auto-levels that maps each channel's 0.5th percentile to 0 and its 99.5th to 255 and stretches what lies between, with a channel whose percentile span is under 16 levels left unmapped. The conservative clipping is the point: a compressed range opens up, a color cast fades, an image that already spans the range is left nearly alone, and nothing is redistributed the way `equalize`, the stronger operation it sits beside, redistributes the whole histogram. The TypeScript SDK gains an `enhance` builder, and the imgix and Gumlet migration guides' enhance rows now convert to it.

- Objects crop (issue #318). A new crop mode, `crop:800x800:objects(dog)`, frames the crop on what a detection model finds instead of a fixed position: the window is the smallest region of the requested aspect that contains the union of every detected object of the named classes (up to 32 names, matched case-insensitively, duplicates folded), scaled by an optional factor about its center (default 1, the tight box; above 1 adds margin, below 1 tightens in), centered on the union and clamped into the frame. The mode needs a detection model (`CRABCROP_DETECT_MODEL`): with none configured it answers 501 rather than silently cropping plain, a class outside the model's vocabulary is a 400, and when the model runs and finds none of the classes the crop falls back to the plain center crop of the same size. Meta responses report the decision under `objects_crop` (the classes, the scale, the path taken, the detections used, the union box), and under `debug:focal` the detections draw amber with the union box as the magenta focal rectangle. The TypeScript SDK, the playground, and the functional suite mirror the mode.

- Encoder option sets (issue #319). `format` now takes per-format encoder options as extra arguments: `format(jpeg,progressive)`, `format(jpeg,subsampling:444)` (444, 422, or 420; 420 remains the standing behavior), `format(png,interlace)` (Adam7 interlacing, and it combines with `palette`), `format(webp,method:6)` (the libwebp compression method, 0 to 6; 4 remains the standing behavior), and `format(webp,sns:50)` (spatial noise shaping strength, 0 to 100). Quality also splits per format, as in `quality(80,jpeg:90,webp:75)`. An option an encoder cannot honour is a 400, never silently ignored: AVIF takes no options (the encoder writes 4:4:4 only and exposes no subsampling control), and a format named with no options renders byte for byte as it always has. The TypeScript SDK gains the matching builders.

### Changed

- The fourth performance wave: less repeated work in the tonal filters, the meta path, and signing, with rendered output byte-identical throughout (issues #332, #333, #334, #335, #336). `enhance` builds its histogram and applies its per-channel lookup tables in row bands (16.91 ms to 10.27 ms at 2400x1600); `exposure` and `gamma` take the frame by value instead of cloning it internally (1.57x and 1.41x at 2400x1600); a meta request that asks for both CLIP tags and a CLIP embedding runs the vision model once instead of twice on the same image (the combined meta cell drops from about 0.91 s to about 0.31 s); and the C2PA signer is built once instead of on every sign (the sign stage drops about 33 percent, a signed response about 12 percent end to end, and the manifest a signature carries is unchanged apart from the fresh identifiers every signature mints).

- Dependency bumps (issues #330, #331). jixel 0.5.0 to 0.5.2 and rustix 1.1.5 to 1.1.6 in the server, and @types/node 26.6.5 to 26.6.6 in the TypeScript SDK, all as Dependabot group updates merged on fully green CI.

### Fixed

- Interlaced PNG encodes are no longer an order of magnitude slower than plain ones (issue #338). The hand-rolled Adam7 assembler behind `format(png,interlace)` compressed its rows with flate2 at level 6 while the plain PNG path uses fdeflate, which left an interlaced encode about 19x slower than the plain encode of the same image (64.8 ms against 3.2 ms at 800x533). The assembler now compresses with fdeflate like the plain path: the interlaced cell speeds up 7.6x to 8.5x, and interlaced files grow 2.5 to 8.9 percent in the IDAT chunk as the price of the faster compressor. Plain PNG output is untouched.

- CI repairs (issue #328). The AI models workflow now provisions the remaining real-model test assets (the moderation, inpainting, and segmentation models, the OCR set, both aesthetic heads, and the focal model), so its gated suite runs 55 passed with zero skips. The yolov8n asset URL moved to the repository's new owner after the upstream SimdYolo repository transferred (Git LFS media URLs do not follow a transfer, and the stale URL had been masked by the asset cache until the cache key changed), and a malformed 61 character checksum pin for the quantized text model, which the verification step had silently skipped on every run, is fixed and now actually verifies.

## [0.9.7] - 2026-11-01

### Added

- Astro and SvelteKit framework integrations (issue #316). Two new packages under `frameworks/` sit on the TypeScript builder beside Next.js, Nuxt, and Hydrogen. The Astro package is an external image service for `astro:assets` (`getURL`, `getHTMLAttributes`, `getSrcSet`, `validateOptions` hooks) configured under `image.service.config` in `astro.config` with base plus preset as the story; because an Astro service runs only on the server, its optional secret never enters client code. Astro's named quality presets (`low`, `mid`, `high`, `max`) map to 25, 50, 80, 100, and `widths` and `densities` become per-variant transforms that keep the requested box's aspect. The SvelteKit package is a loader factory (`createCrabcropLoader`) returning `url` and `srcset` builders for components and load functions, with the same presets-first configuration and the browser secret guard the other loaders carry. - WordPress plugin (issue #314). A first-party plugin under `plugins/wordpress/` rewrites a WordPress site's media URLs (featured images, post content, and srcset) to a self-hosted crabcrop instance, leaving the media library untouched: disabling the plugin returns every URL to its original form. Two modes, presets-first: presets-only (recommended), where WordPress sizes map to preset names and the plugin builds `unsafe` preset URLs, so the instance runs `CRABCROP_ONLY_PRESETS=1` with `CRABCROP_ALLOW_UNSAFE=1` and no secret ever lives in WordPress; and signed, where an optional secret in the plugin settings signs per-size operation strings. Configuration resolves constants (`CRABCROP_WP_*` in wp-config.php), then filters, then the settings screen, so code wins over the admin. Unmapped sizes and any misconfiguration fall back to the original URLs, and an opt-in toggle stops WordPress generating intermediate sizes on upload. The PHP URL builder runs the canonical spec test vectors as its test suite, like every other implementation, and the plugin header joins the release version sites checked by `scripts/check_versions.py`.

- TIFF input (issue #313). TIFF sources now decode, through the image crate's `tiff` decoder (pure Rust, actively maintained, already in the tree as a transitive dependency; it is now named in the feature list so the decoder set does not drift with the image crate's defaults). The upload and probe classification already knew the format; what was missing was proof and a statement. Decoding sits under the same bounds as every other format (the header probe refuses announced dimensions past the limits before any allocation is sized by them), grayscale and RGB, little- and big-endian files all decode, and a multipage TIFF renders its first page. Hostile fixtures pin the edges: announced 20000x20000 dimensions are refused, a cyclic next-IFD chain is refused by the decoder's own cycle detection, and truncated strips and header-only files error instead of panicking. The Gumlet migration guide's source row now splits: TIFF and PDF are supported, RAW and JPEG 2000 remain the conversions.

- PNG palette quantization (issue #313). A new `palette(n)` encoding directive writes PNG output as an indexed (palette) image with at most `n` colors, from 2 to 256: the form other tools call PNG8, at `palette(256)`. Quantization runs through quantizr with full dithering, the same quantizer the GIF encoder uses, but alpha is not binarized the way GIF forces: palette entries keep their own alpha, carried in the file's `tRNS` chunk, so translucency survives. The other formats ignore the directive, the same stance `quality` takes on PNG. Writing the file takes a new direct dependency on the `png` crate (0.18, the same release the image crate wraps, already in the lockfile as a transitive dependency): the image crate's PNG encoder has no indexed color type, and the palette file is written through `png`'s encoder directly. The Cloudflare migration guide's PNG8 row now converts. The TypeScript SDK gains a `palette` builder.

- Focal point crops with zoom (issue #313). A new `focalpoint:<x>x<y>[:<zoom>]` operation names the point the next crop centers on as fractions of the image dimensions, the form imgix documents as `fp-x`/`fp-y`/`fp-z`: the fractions and the zoom carry over as written, with no source dimensions needed. Zoom 1 is the ordinary fill crop positioned on the point; above 1 the window tightens around it, below 1 it loosens toward the fill window and converges on the zoom-1 crop. The point is consumed by `center` and `smart` crops exactly like the `focal:` rectangle (which it supersedes when both are named: the last focal form before the crop wins), the directional alignments and `face` ignore it, and because the point is fractional it can never fall outside the image in effect, so the rectangle's bounds error has no counterpart here. Grammar failures carry the new `invalid_focal_point` error code. The imgix migration guide's focal-point row and worked example now convert directly. The TypeScript SDK gains a `focalPoint` builder.

- Per-side trim (issue #313). `trim` gains a five-argument form, `trim(tolerance,left,top,right,bottom)`: the tolerance pass runs first, exactly as before, and the named pixel amounts then come off the left, top, right, and bottom of what remains, clamped so at least one pixel survives on each axis (the near side takes from the dimension first, the far side from what is left). The one-argument and bare forms are unchanged. The TypeScript SDK gains a `trimSides` builder.

- Gamma correction (issue #313). A new `gamma(g)` filter applies the levels-style midtone gamma: each channel value `v` becomes `255 * (v / 255)^(1 / g)`, with `0 < g <= 10`; 1 is unchanged, values above 1 brighten the midtones, and values below 1 darken them. Black and white are fixed points at every setting and alpha is untouched. The scale is called out because the rest of the adjustment family speaks in percents and offsets: gamma's scale is the exponent itself, the one scale the comparable tools agree on, so a gamma value from another tool carries over as written where `curve` would have needed translated control points. The TypeScript SDK gains a `gamma` builder.

- Self-host production defaults (issue #315). The Helm chart gains `values-production.yaml`, the production shape as a values file: resource requests and limits, the disk result tier on a persistent volume, health probes from the chart defaults, the `/metrics` token wired through an existing Secret (`metricsToken.existingSecret`), and a shared result bucket (`resultBucket`). `values-multireplica.yaml` is now a documented overlay on the production file instead of a standalone shape, with the per-replica memory tier sized where the value is set. Compose gains the matching production profile, `docker-compose.prod.yml`: Caddy with automatic TLS as the only published service, secrets and settings in one owner-only environment file templated by `crabcrop.env.example`, the disk result tier on a named volume, and restart policies; the app port is not published, and the host name reaches Caddy through the compose environment so the signing secret never enters the proxy's environment. Both recipe READMEs lead with the production shape and label the previous default path as evaluation, and both smoke checklists cover a signed request, a cache hit on repeat, a purge, and metrics auth.

A source that cannot resolve inside the configured roots now returns one identical 404 "source not found": a file missing under a root, a path resolving outside every root, and an origin answering 404 all take the new `NotFound` path on both the render route and the explain route. ## [0.8.0] - 2026-10-27

### Added

- Sealed URLs (issue #255). A URL's whole remainder can ride in an opaque token in the signature slot instead of in the clear: `{base}/[<key-id>:]s1.<token>/{friendly-name}`, where the token is base64url(nonce, ciphertext, tag) of AES-256-GCM over the pre-expansion remainder, keyed by a fifth domain-separated subkey (`HMAC_SHA256(secret, "crabcrop/seal-key")`) so there is no second secret and rotation is inherited from the keyring unchanged (a keyed token opens only under its named key; an unkeyed one opens current-then-previous). The server decrypts the remainder into the exact pipeline a verified plain remainder takes, so the sealed and plain forms of one render share one cache entry, one ETag, and one purge target; purge canonicalization unseals a sealed target first, falling back to the presented target. Every sealed failure is the one uniform `403 bad signature` (malformed token, unknown key ID, failed open, oversized token, unknown version marker, and any payload failure after a successful open alike), with successfully opened but expired payloads answering `signature expired` exactly as the plain form; token segments over 4,096 characters are refused before decode, and minting refuses remainders over 2,048 bytes. `/explain` refuses sealed spellings with the same uniform answer and performs no fetch (the server never unseals as a service; operators unseal locally): the CLI gains `seal` and `unseal` verbs, the `crabcrop-url` crate and both SDKs gain matching builders (Python's sealing alone needs the new `crabcrop-url[seal]` extra, the `cryptography` package). Meta for a sealed request carries the render facts and image-derived sections, no operation or source text, and a `sealed: true` marker. The friendly name after the token is cosmetic only: never parsed, validated, or authenticated, and excluded from the cache key. Sealing hides the recipe from page readers, not from intermediaries, and it is not access control; readable signed URLs remain the default and the recommendation. The signing spec gains the full construction, the adversary statement, and canonical sealed test vectors that every implementation reproduces byte for byte.

## [0.7.0] - 2026-10-26

### Added

- Region removal with LaMa (issue #176). A new `remove_region(x,y,w,h)` filter erases a rectangle and inpaints it from the surrounding pixels, mirroring `blur_region`/`pixelate_region` exactly, including the bounds discipline (a rectangle that overflows the image in effect at that point in the chain is a `400`). The model is operator-supplied through `CRABCROP_INPAINT_MODEL`: a LaMa-family ONNX export with two inputs (image plus mask) at a fixed 512×512, preloaded and probed at boot like the other models; the OpenCV zoo export of big-lama follows the contract. Each removal runs the model once on a square crop window around the rectangle and takes only the rectangle's pixels from the result, so everything outside it is bit-identical; unconfigured servers answer `501`, inference runs behind the shared AI gate, and meta responses carry an `inpaint` object listing the erased rectangles. The TypeScript SDK gains a `removeRegion` builder. The docs call out the known failure mode plainly: the fill is fabricated, plausible on smooth surroundings and visibly wrong on structured content (text, faces, repeating patterns).
- Per-object segmentation for the class operations (issue #175). A MobileSAM model pair, operator-supplied through `CRABCROP_SEGMENT_ENCODER_MODEL` and `CRABCROP_SEGMENT_DECODER_MODEL` (both required together, preloaded and probed end to end at boot like the other models), gives the class operations per-object masks: each detection is prompted to the decoder as a box, and the returned silhouette decides what the operation touches. With the pair configured, `blurclass` and `pixelateclass` redact the silhouette instead of the rectangle (the mask's soft edge blends, so the boundary antialiases), and a new `recolorclass(<class>,<hex>)` filter paints the detected objects of a class a solid color, alpha preserved, mask-tight with the pair and box-shaped without it. The image is encoded once per request however many class operations chain; a segmentation failure fails the request like a detection failure does, never a silently rectangular redaction. Meta responses for a request that segmented carry a `segments` object: per object, the label, detection score and box, the mask's tight box, its coverage of the box, and its centroid. The TypeScript SDK gains a `recolorClass` builder and the matching `explain` support.
- OCR text in meta (issue #177). Meta requests that opt in with `ocr=1` gain an `ocr` object: the text read from the processed image as lines in reading order, each `{text, score, x, y, w, h}` with the box in the image's pixels, plus the lines joined as `text_content`, the recognition model's identity, and the language the deployment serves. The pipeline is operator-supplied through `CRABCROP_OCR_DETECT_MODEL`, `CRABCROP_OCR_RECOGNIZE_MODEL`, and `CRABCROP_OCR_DICT` (all three required together, preloaded and probed at boot; the probe checks the dictionary's character count against the recognition model's output width, so a mismatched set fails startup). `CRABCROP_OCR_LANGUAGE` declares the language tag echoed in responses (default `und`). The reference artifacts are the RapidOCR exports of PP-OCRv6 small (Apache-2.0): a DB detector, a CTC recognizer, and an 18,708-character dictionary. The text is an annotation only: an OCR request builds and caches exactly the image entry any other request for the URL would, byte for byte, and an opt-in that cannot be answered reports `{"available": false, "reason": ...}` in the field while the meta request still succeeds.
- Studio scene mode (issue #198). `filters:studio(scene)` is studio's second mode: where `studio(product)` cuts the subject out onto a backdrop, scene mode keeps the photograph's scene and expands to a smart crop on the detected subject plus a per-image light and color correction. The subject is chosen from the mask model's output (the same model `removebg` and product mode run, so no new configuration): the mask's connected components at the subject threshold compete, the largest wins, ties break toward the frame center then reading order, and a winner that is a degenerate speck against the covered region takes the no-subject fallback, which serves the original framing corrected. The reframe crops to the smallest frame-aspect window holding the subject with its `pad` margin (the one argument scene takes, same range and default as product) and resizes back, so the canvas in effect never changes and downstream operations compose unchanged. The correction is histogram-driven and deterministic: a per-channel levels stretch between the 0.5th and 99.5th percentiles (a channel flatter than a 16-value span is left unmapped), then a saturation factor steering the image's mean saturation toward 0.30, capped at 1.35 and never below 1. Meta's `studio` object gains a `mode` field (`product` or `scene`); scene runs report a `scene` object with the winning subject's box, the candidate count, the crop window, the per-channel levels applied, and the saturation factor, so every step of the expansion stays accountable. The product-only arguments (`bg`, `shadow`) are bad arguments under scene, unconfigured servers answer `501` exactly as for product, and inference runs behind the shared AI gate.

The crop decision record behind `debug:focal` now counts the faces detected and the faces the final window keeps whole, so the guarantee is inspectable.
- Studio mode (issue #197). A new intent filter, `filters:studio(product,bg:white,shadow:soft,pad:10)`, names an outcome instead of a mechanism: the subject the segmentation model finds is composited into a listing-ready product shot. The expansion is fixed: mask (the `removebg` model, with the same not-configured `501` when absent), defringe (edge colors decontaminated against the local background so no halo of the old backdrop survives), backdrop and shadow (the resolved backdrop fills the canvas; a contact shadow is synthesized from the subject alpha, blurred, darkened, offset down, strength per the `shadow` argument; `bg:none` keeps transparency and skips the shadow), and pad (the subject scaled and centered to the pad margin, 0 to 40 percent per side, on the canvas in effect at the filter's position). The backdrop resolves as: the named color or `white`; `brand`, the new `CRABCROP_BRAND_COLOR` operator setting (six hex digits), falling back to white when unset; or the brand color by default when the URL names none. A mask that finds no subject serves the original image centered and padded on the backdrop instead of an empty canvas. The composite is a normal image in the chain, valid in every output format; studio takes an AI gate permit (it is part of `RequestDirectives::uses_ai`), counts once against the operation cap, and its output counts against the aggregate output budget. Meta responses gain a `studio` record with the resolved backdrop and its source (`argument`, `brand`, or `default`), the shadow and pad applied, the steps that ran, the fallbacks taken (`bg_brand_unset`, `no_subject`), and the mask confidence when the provider exposes one (the built-in provider's mask field is min-max normalized, not a probability, so it exposes none). `CRABCROP_BRAND_COLOR` joins the configuration fingerprint, so changing it starts a fresh cache epoch. The filter chain splitter is now parenthesis-aware, since the named arguments carry `:` inside the argument list; the frozen ParseError set is unchanged, and bad studio arguments fail as the existing invalid filter error.
- Self-explaining URLs (issue #196). `GET /explain/<signature>/<operations>/<source>` verifies the remainder exactly as the image path does and answers with a report on the URL instead of the image: the signature verdict (with key ID and expiry), the source with its probed facts (media kind, pixel dimensions, encoded size), every operation glossed in plain language (the CLI explain verb's gloss table, shared so a new filter cannot ship undescribed), referenced presets with their expanded operations, a forecast (output dimensions when the chain determines them, the output format, the output pixel count against the aggregate budget), the canonical cache form and group, and links to the image and to the debug focal remainder when the chain contains a crop. Browsers get an HTML page; `Accept: application/json` gets the same report as JSON. The security posture is part of the feature: signature and expiry are verified before any source access, so a bad or expired explain request answers with the image path's own status and body and performs zero source fetches (test-proven with hit counting, the audit R2 pattern); the probe is one bounded loader fetch read from headers only, with no full decode, no detection or AI, and no process, AI, or video gate, so one explain costs at most one image request; the report carries no secrets or derived key material, no configuration values, file paths, or config fingerprint, and no redirect or resolved-address details, with failures mapped to the frozen codes and generic messages; the HTML page escapes every interpolated string, ships no scripts, and is served with `Content-Security-Policy: default-src 'none'` and `nosniff`; and responses are `no-store` and write nothing to any cache tier.

## [0.1.0] - 2026-10-24

The first public release.

### Added

- crabcrop is an on-demand image optimization service written in Rust: the operations are encoded in the URL, the source is fetched and transformed per request, and the result is returned. There are no pre-generated thumbnails and no build step; the URL is the API.

**URL grammar and signing**

- Signed image URLs: every request is `/<signature>/<operations>/<source-url>`, where the signature is the hex HMAC-SHA256 of everything after it, computed over the operations and source exactly as they appear. A bad signature answers `403`; the literal signature `unsafe` skips verification only when the server runs with `CRABCROP_ALLOW_UNSAFE` on.

- Key IDs and secret rotation: a signature segment may carry a key ID (`<key-id>:<tag>`). During a rotation window the server verifies the current secret and the previous one (`CRABCROP_SECRET_PREVIOUS`) side by side, checking a keyed URL against its named key only, so URLs already in the wild keep working until the window closes. An unknown key ID is indistinguishable from a bad signature.

- Expiring URLs: an `exp:<unix-seconds>` segment anywhere among the operations makes a signed URL expire; the HMAC covers it, past the expiry the request answers `403`, and expired URLs never serve from the cache.

- Presets: a preset names an operation string in a server-side file (`CRABCROP_PRESETS_FILE`), and requests reference it as `preset:<name>` anywhere an operation fits. The signature covers the reference, the server expands it deterministically after verification, and cache entries key on the expanded operations. Definitions are validated at startup and cannot contain a source segment, an `exp:`, or another preset; an unknown name answers `400`.

- Presets-only mode: with `CRABCROP_ONLY_PRESETS=1`, free-form operations are rejected with `400`; requests may use preset references, `exp:` metadata, and bare sources only, so public deployments can let browsers and CMSs build URLs from preset names alone.

- Server-wide default operations: `CRABCROP_DEFAULT_OPS` holds an operations string the server prepends to every request after verification, for a house format, quality, or watermark. For the singleton directives the URL wins over the default, and cache entries key on the merged operations, so a bare request and the same request spelled out in full share one entry.

- Domain-separated purge signatures: `POST /purge/<signature>/<path>` and `POST /purge-group/<signature>/<group>` sign under a purge subkey derived from the secret, never the secret itself, so an image signature can never be replayed as a purge signature. The purge target is canonicalized the same way entries are keyed, so any equivalent spelling, a preset reference included, evicts the shared entry.

- Upload endpoint: an optional `PUT /upload/<signature>/<name>` stores originals in an operator-configured destination (a local directory, `CRABCROP_UPLOAD_DIR`, or an S3 bucket, `CRABCROP_UPLOAD_BUCKET`), off by default and absent (404) when not configured. Uploads are signed in their own domain (an upload subkey derived from the secret, like purge signatures) via new `upload_signature` / `uploadSignature` helpers in the Rust crate and the TypeScript and Python SDKs, plus a `crabcrop upload` CLI verb. Bodies are capped by `CRABCROP_UPLOAD_MAX_MB` (default 10, tied to the source fetch cap), must decode as an image the pipeline can serve before they are stored, and never overwrite an existing object unless `CRABCROP_UPLOAD_ALLOW_OVERWRITE` is on (409 otherwise). The response is the exact `file://` or `s3://` source reference to embed in transform URLs. There is no listing and no delete.

**Sources and loading**

- Source kinds: `http(s)://` URLs; `s3://bucket/key`, fetched from AWS S3 or an S3-compatible store (`CRABCROP_S3_ENDPOINT`) and signed with SigV4 when AWS credentials are in the environment (unsigned fetches of public buckets work with none); `gs://bucket/key`, against Google Cloud Storage's S3-compatible XML API, signed with an HMAC key pair when set; and `file:///path`, a local file confined to `CRABCROP_FILE_ROOT`, canonicalized per request so `..` segments and symlink escapes are refused.

- Fetch limits: 10 seconds total per fetch including redirects, a 10 MiB maximum body, and up to 5 redirects for HTTP sources with the source policy re-checked on every hop. If a response carries a `Content-Type` header, it must start with `image/`.

- Source policy: `CRABCROP_ALLOWED_SOURCES` lists host suffixes the loader may fetch from. `CRABCROP_BLOCK_PRIVATE_SOURCES` refuses hosts that are, or resolve to, loopback, private, link-local, or unspecified addresses, and pins the connection to the validated address so the address checked is the address connected. Source URLs with userinfo are always refused. Bucket sources are gated by `CRABCROP_ALLOWED_BUCKETS` instead, and the allowlist is required whenever bucket signing credentials are configured.

- Decode and output bounds: decoding is capped at 16384 px per axis and 256 MiB of decoder allocations, and animated sources at 200 frames and 100 million decoded pixels, so a small file cannot expand into gigabytes. Requested outputs are capped at 16383 px per axis and 100 megapixels.

**Geometry**

- Resize: `<width>x<height>` produces exactly that size; a `0` axis scales proportionally, `orig` takes the source's size on that axis, and a negative dimension flips the image on that axis while resizing.

- Fit inside a box: `fit-in:<width>x<height>` scales the image proportionally so it fits inside the box, with a `0` axis unbounded.

- Orientation-adaptive fit-in: `fit-in:<w>x<h>:adaptive` fits inside the transposed box when the source orientation and the box orientation disagree (portrait source, landscape box, or the reverse), and behaves exactly like plain fit-in when they agree; square sources, square boxes, and boxes without two pixel axes never swap. `pad:` has no adaptive form, since its canvas is explicit. The Thumbor converter now maps `adaptive-fit-in` to it exactly instead of downgrading with a warning.

- Pad to an exact size: `pad:<width>x<height>[:<fill>]` fits the image inside the box, centers it, and fills the rest of the canvas so the output is exactly the requested size. The fill is a 6-digit hex color or `blur`, ambient bars made from a cover-scaled, heavily blurred copy of the image itself; with no fill named, the request's `fill(...)` filter color is used, or black.

- Crop to an aspect ratio: `crop:<width>x<height>[:<align>]` crops to the ratio and resizes to exactly that size. Alignments are `center` (the default), `top`, `bottom`, `left`, `right`, the four corners, `smart` (a window centered on the focal point), and `face` (a window around the largest detected face).

- Corner crop alignments: `crop:` accepts `top-left`, `top-right`, `bottom-left`, and `bottom-right` alongside the single-axis alignments (each corner decomposes per axis: its horizontal component positions a width crop, its vertical component a height crop). The Thumbor converter maps corner alignment pairs to them exactly instead of approximating to the vertical side.

- Caller-supplied focal rectangle for crops: a `focal:<left>x<top>:<right>x<bottom>` segment names the source rectangle the next `crop:` must keep (center and smart crops position on it; directional alignments ignore it). The Thumbor converter now maps the `focal(...)` filter to it.

- Crop a rectangle: `crop-rect:<left>x<top>:<right>x<bottom>` cuts the exact pixel rectangle between the two corners; a rectangle outside the source image fails with `400`.

- Smart-crop debug view: a `debug:focal` segment answers with a diagnostic image instead of the transform result: the canvas the next crop operates on, with the chosen focal point (magenta crosshair), the focal rectangle when one is in play, detected face boxes (amber), and the crop window outline (blue) drawn on it; with no crop it shows the focal analysis of the final image. Debug responses are never cached and are served `Cache-Control: no-store`; animated sources and video output formats are refused with 400. Unknown debug views report their own error code, `invalid_debug`.

**Filters**

- The `filters:` catalog holds 42 names. The 25 pixel filters are: `blur`, `blur_region`, `border`, `brighten`, `contrast`, `convolution`, `curve`, `duotone`, `equalize`, `flip`, `grayscale`, `huerotate`, `invert`, `mask` (circle or ellipse), `monochrome`, `noise`, `pixelate`, `pixelate_region`, `radius`, `rgb`, `rotate`, `saturation`, `sepia`, `sharpen`, and `trim`. Filters chain inside one `filters:` segment in the order written, the segment may repeat in a path, and a repeated directive resolves to the last one.

- Tone curves: a `curve(<channel>,<x>,<y>,...)` filter remaps the `rgb`, `r`, `g`, or `b` channel through 2 to 16 control points (each 0–255, x strictly increasing), linearly interpolated with the ends clamped, for per-channel tone control the additive filters only approximate. Malformed curves report their own error code, `invalid_curve`.

- Convolution: a `convolution(<v1>,...,<vN>,<normalize>)` filter applies a caller-supplied kernel: 9 values (3x3) or 25 (5x5) in row-major order, each a plain decimal from −1024 to 1024, once over the image with edge replication. The trailing flag (0 or 1) scales the kernel by the sum of its entries first; a zero sum applies the kernel as written. Malformed kernels report their own error code, `invalid_convolution`.

- Film grain: a `noise(<amount>)` filter adds monochrome grain: one noise value per pixel applied equally to all three channels (alpha untouched), the value uniform within plus or minus the amount, an integer 0 to 100 percent of full scale. The field is deterministic, seeded from the image content and the amount, so the same URL always produces the same bytes; `noise(0)` is a byte-identical no-op, and animated sources grain per frame from each frame's own content. Malformed amounts report their own error code, `invalid_noise`.

- Encoding directives (6): `format` chooses the output format and overrides negotiation; `quality` sets encoding quality 1 to 100 (default 80) or `auto`; `max_bytes` re-encodes at decreasing quality until the output fits a byte budget; `fill` names the background color used to flatten transparency for JPEG; `no_upscale` caps every resize in the request at the source dimensions; `dpr` scales size and crop targets by the device pixel ratio (1, 1.5, 2, or 3). When crabcrop picks the quality, through `quality(auto)`, a `max_bytes` reduction, or a `Save-Data` step, the response carries an `X-Crabcrop-Quality` header with the value used.

- Verified auto quality: `quality(auto)` picks a quality per image from content analysis, and for JPEG and JPEG XL verifies the pick: the encode is decoded and scored against the processed source with SSIMULACRA2, adjusting quality until the score lands at the target (75 by default, `CRABCROP_SSIM_TARGET`). The achieved score is reported in meta responses as `ssimulacra2`.

- Watermark: `watermark(<url>,<x>,<y>,<alpha>)` fetches another image through the same loader, limits, and source policy as sources and composites it at a position with an opacity; negative coordinates anchor from the right and bottom edges. A watermark that fails to load or decode fails the request (`502`) instead of being skipped.

- Overlay: `overlay(<url>,<x>,<y>,<alpha>,<blend>[,<width>])` generalizes the watermark with the CSS blend modes `normal`, `multiply`, `screen`, and `overlay`, and an optional width as a percentage of the base image's width.

- Text overlay: `text(<text>,<size>,<color>,<anchor>)` draws a label at one of nine grid anchors with a font configured on the server (`CRABCROP_FONT_PATH`); with no font configured, text requests fail with `501`.

- Keep profile: `keep_profile` keeps the source ICC profile instead of converting to sRGB; the profile is embedded in JPEG and PNG outputs.

**Formats and codecs**

- Decode set: JPEG, PNG, WebP, GIF, and JPEG XL sources decode in every build, with EXIF orientation applied before any operation runs, so phone photos come out upright.

- SVG sources: detected by content rather than declared type, sanitized before rendering (script elements, event handlers, and references to external resources are stripped), then rasterized at the requested size and run through the normal pipeline. Output defaults to PNG for SVG sources.

- HEIC/HEIF source decoding: HEIC sources decode in every build through the pure-Rust oxideav stack (`oxideav-heif` + `oxideav-h265`), with no feature flag, configuration, or external tool. The primary image is decoded with grid and overlay compositions resolved, EXIF orientation is applied at decode, embedded ICC profiles feed the usual convert-to-sRGB path, and 10-bit sources flatten to the 8-bit working space. A file whose only colour description lives in the bitstream (no `nclx` colour box) is converted per its SPS VUI, limited range included, matching other decoders instead of the container default. Corrupt HEIC sources keep failing with a specific 502.

- AVIF decoding: AVIF sources decode in builds that include AVIF decoding (the Docker image, the release binaries, and the Homebrew install) via dav1d; animated AVIF sources decode their first frame. Builds without it fail AVIF sources with `502` and an error naming the feature.

- Encode set: JPEG, PNG, WebP, JPEG XL, AVIF, and GIF. WebP encodes lossy at the requested quality and lossless at `quality(100)`; AVIF encoding speed is configurable (`CRABCROP_AVIF_SPEED`), as is the JPEG XL speed tier (`CRABCROP_JXL_SPEED`).

- Animated handling: animated GIFs keep their frames when the output format is GIF; animated WebPs keep their frames, delays, and loop count when the output is WebP or GIF; converting an animated source to a still format uses the first frame. Animated WebP output is always encoded losslessly.

- Video output (gifv): an animated GIF or WebP source can be served as H.264 MP4 or VP9 WebM through an explicit `format(mp4)` / `format(webm)` (never negotiated). The encode runs in an operator-configured external program (`CRABCROP_VIDEO_ENCODER`) over a fixed pipe contract (raw RGBA in on stdin, video out on stdout), bounded by a two-permit gate, a wall-clock timeout (`CRABCROP_VIDEO_TIMEOUT_SECS`, default 30), and an output cap (`CRABCROP_VIDEO_MAX_MB`, default 64). Unconfigured servers answer 501, still sources 400, encoder failures 502; crabcrop ships no codec, so codec licensing stays with the operator.

- Color management: when a source embeds an ICC profile, pixels are converted to sRGB before any operation runs, so sizes, crops, and filters all work in one known space; a source with no profile is assumed to be sRGB. CMYK JPEGs decode through the JPEG decoder's own CMYK conversion.

- Metadata policy: `CRABCROP_METADATA` is `strip` by default (outputs carry no source metadata) or `preserve`, which copies the source's EXIF and XMP segments (and Photoshop/IPTC for JPEG) into JPEG and PNG outputs, with the EXIF orientation rewritten to 1 because the pixels were already rotated at decode.

**Delivery and meta responses**

- Format negotiation: when the URL names no `format(...)`, the request's `Accept` header picks among AVIF, JPEG XL, and WebP by q-value, with ties broken by server preference in that order; a format refused with `q=0` is never picked and wildcards do not count as an offer. An explicit `format(...)` always wins. Animated sources never negotiate to JPEG XL, which would drop their frames. Responses `Vary` on `Accept` and the client hints.

- Client hints: when a URL sizes nothing itself, the server honors the width client hints (`Sec-CH-Width`, `Width`, and the viewport-width variants) and resizes to that width, quantized up to a multiple of `CRABCROP_WIDTH_STEP` (default 100) so nearby viewports share one cache entry. The `DPR` hint applies when the URL carries no `dpr`. A `Save-Data: on` request gets the default quality stepped down from 80 to 70 on the formats that carry a quality.

- Per-request cache lifetime: a `maxage:<seconds>` segment (0 to 31536000) overrides the response `Cache-Control` max-age for that request only. Header-only: it never enters the cache key, so URLs differing only in `maxage` share one stored image; `maxage:0` answers `max-age=0` without `immutable`.

- Meta responses: `Accept: application/json` on any image URL returns metadata about the processed image instead of the bytes: output `width`, `height`, `format`, and `bytes`, plus `source_width` and `source_height`. Meta responses are never cached and are served `Cache-Control: private, no-store`.

- Placeholders: with the `placeholders` media-type parameter, meta adds `dominant_color` (the average color as `#rrggbb`), `placeholder` (a 16 px-wide blurred JPEG preview as a base64 data URI), `palette` (the five most prominent colors), and `thumbhash` (a ThumbHash string client libraries decode into an aspect-correct blurred preview).

- Fallback image: with `CRABCROP_FALLBACK_IMAGE` set, a source that cannot be fetched or decoded degrades to the fallback, which runs through the same operations and is served with `200` and `X-Crabcrop-Fallback: 1`. Fallback responses are never cached. Signature and parse failures never fall back, and neither does a source-policy refusal.

- Cache headers: every image response reports `Cache-Status` (RFC 9211: memory hit, disk hit, or origin fetch) and, for each preset its URL referenced, a `Cache-Group` header (RFC 9875) that makes preset-wide invalidation one `/purge-group` call.

- Errors: error bodies are plain text with a short message; when JSON is requested, a grammar failure instead answers with the v2 JSON envelope carrying one of the parser's frozen, named error codes. Statuses distinguish malformed requests (`400`), bad signatures, expired URLs, and source-policy refusals (`403`), failed encodes and inference (`500`), valid URLs the server is not configured for (`501`), and source fetch or decode failures (`502`, `504` on fetch timeout).

**Caching**

- Memory tier: an in-memory LRU result cache bounded by bytes, 256 MB by default (`CRABCROP_CACHE_MAX_MB`); `0` disables it.

- Disk tier: with `CRABCROP_RESULT_STORAGE_DIR` set, a disk-backed second tier (512 MB default budget) sits under memory: results survive restarts, and disk hits are promoted into memory.

- Shared S3 tier: with `CRABCROP_RESULT_BUCKET` set, a third tier in one S3 bucket (or S3-compatible endpoint), namespaced by `CRABCROP_RESULT_PREFIX`, is shared by every replica. A shared hit promotes into disk and memory, new results are written through to the bucket in the background, and the tier is best-effort: a bucket error reads as a miss, never a failed request.

- Canonical keys: entries are keyed by the request's canonical form, so equivalent spellings of the same request share one entry. Negotiated responses are cached per negotiated format class, per effective DPR value, per quantized width-hint class, and per Save-Data class. Only `200` responses are cached; errors never are.

- Purge fan-out: `/purge` invalidates every stored variant of one result, and `/purge-group` clears a preset's whole recorded output set, across all cache tiers.

**AI features**

- Model posture: AI features run ONNX models in-process, from files the operator supplies; crabcrop never downloads a model, at startup or at request time. Models load at boot, before the server reports ready, and a configured model that cannot load is a startup error with a one-line diagnostic. With no model configured, the feature is off and requests that use it fail cleanly with `501`; there is no silent fallback. Inference runs behind a server-wide gate of 2 concurrent inferences. The runtime library comes from `CRABCROP_ORT_DYLIB` or the system library search path.

- Background removal: `removebg` runs a U²-Net-family model and keeps the subject over transparency; the output format must carry alpha (`png`, `webp`, `jxl`, or `avif`).

- Upscale: `upscale(2)` and `upscale(4)` run a super-resolution model (Real-ESRGAN-family exports follow the contract), with output capped at 4096 px per dimension. The model's native factor is probed at load with a test image and a non-integer factor is rejected at boot; a native 2x model composes two runs to land an exact `upscale(4)`, and source transparency is carried across even though the model only sees RGB.

- Face detection: a YuNet model (`CRABCROP_FACE_MODEL`) powers face-aware smart crops (centered on the area-weighted center of the faces found), `crop:...:face` around the largest face with `facepad` padding, and the `blurfaces` and `pixelatefaces` redaction filters. Chained face operations in one request share a single detection. No model, no faces, or a detection failure falls back to the detail-based focal point for crops; the redaction filters instead require the model (`501` without one) and a detection failure fails the request with `500` rather than serve an unredacted image.

- Class redaction and detections: a YOLOv8-family model (`CRABCROP_DETECT_MODEL`) powers `blurclass(<class>)` and `pixelateclass(<class>)`, which redact every detected object of a class (repeat the filter for more classes; matching is case-insensitive), and meta `detections` with the `detections=1` parameter. The class vocabulary comes from the model's own `names` metadata, or from `CRABCROP_DETECT_LABELS` for exports without it; `CRABCROP_DETECT_THRESHOLD` sets the score floor. A model whose output is not the YOLOv8 layout is rejected at boot.

- CLIP tags and alt text: a CLIP model pair with its tokenizer and a label file adds `tags` (zero-shot labels scored against the processed image, above `CRABCROP_CLIP_THRESHOLD`) and `alt_text` composed from the best labels to meta responses. Labels are embedded once at boot, so a meta request runs only the image encoder; a tagging failure omits the fields instead of failing the response.

- Declared detectors: `CRABCROP_DETECTORS_FILE` points at a JSON file wiring operator ONNX models to two built-in contracts, with no operator code loaded: `boxes` detectors (YOLOv8-family, class names from the declaration or the model's metadata) join class redaction (resolved built-in first, then declared in file order) and meta detections (aggregated, each box attributed with a `detector` field), and `focal` heatmap models feed smart crops between the face model and saliency (first declaration wins, later ones stand by). Every declaration is validated, loaded, and probed at boot; a broken one is a startup error naming it.

- AI image variant: `Dockerfile.ai` builds on the base image with a second layer adding the pinned ONNX Runtime, the U2Netp model, and the YuNet model, each hash-checked at image build time, and enables the features by setting the variables above.

**Client libraries and loaders**

- Signing spec and test vectors: the URL grammar and signing scheme are specified in `spec/url-signing.md`, an unversioned grammar where a URL minted today keeps its meaning, with a canonical set of test vectors in `spec/test-vectors.json` that every implementation runs as its test suite.

- Rust crate: `crabcrop-url` provides `sign`, `verify`, `build_url`, and `build_srcset`, plus the `purge_signature`, `purge_group_signature`, and `upload_signature` helpers. The server verifies with this same crate, so client and server cannot drift.

- TypeScript SDK: `@crabcrop/url` provides `sign`, `verifyUrlSignature`, `buildURL`, and `buildSrcSet`, the purge and upload signature helpers, and typed operation builders (`ops`, `filter`) that validate against the grammar and compile to the same canonical strings. Standard library only.

- Python SDK: `crabcrop_url` provides `sign`, `verify`, `build_url`, and `build_srcset`, plus the purge, purge-group, and upload signature helpers. Standard library only.

- Framework loaders: a Next.js custom loader for `next/image`, a Nuxt provider for `@nuxt/image`, and a Hydrogen loader for external (non-Shopify-CDN) images. All three recommend presets as the configuration, so client-side URL building never needs the secret.

- Playground: a static page (no build step, no server state) for building, signing, previewing, and debugging URLs in the browser; the secret never leaves the page, signatures verify locally, and pasted URLs are explained segment by segment with errors highlighted.

- MCP server: a first-party MCP server (stdio, no dependencies) exposing `sign_url`, `explain_url`, `fetch_meta`, and `purge_result` over the same SDK and HTTP surface, for coding agents.

**Operations and deployment**

- Operator CLI: the `crabcrop` binary doubles as its own CLI. The verbs are `sign` (sign a URL, validated against the server grammar first), `explain` (explain a URL segment by segment, verifying its signature), `meta` (fetch the meta JSON, with `--placeholders` and `--detections`), `purge`, `purge-group`, `upload` (store an original and print the source reference for transform URLs), and `convert-thumbor` (convert a Thumbor URL, re-signed, with losses reported on stderr).

- Health and metrics: `GET /health` answers `200` with the body `ok`, and `GET /metrics` serves Prometheus metrics: request counts by status class, request, load, and process durations, cache hit and miss counters, loader and engine error counters, and byte totals. Both are unauthenticated and served `Cache-Control: no-store`, so they belong on the internal network behind the proxy.

- Structured request logs: every image request writes one structured JSON log line to stdout with the operation summary, status, per-stage timings, and cache result, never the full source URL.

- Overload behavior: the processing, AI, and video gates shed overload with `503` rather than queue without bound.

- Upload metrics: accepted and rejected uploads count into `crabcrop_uploads_total` on the metrics endpoint.

- Container images: a multi-stage `Dockerfile` whose runtime image carries only the binary and CA certificates, and the `Dockerfile.ai` variant on top of it. Releases publish both to GHCR as `ghcr.io/dayvson/crabcrop` and `ghcr.io/dayvson/crabcrop-ai`, tagged with the version and `latest`.

- Kubernetes and cloud recipes: `deploy/helm` is a Helm chart and `deploy/kustomize` the same workload in kustomize form (base, components for presets, the disk tier, and the AI variant, plus single and multi-replica overlays); `deploy/compose` runs the workload under Docker Compose. Per-cloud recipes for ECS Fargate, Cloud Run, and Container Apps each carry their secret wiring and a smoke checklist.

- Release artifacts: cargo-dist builds the server for Linux and macOS on both architectures, plus a shell installer and SHA-256 checksums, attached to the GitHub Release; the Homebrew formula is generated from the release checksums.

- Migration guides: `docs/` carries guides for moving existing URL templates from Thumbor, from imgproxy, and from Cloudinary.

### Fixed

- Boot with an AI model configured but no loadable ONNX Runtime (no `CRABCROP_ORT_DYLIB` and no system runtime) died on a panic inside the `ort` crate instead of failing startup. The runtime is now loaded explicitly from the configured path, or from the path ort itself would search (`ORT_DYLIB_PATH`, then the system library name), and a load failure is the usual `cannot load ...` boot diagnostic with exit code 1.
