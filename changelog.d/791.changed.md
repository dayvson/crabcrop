A JPEG XL encode now runs on as many threads as the stills lane's load leaves it (issue #791). jixel spread every encode over one thread for each core of the host, starting them inside the encode, so with the stills lane full every encode's threads traded the cores with the other encodes'. A render now takes the stills lane's permits, one for each core, divided among the still renders in flight when it starts, rounded down and at least one: alone, its encode uses every core, as before; with the lane full, one thread. jixel writes the same file at any thread count, so the bytes are as they were. Measured end to end on a 4-core VM, with the benchmark's JPEG XL request (800 pixels wide, quality 80) over its 25 sources, four requests in flight and the result cache off, the server answers about 11% more requests a second (71.1 against 65.7, the median of 48 rounds in five holds), and the median latency falls from 59 to 53 ms; one request at a time takes the time it took (34.6 against 34.4 ms). Responses are unchanged.
