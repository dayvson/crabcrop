A 16-bit source bound for an output this pipeline writes only at 8 bits is now narrowed to 8 bits before it is resampled (issue #814). fast_image_resize's 16-bit kernels use i32 weights and i64 sums and cost four to five times the 8-bit ones, so a 16-bit PNG or TIFF resized for an 8-bit output (JPEG, WebP, GIF, AVIF or JPEG XL) was resampled at a depth the response could not carry; it is now narrowed first, keeping its channels, so resampling a 2400x1600 RGB16 source to 800x533 drops from about 21 ms to 9 ms. The narrowing is the same high-byte conversion the encoder ran on the resampled frame, so the only change is that the resample rounds at 8 bits instead of 16: a resized sample moves by at most one level on a smooth gradient — within one level of the previous render everywhere, so it carries no contour the previous render lacked — and about a tenth of a dithered frame moves, at 59 to 61 dB PSNR against the 16-bit path. A PNG output, which this pipeline writes at 16 bits, keeps its depth and is left untouched; a JPEG source, already 8-bit, and a float source are untouched. The pixels of an affected render differ, which the cache epoch issue #793 opens covers. No upgrade-corpus source is 16-bit, so no corpus entry is re-baselined for this change.
