Filters that split a frame into row bands run them on one pool of threads the server starts at boot, a thread for each core it may use, instead of reading the core count at every call and starting a thread per band for every pass (issue #739). They are the blurs, `rotate` at an angle that is not a quarter turn, `grayscale`, `brighten`, `contrast`, `gamma`, `exposure`, `highlights_shadows`, `huerotate`, `saturation`, `vibrance`, `rgb`, `curve`, `sepia`, `duotone`, `monochrome`, `enhance`, `flip`, and the half and three-quarter turns. A pass still splits into at most four bands, and the request waits while the pool runs them, so the band work of every request in flight keeps at most one thread per core busy, where each request used to start up to four threads of its own per pass. Responses are unchanged: each banded filter writes the same bytes on one thread and on pools of 2, 3 and 8. Measured on a 4-core VM with a release build on a 4000x3000 frame, over 12 alternating rounds, a chain of six of these filters takes 59.2 ms where it took 66.3 ms, and four threads rendering it twice each take 444 ms where they took 565 ms. One blur or rotate alone takes the time it took, within the rounds' spread; `enhance` alone measured 10.9 ms where it took 9.3 ms. The server runs one `filter-N` thread per core from boot, none on a one-core host.
