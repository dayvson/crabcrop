A JPEG source whose first operation is a resize to a third of its size or less now decodes at reduced scale (issue #653). libjpeg-turbo, which already writes JPEG output, decodes such a file at a half, a quarter or an eighth of its size, the smallest of the three that still leaves at least one and a half times the resize's target on both axes, and the resize finishes from that frame, so the full-size pixels are never made. Five of the six requests of the documented benchmark mix start this way. Measured on a 4-core VM with both paths in one build, the decode and resize of the benchmark's 2400x1600 source to 800 wide takes 6.6 ms where it took 12.2 ms, and to 400 wide 4.4 ms where it took 11.5 ms; a 2400x1600 photograph to 800 wide takes 11.8 ms where it took 20.5 ms, and saved as progressive 30.9 ms where it took 46.1 ms; a phone photo (EXIF orientation 6, a Display P3 profile) to 533 wide takes 17.6 ms where it took 38.4 ms, since the rotation and the color conversion run on the smaller frame too. The response is the same size, and so is the source size it reports: `orig`, a proportional side, `no_upscale`, a width hint and a DPR factor all go by the size the file declares, turned upright by its EXIF orientation. The pixels change slightly, which the cache epoch above covers: over the 1,124 renders of the JPEGs in benchmark/fixtures and tests/functional/corpus that take the path, the image handed to the encoder is 55.0 dB PSNR from the one a full-size decode gives at the median and 46.8 dB at the 5th percentile, and at worst 37.9 dB, for a 16 px wide thumbnail of a 200 px wide photo. Every other request decodes as before: any other first operation, `fit-in` included; a JPEG stored as grayscale, CMYK, YCCK or RGB, or arithmetic-coded, lossless or 12-bit; a resize to more than a third of the image (a phone photo shown 1600x2400 and resized to 800 wide is halved, so it decodes at full size); and a file libjpeg-turbo refuses or warns about, which the full-size decode then answers as it always did. The declared size is held to the decode limits before the scaled decode starts, and libjpeg-turbo to zune-jpeg's limit of 100 scans in a progressive file, so a file past either is refused as before. One difference is possible, for a file whose compressed data is damaged: libjpeg-turbo reads a few progressive files with a damaged scan that zune-jpeg refuses (9 of 42,000 mutated files in a differential run), so such a file can render at a size that takes the path where it failed, and a damaged file both decoders read can show its damage differently. The upgrade corpus entries that resize the 1000x667 `crab-photo.jpg` to 300 wide first (`resize-exact`, `format-webp`, `format-avif`, `format-jxl`, `format-png`, `format-gif`, `quality-override`, `grayscale`, `preset-thumb`, `source-root-short` and `sealed-url`) are re-baselined for this reason.
