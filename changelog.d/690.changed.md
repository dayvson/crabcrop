A fresh server no longer hands the buffers of a large render back to the kernel after every request (issue #690). On Linux with glibc, how much freed memory the allocator keeps follows the largest block the process has freed so far. A server that had only decoded sources of a few megapixels kept too little for a render that comes close to its source's size, such as a resize from 2400x1600 to 1600 wide or a rotation at full size: it gave the frame buffers back at the end of each request and took about 6,000 page faults to get them again at the next. The first source of 6 megapixels or more ended that for the life of the process. The server now reaches that state at boot, by freeing one untouched block of just under 32 MiB. On a server that has only seen 2400x1600 sources, a resize to 1600 wide went from 38.8 to 28.7 ms and a full-size `rotate(90)` from 38.9 to 28.4 ms end to end, with the same bytes; requests whose buffers the allocator already kept, an 800-wide resize among them, do not change. What it costs is memory the process keeps: up to 64 MiB of freed buffers in each of the allocator's heaps stay resident between requests, so resident memory rises to its peak and stays near it (in the test, 174 MiB where it had fallen back to 27 MiB), as it already did on any server that had decoded one large source. docs/deployment.md says how to size a memory limit for that. Nothing changes on musl or macOS.
