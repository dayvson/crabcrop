A `crop-rect` followed by a resize no longer premultiplies a copy of the whole frame of an image with transparency (issue #807). The resize backend premultiplied a borrowed RGBA8 frame into a second buffer the size of the frame, whatever the crop box, though its kernel reads only the box and the filter's reach around it. The fused crop and resize own the frame, so that part is now premultiplied where it sits, and the frame is resampled through the same crop box with the same coefficients: a 600x400 window of a 2400x1600 cut-out resized to 300x200 went from 2.6 to 0.67 ms (from 8.0 ms with glibc's default malloc thresholds). The resize a trim survey runs on a frame it borrows also skips the premultiply when it would change no pixel, as for an opaque frame or a GIF frame: 9.5 to 8.1 ms for a 2400x1600 GIF frame resized to 800x533. Responses are unchanged.
