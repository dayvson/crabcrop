`CRABCROP_AVIF_TILES` sets how many tiles an AVIF is written in: 1, 2, 4, 8 or 16, four by default (issue #688). Since issue #671 every host writes four, so that replicas with different core counts render the same file, and a host with more than four cores runs several AVIF encodes side by side but gives one encode no more than four of them. More tiles make one encode faster on a host with a core for each, and the file larger. The encodes run in pools of as many threads as the count, one pool for every that many cores, rounded up; a count above the host's core count is allowed, and makes one pool. Any other value stops the boot with an error that names the variable. The count is part of what a URL renders to, so it is in the configuration fingerprint: replicas set to different counts keep separate cache entries instead of serving each other's files, and print different fingerprints at boot. Four adds nothing to the fingerprint, so the default renders the bytes it rendered and keeps its cache epoch. Measured on a 4-core VM with one encode alone at the default speed and quality, an 800x533 photograph takes 99 ms in one tile, 56 ms in two, 39 ms in four, 42 ms in eight and 39 ms in sixteen, at 24,183, 24,315, 24,435, 24,732 and 25,113 bytes, and a 2400x1600 photograph 811, 473, 306, 305 and 285 ms, at 145,862 to 148,081 bytes. On four cores, eight and sixteen tiles cannot use more cores than four do, and with four encodes at once no count was faster than four. A host with eight or more cores was not available, so what eight and sixteen tiles save there was not measured; docs/configuration.md has the figures.
