Sources with a color profile convert to sRGB in place (issue #649). The
conversion allocated a second buffer the size of the frame, transformed into
it, copied the result back and freed it. On a decode that already holds
several frame-sized buffers this made the allocator hand memory back to the
system and fault it in again on the next step: about 7,400 page faults per
decode of a 2400x1600 phone photo. An 8-bit frame whose profile is a matrix
with one tone curve and no lookup table, which is what cameras, phones and
editors embed (Display P3, Adobe RGB, the common sRGB profiles), is now
rewritten where it lies. A 2400x1600 JPEG with EXIF orientation 6 and a
Display P3 profile decodes, turns and converts in 33.4 ms where it took
45.4 ms (1.36x), and in 27.7 ms (1.64x) with the rotation of issue #648;
its page faults drop from about 7,400 a decode to about 1,900. Every other
case keeps the transform between two buffers, now without the copy back,
because there the color library's in-place transform is a different
computation and would change pixels: a profile with a lookup table beside
its matrix, a profile with a tone curve per channel, 16-bit frames, and a
CPU that is neither x86-64 with SSE4.1 nor AArch64. Responses are
unchanged.
