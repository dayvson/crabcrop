Each AVIF render the stills lane runs at once now encodes in a thread pool of its own (issue #790). The server kept one pool for every `CRABCROP_AVIF_TILES` cores, so a 4-core host at the default four tiles had one pool of four threads, and every AVIF encode in flight ran in it: a thread that waited for a tile of its own encode ran a tile of another one meanwhile, and an encode ended only once those tiles had ended too. The server now keeps one pool for every core, as many as the stills lane has permits, each of as many threads as the tile count, so the tile count, and with it every file, is as it was. Measured end to end on a 4-core VM, with the benchmark's AVIF request (800 pixels wide, quality 80) over its 25 sources, four requests in flight and the result cache off, the server answers as many requests a second as before (29.5 against 29.1), and the 90th percentile of their latency falls from 194 to 161 ms and the 99th from 344 to 200 ms; one request at a time takes the time it took, to within 2%. A host keeps more encoder threads, idle while no AVIF encodes: at the default four tiles, four for every core where it kept one. The pool count is `CRABCROP_AVIF_POOLS` (default 8): one per core for that isolation, capped so a many-core host does not run `cores * tiles` threads (a 64-core host at four tiles would otherwise hold 256), and floored at `cores / tiles` so the cores stay busy. The cap changes no response bytes and is not in the configuration fingerprint. Responses are unchanged.
