JPEG output is now written by libjpeg-turbo 3.1.0, compiled into the binary, instead of the pure-Rust `jpeg-encoder` crate (issue #668). The encode step of a JPEG response takes about a third of the time it did: measured on a 4-core VM, an 800x533 JPEG at the default quality went from 2.6 ms to 0.8 ms and a 2400x1600 one from 31 ms to 12 ms, and `quality(auto)`, which encodes, decodes and scores several candidates, went from 180 ms to 117 ms at 800x533. Every JPEG's bytes change, which the cache epoch above covers. What a URL asks for means what it did: `quality(...)` is libjpeg's 1 to 100 scale and writes the same quantization tables as before, chroma is 4:2:0 unless `format(jpeg,subsampling:444)` or `subsampling:422` names another layout, output is baseline unless `format(jpeg,progressive)` asks for progressive, and `fill(...)`, `max_bytes(...)`, `quality(auto)`, `Save-Data`, metadata under `CRABCROP_METADATA=preserve`, `keep_profile` and C2PA signing work as before. The picture changes where chroma is subsampled, which is every JPEG that does not name `subsampling:444`: the old encoder kept one chroma sample of every two or four and dropped the rest, and libjpeg-turbo averages them, so color edges no longer alias. Over the 44 JPEG sources of tests/functional/corpus and benchmark/fixtures, fitted into 800x800 at the default quality, the files total 1.0% fewer bytes and their mean SSIMULACRA2 score rises from 77.6 to 80.6. `quality(auto)` therefore reaches its target at a lower quality and serves smaller files: on a photograph at 800x533 it settled on quality 76 where it had settled on 86, for 32% fewer bytes at the same score. `X-Crabcrop-Quality` reports the lower value. `format(jpeg,progressive)` is the one case that gets slower: libjpeg builds the Huffman tables of a progressive file from the image, so those encodes take about 1.4 to 1.6 times as long as before, and the files come out about 18% smaller. The bytes do not depend on the host: libjpeg-turbo's AVX2, SSE2, Neon and plain C code write the same file, so replicas on different CPUs and architectures render one URL to the same JPEG. Building from source now needs cmake and make besides a C compiler, and nasm on x86_64 as before; `cargo install crabcrop` is such a build. The Docker images and the release binaries link the library statically, so nothing changes at run time. The repo `Dockerfile` installs cmake in its build stage, and docs/deployment.md lists the new build tools. The upgrade corpus entries that render JPEG (`resize-exact`, `crop-plain`, `crop-gravity`, `quality-override`, `grayscale`, `metadata-strip`, `metadata-preserve`, `preset-card`, `source-root-short` and `sealed-url`) are re-baselined for this reason: each is 0.2% to 1.6% smaller.
