With `AWS_ACCESS_KEY_ID` unset, the server now signs its AWS requests (bucket sources, uploads and the shared result tier) with the credentials of the container credentials endpoint that ECS serves a task role on and EKS Pod Identity a pod's role on, `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` or `AWS_CONTAINER_CREDENTIALS_FULL_URI`, with the token in `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` or `AWS_CONTAINER_AUTHORIZATION_TOKEN` (issue #709). It fetches them before its first AWS request and prints an `aws credentials:` line, then fetches the next set 15 minutes before they expire, so temporary credentials no longer run out until a restart. A fetch that fails is logged and retried every 30 seconds, and requests sign with the last set meanwhile. A full URI over plain `http` to anything but the ECS or EKS agent or a loopback address is a startup error. The static keys, when set, work exactly as before, and the endpoint is never asked. Container credentials do not trip the `CRABCROP_ALLOWED_BUCKETS` boot check, so an ECS or EKS deployment that boots today keeps booting, and an empty allowlist still refuses every bucket fetch. A deployment on ECS or EKS with a role and no keys, whose bucket requests used to go unsigned, now signs them with the role; set the endpoint variable to an empty value to keep it unsigned. Web identity tokens (IRSA) and EC2 instance metadata are still not consulted.
