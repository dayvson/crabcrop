A damaged progressive JPEG gets one answer at every size (issue #713). Since issue #653, a JPEG whose first operation is a resize to a third of its size or less decodes at reduced scale through libjpeg-turbo, and every other request decodes it at full size through zune-jpeg. zune-jpeg refuses a progressive file whose first scan its reader is done with before it comes to the marker that ends the scan, where libjpeg-turbo reads the scan without a warning, so a file damaged that way rendered at small sizes and failed with `502` at large ones: 9 of 42,000 mutated files in the differential run behind issue #653, all progressive, all this way. The scaled decode now reads a progressive file's first scan as zune-jpeg's reader does, a table lookup per block and no pixels, and leaves a file zune-jpeg would refuse to the full-size path, so such a file fails at every size. A progressive file with restart intervals, which that reading does not follow, now decodes at full size as well. Every other JPEG decodes at the scale and to the pixels it did.
