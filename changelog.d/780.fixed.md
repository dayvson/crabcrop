A stored result no longer answers a request the source policy refuses (issue #780). The policy is part of no cache key, so once it was narrowed, a render that memory, the disk tier or the shared bucket held of a source it now refused kept serving, from the bucket on every replica, until it was purged or evicted: with a host dropped from `CRABCROP_ALLOWED_SOURCES`, a URL already rendered from it answered `200` from the disk tier while any other size of the same source answered `403`. Before the disk tier or the bucket answers, the server now runs the checks that the request's source and watermark URLs decide on their own: the host allowlist, an IP address against the non-public address refusal, the bucket allowlist and naming rules, and whether file sources are configured. A request they refuse reads neither and gets the answer a render gets, `403 source_forbidden`; the stored render stays, and serves again if the policy admits its source again. Memory holds only renders the server stored, or read from those tiers, once its own policy admitted their sources, so a memory hit runs no check and costs what it did. The checks look no host name up, so no hit costs a lookup, and a result stored from a host name that now resolves to a non-public address keeps serving until it is purged. See docs/configuration.md.
