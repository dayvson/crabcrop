AVIF output no longer depends on the host's core count (issue #671). The AVIF encoder writes as many tiles as it has threads, and it took its thread count from the host: the same 800x533 render came out at 11,165, 11,267, 11,433 or 11,738 bytes on hosts with one, two, four or eight cores. Replicas with different core counts therefore rendered one URL to different files. Each had its own ETag, so a client that revalidated against another replica got a full `200`, and a shared tier kept the file of whichever replica rendered first. Every host now writes four tiles, or fewer when the frame is too small for four, and runs an encode on four threads. A four-core host writes the files it always wrote, in the same time. On any other host the bytes of an AVIF change once, which the cache epoch above covers. With one or two cores the files come out 0.3% to 2.4% larger and the encode takes the same time to within the 5% the measurement resolves. With more than four cores the files come out smaller (0.5% to 2.6% with eight cores), and one encode no longer uses more than four of the cores, so an AVIF encode that has such a machine to itself takes longer than it did: on four cores, four tiles encode an 800x533 frame about 2.8 times as fast as one tile and about 1.7 times as fast as two, and what eight tiles added on eight cores is given up. The encodes run in pools of four threads, one pool for every four cores, so a larger host still runs that many AVIF encodes side by side at full speed. Other formats are not touched.
