With an expiry, the URL builders refuse operations and sources that would decide the URL in its place (issue #782). The builders put `exp:<expires>/` in front of the operations and the source, and the server keeps the last `exp:` of a URL, so operations or a source that carried their own `exp:`, such as page content that the SvelteKit, Hydrogen and Astro integrations pass along with their `expires`, set the URL's lifetime whatever expiry was given, and a source that began with an operation added it to the signed URL. Given an expiry, the builders now refuse operations that carry an `exp:` or `maxage:` segment, and a source whose first segment the server reads as an operation, `exp:`, `maxage:` or `preset:`: in the `crabcrop-url` crate with `BuildError::ExpiryOverride` (`SealError::ExpiryOverride` for `SealedUrl`), and in the TypeScript and Python SDKs with `ExpiryOverrideError` (a `ValueError` in Python). The playground and the WordPress plugin's `CrabcropUrl::build` (with `InvalidArgumentException`) refuse the same inputs with the same messages, and so do the MCP server's `sign_url` and the framework integrations, through the TypeScript SDK; the plugin's own URLs carry no expiry, so they are unchanged. Without an expiry those inputs build as before, and every other build signs the same URL as before. `spec/test-vectors.json` gains refusal and build vectors for the rule, which every implementation runs. The server is unchanged.
