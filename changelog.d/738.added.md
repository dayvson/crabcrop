Four variables set the address-space caps the external tools and the SVG worker
run under on Linux, which were fixed (issue #738):
`CRABCROP_VIDEO_ENCODER_ADDRESS_SPACE_MAX_MB` (default 8192),
`CRABCROP_VIDEO_DECODER_ADDRESS_SPACE_MAX_MB` (3072),
`CRABCROP_PDF_RENDERER_ADDRESS_SPACE_MAX_MB` (3072) and
`CRABCROP_SVG_WORKER_ADDRESS_SPACE_MAX_MB` (4096, AVIF decodes included), in
megabytes. Unset, each tool runs under the cap it had. A value under what the
tool needs to start (1024 for the video tools, 256 for the PDF tools, 512 for
the worker) stops the boot with an error that names the variable, and so does
one over 65536. The PDF renderer's boot check renders under its cap, so a cap
the renderer cannot work in stops the boot too, and its JPEG 2000 check holds
a document's images to the cap set. A cap other than its default joins the
configuration fingerprint, since the PDF renderer leaves out of a page an
image it cannot decode under its cap. The boot lines of the video encoder, the
video decoder and the PDF renderer name the cap in force. An address-space cap
is not a limit on resident memory, and none follows a container's memory
limit; docs/configuration.md has what each least was measured at.
