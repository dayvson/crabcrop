The server now sets jemalloc as its global allocator (issue #801). On the warm-cache hit path, where many connections serve cached renders at once, jemalloc's per-thread caches remove the contention on glibc's malloc arenas: 64-connection memory hits measured about 1.7x the throughput of the glibc default at roughly two-thirds of the server CPU per hit, with 304 revalidations and HEAD requests faster too, while renders (CPU-bound) and single-connection latency are unchanged and every response is byte-identical. Peak resident memory stays at the glibc level and the settled footprint is lower, because jemalloc returns the freed frame buffers that the glibc arenas held on to between requests. jemalloc builds from vendored C sources and links statically, so the runtime image and the release binaries gain no shared-library dependency. It is the default `jemalloc` cargo feature, so a `--no-default-features` build falls back to the system allocator (documented under Allocator in docs/configuration.md); the issue #690 boot step that nudged glibc's own malloc thresholds (`raise_malloc_thresholds`) is inert under jemalloc and applies only to that fallback build.
