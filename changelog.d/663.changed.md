AVIF output of an opaque 8-bit image spends less time before its tiles
start (issue #663). The AVIF encoder (ravif) converted every pixel to YCbCr
in `f32` with fused multiply-adds and `round` before rav1e saw it. The
release binaries are built for the baseline x86-64 target, which has
neither instruction, so that was nine libm calls for each pixel, on one
thread: 5.7 ms of an 800x533 encode. For an RGB8 image the engine now adds
the three values up from fixed-point tables, recomputes by ravif's own
steps the one color in 200 whose sum lands near a rounding boundary, and
hands the planes to the ravif call the image crate ends in, with the same
settings. An 800x533 AVIF at the default speed went from 32.8 to 29.4 ms
and a 2400x1600 one from 298 to 243 ms. The files are the same, byte for
byte: the conversion agrees with ravif's for every 8-bit color, and the
tile and thread counts, the `max_bytes` ladder and the encode budget are
as they were. Images with alpha, gray, 16-bit and float images take the
image crate's encoder as before. ravif is now named in Cargo.toml, at the
version already in the tree, so no crate is added. Responses are
unchanged.
