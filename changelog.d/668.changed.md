This release starts a new cache epoch. Changes below alter the bytes served for URLs that already exist (every JPEG output, which libjpeg-turbo now writes, issue #668; AVIF output on hosts that do not have four cores, issue #671; renders of an 8-bit source whose embedded profile is sRGB in effect, which now keeps the pixels it decodes to, issue #662; JPEG XL output of a few small images with an alpha channel, and every JPEG XL output where `CRABCROP_JXL_SPEED` names `fast` or a slower tier, which the updated encoder writes, issue #670; and `quality(auto)` JPEG and JPEG XL output too large for its pick to be verified, which is now encoded once at the first pick), so the rendering version in the configuration fingerprint moves from 6 to 7 and the default configuration no longer prints the 0.12.0 fingerprint, `30565010cfa46711`. The first start on this version begins a new epoch: entries written by 0.12.0 and earlier stay in the disk and shared tiers under their old keys, unreachable, until they age out, and during a rolling upgrade old and new replicas read and write separate entries instead of serving each other's renders. Expect a cold cache after the upgrade: every cached render is made again once, in every format, not only the JPEGs. The epoch does not reach a CDN in front of the server: a JPEG response a CDN stored before the upgrade stays until it expires or is purged. It shows the same picture as the new bytes, encoded by the previous encoder. A stored render of a source tagged sRGB, in any format, shows the same picture too, made from pixels a level of rounding away.
