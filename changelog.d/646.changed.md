Animated WebP sources decode about twice as fast (issue #646). Each frame's
bitstream now goes through libwebp, as a still WebP's does, instead of the
image crate's own VP8 and lossless decoders. The frames are still composited
by that crate's rules, ported here, so every frame comes out the same bytes
as before, with the same size and delay. On a 12-frame 800x533 animation the
decode, every frame composited, takes 46 ms where it took 98 ms (2.1x), on one
thread as before; that is the decode stage of a request, so a render that
also encodes the animation gains less in proportion. The frame cap, the
decoded-pixel and allocation budgets and the processing deadline, checked
before each frame, apply as they did. The image crate's decoder still opens
the file, so the container checks and their errors are the same, and it
decodes from the start any file the new path does not recognize and any
whose frame libwebp refuses. One difference is possible, for a file whose
compressed frame data is damaged: libwebp now reads the damage, as it
already did in a still WebP, so such a frame can render where it failed,
or render other pixels. A damaged container, a truncated file and a frame
whose data is another size than its header says behave as before.
Responses are otherwise unchanged. Three things the image crate does that
libwebp's own animation decoder does not are kept on purpose, because
changing them changes pixels: it takes one off every non-zero color channel
of an opaque pixel in a blended frame that has alpha, it fills the canvas
and a disposed frame with the ANIM background color, and it fills three
bytes at a time before a frame without alpha. Whether to render as libwebp
does is left to issue #339.
