A shared-tier purge no longer holds the bucket's whole listing (issue #709). Each purge request listed every page of the prefix before it answered, and a background scan waiting for one of its two turns kept every name the request had not read, about 113 bytes a name: against a test bucket of 31,000 entries, 41 per-URL purges in a row took 0.70 seconds each and raised the server's memory from 48 to 233 MB, and at 100,000 entries 10 purges took 1.46 seconds each and raised it from 47 to 206 MB. The request now lists one page, of the 128 names it scans itself, and the scan lists on from there, 1,000 names a page, judging each page before it lists the next; a scan waiting for its turn keeps only the continuation token. The same 41 purges took 0.44 seconds each at 31,000 entries and 0.45 at 100,000, and memory rose from 48 to 60 MB in both. A bucket that answers a page with the continuation token it was asked for, which used to keep a scan listing that page forever, now ends the scan unfinished, so its purge stays in force. A per-URL purge still scans every entry: entries are named by a digest of their whole key, so a URL's older spellings share no name prefix a listing could narrow to, and naming them so would orphan every entry already in a bucket.
