The release workflow publishes the `crabcrop` crate to crates.io, after
`crabcrop-url` and under the same approval, so `cargo install --locked
crabcrop` installs every release (issue #711). The crate was published by
hand, when at all: 0.13.0 went up 71 minutes after `crabcrop-url`, and 0.9.6
never did. Both crates are packaged and built from their packages before the
release approval, in a job with no secrets, so a crate that does not build
stops the release before anything is public, and the job that holds the
crates.io token builds nothing. The workflow also publishes the MCP server's
registry entry, `io.github.crabcrop/crabcrop` (`sdks/mcp/server.json`), once
`@crabcrop/mcp` is on npm, with the registry's own publisher pinned by
version and SHA-256, so the MCP registry lists each release instead of only
0.1.0, which was submitted by hand. A prerelease is not listed there, as npm
keeps one off `latest`. Both publishing jobs skip a version their registry
already has, so re-running a failed job finishes the release instead of
failing on what an earlier attempt published.
