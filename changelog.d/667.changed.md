Animated GIF output prepares its frames on up to four threads (issue #667).
Every frame gets a palette of its own and is compressed by itself, so the
frames are quantized and compressed side by side and then written in frame
order: the file is the bytes one thread writes. On a 4-core VM the encode of
a 12-frame 480x320 animation went from 123 to 40 ms (3.05x), and four such
encodes at once take as long as before (0.98x). The thread count is the
host's cores, four at most, never more than the frames, and one for a single
frame or an animation under 64x64 pixels. An animated GIF render still takes
one permit of the stills lane, so one render can now keep up to four cores
busy for the length of its encode, and a still render on the same host waits
for them: an 800 px JPEG resize took 22.7 ms beside one animated GIF render
where it took 17.7 ms beside the single-thread encoder, and 49.6 against
33.4 ms beside four. The processing deadline is still checked before every
frame, on whichever thread takes it. A frame that fails, a deadline that
passes or a panic stops the other threads before their next frame, and the
request gets the failure of the earliest frame, as before. The prepared
frames, the file's own image data, are held until the last one is ready.
