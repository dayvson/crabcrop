A keep-alive request no longer wakes its own connection (issue #639). The
watch that keeps the header and idle timeouts of issue #607 woke its
connection's task when a request head started and again when the handler
ended. That task is the one doing both, so every request was polled a
second time, re-armed its timer twice, and, on a server with idle workers,
woke a parked worker to take the connection over: about two `futex` calls
for each request, and three of four workers kept busy by one connection.
The watch now sleeps to a time no later than any deadline the connection
can come to have, and is woken only when a request head starts and stalls.
Sequential hits on one keep-alive connection over loopback went from 55.8
to 50.8 µs for each request with 14 KB bodies and from 367 to 341 µs with
1 MB bodies, and the server's CPU time for each small one from 68.4 to
44.0 µs. With 64 connections, where no worker is idle, nothing measurable
changes. The bounds are as they were: the header timeout from a
connection's start and from the first byte of each later request head, the
idle timeout with its HTTP/2 rules, neither while a handler works, and the
connection cap. While a handler runs, the watch now looks once every header
or idle timeout, whichever is shorter, and finds nothing due. Responses are
unchanged.
