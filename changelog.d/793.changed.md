This release starts a new cache epoch: baseline JPEG output now carries optimized Huffman tables built from the image (issue #793). The encoder calls `set_optimize` for baseline output, so libjpeg-turbo computes the tables from the image's own symbol counts, where it wrote libjpeg's standard tables before, and the entropy-coded data is shorter for the same decoded pixels: about 9% fewer bytes on the 25 benchmark sources at 800 wide, quality 80, for one more pass over the coefficients at encode (about 1.4 ms more at 800x533). The decoded pixels do not change. Progressive output already builds optimized tables for every file, so the flag is set for baseline only. The pure-Rust encoder before libjpeg-turbo built its own optimized tables that zune-jpeg, the decoder this engine reads JPEG with, decoded to the wrong colours on tiny and flat images (issue #38), which is why baseline carried the standard tables; libjpeg's optimized tables are read back correctly, baseline and progressive, at every subsampling, which the tests decode and check. The rendering version in the configuration fingerprint moves from 8 to 9 for this change and the others in this release (issues #815, #785, #814), so the first start on this version begins a new epoch: entries written by 0.15.0 and earlier stay in the disk and shared tiers under their old keys, unreachable, until they age out, and during a rolling upgrade old and new replicas read and write separate entries. Expect a cold cache after the upgrade. The upgrade-corpus entries that render JPEG (`resize-exact`, `crop-plain`, `crop-gravity`, `quality-override`, `grayscale`, `metadata-strip`, `metadata-preserve`, `preset-card`, `source-root-short` and `sealed-url`) are re-baselined for this reason, each 1.5% to 3.5% smaller.
