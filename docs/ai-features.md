# AI features

The features that run ONNX models in-process: `removebg` (background removal), `studio` (product-shot composites and scene reframing on the same mask model, see [Studio mode](filters.md#studio-mode)), `upscale` (super-resolution), `remove_region` (region removal by inpainting), face detection for crops and redaction, and per-object segmentation that tightens the class filters to silhouettes. The models are files you supply, deployment artifacts, like the `Dockerfile.ai` image variant in this repo. crabcrop never downloads a model, at startup or at request time. The annotation models (CLIP tags, moderation, embeddings, the aesthetic score, OCR, and detection boxes) answer through meta responses, so they also need meta mode on (`CRABCROP_META_MODE=1`, off by default; see [Meta responses](meta.md#meta-responses)).

How configuration works:

- Point `CRABCROP_REMOVEBG_MODEL` at a U²-Net-family model file (320×320 input; the U2Netp export is a good fit) and/or `CRABCROP_UPSCALE_MODEL` at a super-resolution model. The upscale contract is dynamic-size RGB in (values 0..1), the same image out at an integer factor; Real-ESRGAN-family ONNX exports follow it, and Swin-family exports work too: their window grid needs input dimensions on a multiple of 8, so the provider pads with replicated edge pixels and crops the result back to the exact size.
- Point `CRABCROP_INPAINT_MODEL` at a LaMa-family inpainting model to enable the `remove_region(x,y,w,h)` filter: the rectangle is erased and inpainted from the surrounding pixels, with the same bounds rule as `blur_region` (a rectangle that overflows the image is a `400`). The contract is a two-input session (image plus mask) at a fixed 512×512: image in as RGB values 0..1, mask 0..1 with 1 the hole, output back in 0..255. The OpenCV zoo export of big-lama (`inpainting_lama_2025jan`, Apache-2.0, from the OpenCV zoo model collection) follows it. Each removal runs the model once on a square crop window around the rectangle (twice the rectangle's larger axis, so the model sees context as well as hole) resized to 512×512, and only the rectangle's pixels are taken from the result: everything outside it comes back bit-identical. The source's alpha and sample depth are kept, inside the rectangle too: the model fills color, not transparency, so transparent pixels stay transparent, and a 16-bit or float source is fed to the model and written back at its own precision. Meta responses for a removal carry an `inpaint` object listing the erased rectangles. Know the limits before you rely on it: the model *fabricates* what goes in the hole, plausibly on smooth or textured surroundings and visibly wrong on structured content (text, faces, repeating patterns, straight edges that should continue). A removal takes seconds of inference (behind the shared AI gate), and the result cache absorbs repeat requests for the same URL, so a given removal is normally paid for once.
- Point `CRABCROP_FACE_MODEL` at a YuNet model to make `crop:...:smart` center on detected faces (the area-weighted center of the faces found). Face detection only ever improves a smart crop: no model, no faces, or a detection failure all fall back to the detail-based focal point, and a smart crop without the model behaves exactly as before. The same model powers the explicit face operations: `crop:...:face` (crop around the largest face; falls back to the smart window when detection fails or finds nothing), and the `blurfaces` / `pixelatefaces` redaction filters. Those require the model, without one they return `501`, and a detection failure fails a redaction request rather than serve an unredacted image: `502` (`inference_bad_output`) when the model's output is unusable, `500` (`inference_failed`) for any other failure. Chained face operations in one request share a single detection.
- Point the `CRABCROP_CLIP_*` set at a CLIP model pair (image and text ONNX exports with the projection head), its `tokenizer.json`, and a label file with one label per line, and meta responses gain `tags` and `alt_text`: zero-shot labels scored against the processed image, plus a short alt text composed from the best three. Labels are embedded once at boot, so a meta request runs only the image encoder, behind the same inference gate; a tagging failure omits the fields instead of failing the response. Labels are embedded exactly as written, so phrase-style labels (`aerial view of a beach`) work as well as single words.
- Point `CRABCROP_MODERATION_MODEL` at a ViT classifier export (the Falconsai nsfw_image_detection shape: a 224x224 image input, one logits row out) and meta requests that opt in with `moderation=1` gain a `moderation` object with the model's per-category verdict scores, softmaxed into probabilities and reported with the model identity. `CRABCROP_MODERATION_LABELS` names the model's outputs, one per line in output order, with the count checked against the model at boot; without it, a two-output model answers as `normal` and `nsfw`, and any other output count is a startup error. With no model set, the labels file instead names zero-shot prompt labels scored by the CLIP pair (which must then be configured), reported as review `signals`, never as verdicts. Verdicts are annotations only: nothing is blocked, blurred, or altered at serve time, and a failed or unconfigured moderation reports itself unavailable in the field instead of failing the meta request. Treat the scores as a model's opinion, not ground truth: the reference model's training data is undisclosed and no subgroup evaluation is published, and NSFW classifiers as a class over-flag swimwear, medical imagery, and art. Validate on your own corpus before acting on a score.
- Point `CRABCROP_AESTHETIC_HEAD` at a LAION-style linear aesthetic head (the PyTorch save, e.g. `sa_0_4_vit_b_32_linear.pth` for a ViT-B/32 encoder) and meta responses gain an `aesthetic` object: the head's score of the CLIP embedding, reported with the head's and the encoder's identities. The head must match the configured encoder: a head built for a 768-dimensional encoder (ViT-L/14) scored against a 512-dimensional embedding (ViT-B/32) reports a null score with `reason: "dimension_mismatch"` and the expected and actual dimensions, per request, never as a startup failure; a malformed head file is a startup error, like every other configured artifact. The same embedding is available on its own: meta requests that opt in with `embeddings=1` gain `embedding` (base64-packed float16 little-endian) plus `embedding_model`, `embedding_dim`, `embedding_encoding`, and `embedding_normalized`, ready to store in a vector index or a DAM. The score is descriptive only, never a gate: it encodes the taste of the LAION aesthetics data, itself scored against human ratings of mostly conventional photography, so it favors sharp, brightly lit, conventionally composed photos and underrates plenty of good work. Do not rank, filter, or price by it without validating on your own corpus.
- Point `CRABCROP_OCR_DETECT_MODEL` and `CRABCROP_OCR_RECOGNIZE_MODEL` at a PP-OCR-family model pair (a DB text detector and a CTC recognizer) and `CRABCROP_OCR_DICT` at the recognition model's character dictionary, and meta requests that opt in with `ocr=1` gain an `ocr` object: the lines the pipeline reads in the processed image, in reading order, each with its text, a confidence score, and its box, plus the lines joined as one `text_content`. The reference artifacts are the RapidOCR exports of PP-OCRv6 small (Apache-2.0, from the RapidOCR model collection): a detection model of about 10 MB and a recognition model of about 21 MB, with the `ppocrv6_dict.txt` dictionary (18,708 characters: Chinese, Japanese, Latin scripts and more in one model). The dictionary is operator configuration, not a download at runtime: it must be the table the recognition model was trained with, and the boot probe checks its character count against the model's output width, so a mismatched set fails startup rather than returning misaligned text. The recognition model fixes the script and the language coverage; `CRABCROP_OCR_LANGUAGE` declares which language the deployment serves (a BCP-47 tag, default `und`) and meta echoes it beside the model identity, so a stored response stays interpretable after the model is swapped. Text is an annotation only: it never alters, blocks, or re-renders the image, and an OCR request renders exactly the image any other request for the URL would (as a meta request, it is never cached). One pipeline guard worth knowing: a detection box spanning essentially the whole frame is dropped, because on smooth backgrounds (a gradient, a clear sky) the detector fires as one giant component, and a real text line always keeps margins on some side. Expect photo-text variance: clean rendered or printed text reads essentially perfectly, while small, stylized, or low-contrast text in photos will misread characters (a 0 read as an O is the classic), merge or split lines, and miss text the detector never fires on. Scores are the model's own confidences, useful for triage, not proof. Validate on your own corpus before building on the text.
- Point `CRABCROP_DETECT_MODEL` at a YOLOv8-family detection export and more surfaces unlock. The class filters `blurclass(<class>)` and `pixelateclass(<class>)` redact every detected object of a class, and `recolorclass(<class>,<hex>)` paints every detected object of a class a solid color, alpha preserved (repeat the filter for more classes; matching is case-insensitive). They inherit the face redaction rules: no model is a `501`, an unknown class is a `400`, and a detection failure is a `502` or a `500` as for faces, never an unredacted response. The `crop:...:objects(<class>...)` mode crops to the union of the named classes' detections; it shares the `501` for no model and the `400` for an unknown class, but a detection failure there degrades to the plain center crop, like the face crop's fallback, because no redaction promise is at stake. And meta requests with `detections=1` return the detection boxes for debugging. The class vocabulary comes from the model's own `names` metadata, which Ultralytics exports carry; for exports without it, `CRABCROP_DETECT_LABELS` supplies one class per line in index order. A model whose output is not the YOLOv8 layout is rejected at boot. The YOLOv8 output layout is an interface, not a recommendation of any particular weights: the detect model is an operator-supplied deployment artifact, and crabcrop bundles, defaults to, and recommends none. Ultralytics' own YOLO weights are licensed under AGPL-3.0, a source-disclosure trigger for a network service, so an operator who deploys them runs them under their own agreement.
- Point `CRABCROP_SEGMENT_ENCODER_MODEL` and `CRABCROP_SEGMENT_DECODER_MODEL` at a MobileSAM export pair (an image encoder and a box-prompt decoder; MobileSAM is Apache-2.0, and the pair is about 28 MB plus 17 MB as ONNX) and the class filters change shape: `blurclass` and `pixelateclass` redact each object's silhouette instead of its rectangle, and `recolorclass` paints the silhouette. Segmentation is box-prompted: each detection is prompted to the decoder as its own box, and the mask that comes back decides, pixel by pixel, what the operation touches; the mask's soft edge blends, so silhouettes antialias instead of stair-stepping. The image is encoded once per request however many class operations chain, and each box costs one small decode: the decoder answers at most at the encoder's 1024 px scale, whatever the image size, and only the box's own region is resampled up to the box, so beyond the box's own mask a decode's memory does not grow with the source. Meta responses for a request that segmented carry a `segments` object: per object, the label and detection score and box, the mask's tight box (the silhouette's own extent, often well inside the detection), its coverage (the share of the box the silhouette fills), and its centroid. The object is omitted if any score or coverage in it has no JSON representation (a non-finite value), rather than printing a malformed body. Without the pair, the class filters keep their rectangle behavior exactly; with the pair, a segmentation failure fails the request like a detection failure does, never a silently rectangular redaction. Class operations still need a detection model: the segmenter refines boxes, it does not find them.
- Models load at boot, before the server reports ready. A configured model that cannot be loaded, missing file, wrong shape, is a startup error with a one-line diagnostic, not a surprise for the first request. The upscale model's native factor is probed at load with a 16×16 test image; a model that does not enlarge by an integer factor is rejected at boot. The mask model is probed at load too: an export whose output is not the 320x320 mask field is rejected at boot rather than failing on the first `removebg` request. The inpainting model is probed the same way (a small removal must succeed, and a model without the image-plus-mask input pair is rejected) rather than failing on the first `remove_region` request. The segmentation pair is probed the same way again (an encode and a box-prompted decode must succeed end to end, a decoder without the prompt inputs is rejected, and so is one that answers a larger mask than the size it is asked for) rather than failing on the first class operation. The OCR set is probed the same way too (detection on a blank image and recognition on a blank crop must both succeed, and the dictionary's character count must match the recognition model's output width) rather than failing on the first `ocr=1` request.
- With no model configured, the filter is off: requests that use it fail cleanly with `501` (`removebg is not configured on this server`, `upscale is not configured on this server`, `remove_region is not configured on this server`). There is no silent fallback, `upscale` never degrades into a plain resize.
- Inference runs behind a server-wide gate of 2 concurrent inferences, so a burst of AI requests cannot starve the normal transform pipeline.

### Declared detectors

Beyond the one built-in detection model, `CRABCROP_DETECTORS_FILE` points at a JSON file that declares more of your own models against two built-in contracts. The file is configuration only: crabcrop never loads or runs operator code; it wires each named model to a contract it already implements.

```json
[
  {
    "name": "crates",
    "model": "/models/crates.onnx",
    "kind": "boxes",
    "labels": "/models/crates.txt",
    "threshold": 0.4
  },
  {
    "name": "logos",
    "model": "/models/logos.onnx",
    "kind": "boxes",
    "labels": ["nike", "adidas", "puma"]
  },
  {
    "name": "saliency",
    "model": "/models/saliency.onnx",
    "kind": "focal"
  }
]
```

- `name` (required) identifies the declaration: letters, digits, `_`, `-`; duplicate names are a startup error, and `builtin` is reserved for the built-in detector (it is the source name meta detections report for its boxes). `model` (required) is the ONNX file path. `kind` (required) is `"boxes"` or `"focal"`; anything else is a startup error naming the declaration.
- The file is bounded configuration: at most 1 MiB, at most 16 declarations (each one loads a model at boot and joins every meta request's detections, so the count bounds both costs). A declaration's vocabulary is capped at 4096 classes, inline labels of at most 256 characters each.
- **`boxes`** is a YOLOv8-family detector, decoded by the same post-processing as `CRABCROP_DETECT_MODEL`. Its class vocabulary comes from the declaration's `labels`, a path to a labels file (one class per line, in index order) or an inline array of class names, when given, and from the model's `names` metadata otherwise; declared labels win when both exist. `threshold` (0 to 1) sets its score floor, default 0.5 like the built-in detector. A `boxes` declaration with no vocabulary from either source is a startup error, as is a model whose output the decoder cannot read.
- **`focal`** is a heatmap model: one fixed `[1, C, H, W]` input (C is 1 for luma, 3 for RGB) of at most 409,600 pixels (the detection contract's 640x640 frame; the input tensor and the boot probe are allocated from the declared shape, so a larger declared frame is a startup error) and exactly one output shaped `[H, W]`, `[1, H, W]`, or `[1, 1, H, W]`. The focal point is the heatmap's hottest cell, ties going to the first in row-major order. `labels` and `threshold` do not apply to this kind.
- Class redaction resolves a class across providers in a fixed order: the built-in detector first, then declared `boxes` detectors in file order; the first provider whose vocabulary knows the class runs it. Chained class filters still share one run per provider per request.
- Meta detections aggregate every configured detector: the built-in's boxes first, then each declared detector's in file order, and every box carries a `detector` field naming its source (`"builtin"`, or the declaration's name). One detector's failure omits only its own boxes.
- Smart crops consult focal sources in this order: a caller focal form (`focalpoint:` or `focal:`, the last one named in the chain), then the face model, then the first declared `focal` provider, then the built-in saliency estimate. Only the first `focal` declaration is consulted; later ones are loaded and probed at boot, then stand by.
- Every declaration is loaded and probed at boot, like every other model: a missing model file, an unreadable or malformed declarations file, an unknown kind, or an output that does not fit the contract is a startup error naming the declaration.
- `upscale(4)` on a server whose model is natively 2× composes two model runs and lands the exact requested size; when the native factor does not divide the request, a final high-quality resize trims the difference. Source transparency is carried across an upscale even though the model only sees RGB, and the result keeps the source's sample depth: a 16-bit or float source is fed to the model and written back at its own precision, so a 16-bit RGBA PNG served as PNG stays 16-bit RGBA.
- The ONNX Runtime library itself comes from `CRABCROP_ORT_DYLIB`, or from the standard `ORT_DYLIB_PATH` variable, or the system library search path when neither is set.

The `Dockerfile.ai` variant in this repo shows the intended shape: the base image stays free of AI payload, and a second layer adds the pinned ONNX Runtime 1.31.0, the U2Netp model, and the YuNet model, each hash-checked at image build time, and enables the features by setting the variables above. Layer your own super-resolution model the same way and set `CRABCROP_UPSCALE_MODEL` to enable `upscale`.
