# Deployment

Every recipe below runs the same server, configured entirely through the environment (see [Configuration](configuration.md#configuration)). Release images are published to GHCR as `ghcr.io/dayvson/crabcrop`, tagged with the release version; the AI variant is `ghcr.io/dayvson/crabcrop-ai`. Pin the exact image by digest where your platform supports it, as the Helm chart does with `image.digest`. Every recipe needs `CRABCROP_SECRET`, the HMAC secret that signs and verifies every URL, at least 16 bytes: the server refuses to start without it.

The repo ships a multi-stage `Dockerfile` (the runtime image carries the binary, CA certificates, and the dav1d library for AVIF decoding):

```bash
docker build -t crabcrop:latest .
docker run -p 3000:3000 -e CRABCROP_SECRET="$(openssl rand -hex 32)" -e CRABCROP_BLOCK_PRIVATE_SOURCES=1 crabcrop:latest
```

For the AI features, build `Dockerfile.ai` on top of that image; see [AI features](ai-features.md#ai-features).

### Put a CDN in front

Any platform above can sit behind a CDN. Each recipe in this family configures one CDN in front of an already-running crabcrop origin, and each folder carries the config artifact its steps refer to.

| CDN | Recipe | Config artifact | Group purge bridged to | Built-in optimizer to disable |
| --- | --- | --- | --- | --- |
| Cloudflare | [Cloudflare](../deploy/cloudflare/README.md) | `cache-tag-worker.js` (the tag bridge Worker) | Cache tags (the `Cache-Tag` header) | Polish |
| CloudFront | [CloudFront](../deploy/cloudfront/README.md) | `normalize-accept.js` (a CloudFront Function) | Cache tags (the `Cache-Group` header, via `CacheTagConfig`) | None: CloudFront has no built-in image transformation for custom origins |
| Fastly | [Fastly](../deploy/fastly/README.md) | `fastly-snippets.vcl` | Surrogate keys (the `Surrogate-Key` header) | Image Optimizer |
| BunnyCDN | [BunnyCDN](../deploy/bunnycdn/README.md) | `cache-tag-middleware.ts` (a middleware script) | Cache tags (the `CDN-Tag` header) | Bunny Optimizer |
| Akamai | [Akamai](../deploy/akamai/README.md) | `property-rules.json` (a rule fragment) | Cache tags (the `Edge-Cache-Tag` header) | Image and Video Manager |

Two things hold behind every CDN. Error responses carry `Cache-Control: no-store`, so an edge that follows the origin's headers never serves one request's failure to the URL's other viewers; the CloudFront recipe also turns off CloudFront's own short caching of errors, which does not wait for headers. And the client hint headers (`DPR`, `Sec-CH-DPR`, the width hints and `Save-Data`) can change a URL's bytes. Cloudflare, CloudFront, BunnyCDN and Akamai, as their recipes set them up, do not key on those headers, so those recipes set `CRABCROP_CLIENT_HINTS=0` on the origin and every request for a URL gets the one response the edge stores. Fastly keys on `Vary` and can leave hints on. With hints on, a response a hint applies to is `private`, which an edge that follows the origin's headers does not store (see [Client hints and shared caches](responses.md#client-hints-and-shared-caches)).

### Production notes

#### The cache tiers, and what replicas change

Results are cached in up to three tiers: an in-memory LRU (256 MB by default, `CRABCROP_CACHE_MAX_MB`), a disk tier underneath it (`CRABCROP_RESULT_STORAGE_DIR`, 512 MB by default) whose entries survive restarts, and a shared S3 tier (`CRABCROP_RESULT_BUCKET`) that every replica reads and writes. The first two tiers are local to each process, so running more replicas trades cache hit rate: every replica produces identical bytes for a signed URL, and a miss just costs a re-fetch and re-process. Once you run several replicas, the shared tier is what keeps the hit rate whole; each recipe says how to wire it on its platform. A render is written through to the bucket in the background, after its response, with at most 64 bucket writes in flight per replica. When a slow or stalled bucket holds all 64, the next render is not written through: it stays in that replica's own tiers, the next replica to miss renders it again, and the skip counts in `crabcrop_cache_shared_puts_skipped_total`. A hit that adds a cache group to a stored entry also writes the bucket copy, so that a purge of the group finds it there; that write is never skipped. It waits in the background for one of the 64 to free up, and the response does not wait for it.

The disk tier's directory should hold only what the server writes there, and the server writes only regular files. At boot, it skips anything else named like an entry (`<64 hex digits>.bin`), such as a FIFO, a socket, a device, a directory or a symlink: it does not open it, logs it, and leaves it in place. A lookup does not wait for a FIFO's writer or follow a symlink, and it checks what it opened. Anything that is not a regular file, a symlink included, is treated like a corrupt entry: the lookup is a miss, and the path is deleted unless it is a directory.

One behavior does not cross processes: purges. A purge is guaranteed for the process that receives it and for the configured persistent and shared stores: the entry is removed from that process's memory, its disk tier, and the shared bucket. It does not invalidate the memory of any other replica, so a replica that already holds the entry can keep serving it until that process evicts the entry or restarts. Because the removals reach the receiving process's disk tier and the bucket, a replica that misses in its own memory finds nothing underneath in those tiers and re-renders, and in them a purged entry is never resurrected from a lower tier. On a bucket large enough that the purge's scan finishes in the background, the purge's tombstone covers the gap: the receiving process writes it to the bucket (under `purges/` inside `CRABCROP_RESULT_PREFIX`, authenticated with a key derived from the secret, so a planted one never applies; one the bucket will not serve is retried, counted and logged, see [A replica that cannot read the purge tombstones](#a-replica-that-cannot-read-the-purge-tombstones)) before it touches any tier, and every replica reads the tombstones at boot and every 5 seconds after. While a tombstone lives, each replica treats a disk or bucket copy it covers that was written before the purge began as a miss, so a bucket copy the scan has not reached yet is not served, and a restart mid-scan does not undo the purge; copies rendered after the purge began serve normally, and the scan leaves them in place. A replica answers no request, `/health` included, until its first read of the tombstones ends, and prints its `crabcrop listening` line then; it binds the port earlier, so a connection made meanwhile waits. Each read of the tombstones, at boot and every 5 seconds after, reads 16 at a time and ends within 10 seconds: one deadline covers the listing, the reads and the deletes of expired or superseded tombstones together. A slow or hanging bucket therefore holds back the first answer by 10 seconds at most, inside the roughly 45 seconds the liveness probe in the Helm chart and the kustomize base allows (a first probe at 5 seconds, then one every 20, a restart after three failures). A refresh reads the newest tombstones first, the ones it has read by its deadline apply, and the next refresh reads only those it has not read yet or that changed since, so a slow bucket that keeps answering catches up over a few refreshes. A tombstone the replica has read before stays in force when a later read of it fails or does not finish in time: the version it read keeps applying, and the next refresh reads it again. A read that answers 404 is not a failure, and the tombstone drops out: another replica deleted it after the listing. Every other read the bucket fails (an error status, a connection that closes or times out, a body that breaks off) counts once in `crabcrop_cache_tier_errors_total`. The reads a refresh has not finished at its deadline, started or not, count once together, so a hanging bucket adds about one error per refresh however many tombstones it holds (a read that the store's own 10 second bound or a connection failure ends first counts on its own). Each refresh with either logs one `shared storage: cannot read purge tombstones` line on stderr, with how many reads failed, how many were left at the deadline, and how many of those tombstones are not in force on that replica, naming the oldest three. A listing that fails or does not finish in time keeps the tombstones the replica already has (none, at boot), counts once, and logs `cannot list purge tombstones`. A tombstone the replica has never managed to read does not apply there until a refresh reads it; [A replica that cannot read the purge tombstones](#a-replica-that-cannot-read-the-purge-tombstones) says what that replica serves meanwhile, how to see it, and how to close the gap (issue #577). The same holds for a purge the replica has read whose tombstone another replica deletes because a newer, finished purge of the same target supersedes it: the replica then follows the newer tombstone, so until it reads that one, neither applies there. Each replica runs at most two background scans at a time, and each scan reads 16 entries at a time. The parts of the scans that run inside purge requests share 32 reads at a time between them, so a replica keeps at most 64 purge reads in flight however many purges arrive. A repeated purge of a target whose scan is still running there joins that scan instead of scanning the bucket again in parallel; when the scan ends, one more pass runs for every purge that joined it. A tombstone expires 15 minutes after its scan ends, and the replicas delete expired ones as they refresh. One whose scan never ended (the process stopped first) stays in force until a later purge of the same target finishes its scan. So does one whose scan could not reach every entry because the bucket failed to answer a listing, a read, or a delete; each such failure counts in `crabcrop_cache_tier_errors_total`. Copies are compared by the time their render began, so replica clocks should agree to within 5 seconds, as any NTP-synced fleet does; a copy another replica renders in the first 5 seconds after a purge counts as purged, so it is not cached and the next request for it renders again. In the seconds before a replica has read a new tombstone, it can still read a bucket copy the scan has not reached and keep it in its own memory, like a copy it already held. Its own disk directory is the exception of the same kind as its memory: a purge sent to another replica does not delete its disk entries, so with per-replica disk tiers a disk copy that nobody requests while the tombstone lives can serve again afterwards, until the replica receives the purge itself or evicts the entry. Cache entries record when their render began from this release on (entry format `CRABDISK6`); entries written by earlier releases keep serving and count as older than every purge. An earlier release cannot read the new entries: rolled back, its disk tier deletes them at boot and it re-renders over the bucket's copies; during a mixed-version rollout, send purges to upgraded replicas, because an earlier-release replica writes no tombstone and its scan skips entries in the new format. Cross-replica purge invalidation is deliberately out of scope. If a purge has to take effect everywhere immediately, send it to each replica, or run a single replica.

#### A replica that cannot read the purge tombstones

A replica applies another replica's purge only once it has read the purge's tombstone. The target (a cache key, a group or a source) is inside the authenticated object, not in its name. Two things keep a replica from reading one:

- The bucket fails or stalls the listing of `purges/`. The replica logs `shared storage: cannot list purge tombstones` and keeps the tombstones it has. A replica that starts this way starts with none.
- The bucket lists a tombstone but fails or stalls its read. Its GETs fail or hang, the replica may list `purges/` but not read objects there, or the object was encrypted with a customer-provided key (SSE-C) or moved to an archival storage class. The replica logs `shared storage: cannot read purge tombstones`. That line's `not in force until read` counts such tombstones, and `oldest not in force` names the three whose purges began first.

To see it:

- `crabcrop_cache_shared_tombstones_unread` counts the tombstones the replica's last complete listing named that it has never read.
- `crabcrop_cache_shared_tombstones_listed_timestamp_seconds` is when it last listed them completely, 0 before its first complete listing. A healthy replica lists them every 5 to 15 seconds.
- Both failures also count in `crabcrop_cache_tier_errors_total{tier="shared"}`.
- Alert when the unread count stays above 0, or the listing time falls more than a minute behind, for more than a minute.

Until the replica reads a tombstone, as in the seconds before it reads any new one:

- It serves the copies the purge covers from its disk tier. It also serves them from the bucket where the purge's scan has not reached them and the replica can still read entries.
- It keeps the copies it serves in its memory. A tombstone it reads later does not remove them from there.
- When a request adds a cache group to such a copy, it writes the copy back to the bucket with that group, even where the scan has already passed. The copy keeps the time its render began. Replicas that have read the tombstone treat that copy as a miss and delete it when a request reaches it. Once the tombstone expires, 15 minutes after its scan ends, the copy serves on every replica.

Every refresh retries. Once the replica reads a tombstone that is still live, its disk and bucket lookups apply it. Nothing undoes what it served or wrote before that.

To close the gap, wait until its refreshes succeed again: no new `cannot list` or `cannot read` lines, the unread count at 0, and the listing time current. Then:

1. Find the purges it missed: the tombstones its `cannot read purge tombstones` lines count as not in force (they name the oldest three; when the count is higher, take every tombstone listed under `purges/` then), and every purge sent while its listing time stood still. For a replica that started during the outage, that is every tombstone listed then. Listing `purges/` under `CRABCROP_RESULT_PREFIX` shows the tombstones not yet deleted, named `<start ms>-<writer>-<sequence>`. Each body names its kind (`key`, `group` or `source`) and its target in plain text after its first two lines. A tombstone is deleted 15 minutes after its scan ends, and the purge log records only a hash of each target, so keep your own record of the purges you send.
2. Send each of them again to that replica's own address, such as its pod IP or a `kubectl port-forward` to the pod, not through a Service or load balancer that picks a replica. The purge removes that replica's memory and disk copies, and its scan removes the copies written back to the bucket: it begins later, so it covers every copy the first one did. If the first purge's tombstone is no longer listed, send the purge to every replica, since any of them may have served a written-back copy and kept it in memory. To send a source purge again, upload the same original again, with `CRABCROP_UPLOAD_ALLOW_OVERWRITE` on.
3. If you cannot tell which purges it missed, restart it once its reads succeed. That clears its memory, and it puts every tombstone still listed in force before the replica answers. It does not reach purges whose tombstones were deleted meanwhile, or the copies the replica wrote back to the bucket. Send those purges again.

To prevent it, give every replica `s3:ListBucket` on the bucket and `s3:GetObject` on `purges/` under `CRABCROP_RESULT_PREFIX` (and `kms:Decrypt` with SSE-KMS). Keep customer-provided-key encryption and lifecycle transitions to archival storage classes off that prefix. A tombstone whose scan never ended never expires, so a transition after some number of days makes it unreadable on every replica.

An object under `purges/` that no replica can read is never deleted, because its expiry is inside it. Every replica retries it on every refresh, counts it, logs it and shows it in the unread count. It changes nothing else, and no request misses because of it. Delete the object to end it.

The replica does not close the gap itself, because it cannot tell which copies an unread purge covers. Treating every older copy as purged would re-render its whole disk tier from the origin during the bucket outage that hides the tombstone. Every version of that rule tried so far could also leave copies without the cache groups they were served under (issue #577).

#### Shutting down

On `SIGTERM` or Ctrl-C the server drains, then exits with status 0:

1. It stops accepting connections, closes idle ones, and lets the requests in flight finish.
2. It waits for the background work those and earlier requests left: renders whose client disconnected after the render started, which finish and are stored, then shared-tier write-throughs and purges whose caller disconnected before the answer.
3. It exits. A background purge scan is not waited for: one cut short leaves its purge's tombstone in force until a later purge of the same target finishes its scan (see [the cache tiers](#the-cache-tiers-and-what-replicas-change)), so the purge still holds. The exception is a purge whose tombstone the bucket refused (counted in `crabcrop_cache_tier_errors_total`): it held in the stopping process only, so the copies its scan had not reached can serve again. Send that purge again.

One deadline bounds the first two steps together: `CRABCROP_SHUTDOWN_GRACE_SECS` (8 seconds by default) from the signal on. At the deadline the process exits with whatever is still running: a request still in flight is cut off with its render, and a bucket write still in flight is dropped, as is a render whose client had left; stderr gives one count for the background writes dropped and one for those renders; a request cut off is reported on its own line and is not counted among them. A dropped render write-through costs one render on the next replica that misses, and a dropped render one on the next request for it. A dropped group write-back leaves the bucket copy outside a later purge of that group, as a failed bucket write does. A second `SIGTERM` or Ctrl-C during the drain ends it at once, in the same way. The server never runs past the grace, so give the platform a stop timeout longer than it, or the platform kills the process mid-drain:

- Kubernetes: the Helm chart passes `shutdownGraceSeconds` (default 8) to the server and sets the pod's `terminationGracePeriodSeconds` to it plus 5, so set the grace there; the chart refuses `CRABCROP_SHUTDOWN_GRACE_SECS` in `env`. Elsewhere `terminationGracePeriodSeconds` defaults to 30 seconds, which covers the default grace.
- `docker stop` and Compose: 10 seconds by default. A grace of 10 or more needs `docker stop --time` or Compose's `stop_grace_period` raised to match.
- Cloud Run: 10 seconds, fixed. Keep the grace under it.
- ECS on Fargate: the container's `stopTimeout` in the task definition, 30 seconds by default (120 at most).
- Azure Container Apps: `terminationGracePeriodSeconds` under the app's `template`, 30 seconds by default.
- systemd (the VM unit): `TimeoutStopSec=` in the unit, 90 seconds by default.

The listener closes at the signal, so a load balancer that still routes to the instance gets refused connections until it notices. Where the platform removes the instance from the balancer while it signals it, as Kubernetes does, a `preStop` hook that sleeps a few seconds keeps it serving meanwhile; add the sleep to `terminationGracePeriodSeconds`. The Helm chart sets no such hook, and its 5-second margin is not room for one.

#### Lock down the edge

Run crabcrop behind a reverse proxy or CDN in production. The application bounds its own work (the processing, AI, video, and animation gates shed overload with `503`) and the source bytes it holds before that work starts (`CRABCROP_SOURCE_BUFFER_MAX_MB`: each body is charged as it arrives with a read-ahead of at most 1 MiB, an origin that stalls or sends slowly holds only what it sent, and a request that cannot get budget within 5 seconds sheds with the same `503`), but connection-level protections belong at the edge: request and header timeouts, connection limits, rate limiting, and TLS termination. The server also keeps its own connection bounds, as a backstop for when nothing is in front of it: a connection must send its request head within `CRABCROP_HEADER_TIMEOUT_SECS` (30 seconds), one with no request running and no bytes moving closes after `CRABCROP_IDLE_TIMEOUT_SECS` (65 minutes; on HTTP/2, pings and other frames between requests do not count), and at most `CRABCROP_MAX_CONNECTIONS` are open at once (three quarters of the open-file limit). They are generous: the idle timeout is above the time the common edges keep an idle pooled connection by default, so the edge closes it first. Raise it if your edge keeps one longer. They do not tell one client from another and limit no request rate, so they do not replace the edge. Where the proxy runs on the same host outside a container (the VM recipe), set `CRABCROP_BIND=127.0.0.1` so the server's port answers only on that host. In a container keep the default: a proxy in another container and the platform's probes reach the container's own address, not its loopback. Restrict `/health` and `/metrics` to your internal network at the proxy: `/health` is unauthenticated, and `/metrics` is gated by its bearer token (it answers `403` when no `CRABCROP_METRICS_TOKEN` is configured, and `401` for a missing or wrong bearer when one is). Both are served with `Cache-Control: no-store`, and the metrics expose traffic and error counters.

#### Container hardening

The images run as user and group 65534 (nobody), given by number, so Kubernetes can check `runAsNonRoot` against it. They carry no curl. The `HEALTHCHECK` runs `crabcrop health`, which asks the server on the container's own port (`CRABCROP_PORT` or `PORT`) for `/health`: at 127.0.0.1 when `CRABCROP_BIND` is unset or `0.0.0.0`, at `::1` when it is `::` (then 127.0.0.1 if `::1` cannot be reached), and otherwise at the address it names. It exits 0 on a `200`, and 1 on any other answer or none within 2 seconds. Use it for your own checks inside the container too, such as `docker compose exec crabcrop crabcrop health`.

The server needs no writable root filesystem. It writes to the disk tier's directory (`CRABCROP_RESULT_STORAGE_DIR`), to the upload directory (`CRABCROP_UPLOAD_DIR`) when one is set, and to the temporary directory (`TMPDIR`, else `/tmp`). There `frame:` stages the source and the video and PDF tools run, so only images that add those tools use it. Where a platform can make the root filesystem read-only, those directories need writable mounts.

The Helm chart and the kustomize base do this, and pass the Kubernetes Pod Security "restricted" profile: `runAsNonRoot: true`, user and group 65534, the `RuntimeDefault` seccomp profile, no privilege escalation, every capability dropped, a read-only root filesystem with an `emptyDir` at `/tmp` (1Gi), and no service account token. An optional NetworkPolicy (Helm `networkPolicy.enabled`, the kustomize `network-policy` component) allows ingress to the HTTP port, and egress to DNS and to public IPv4 addresses only: not to the private ranges, link-local (the cloud metadata address) or `100.64.0.0/10`. It covers what `CRABCROP_BLOCK_PRIVATE_SOURCES` does not: hosts in `CRABCROP_ALLOWED_SOURCES` skip the address check, and code running in the pod is not bound by it. Both recipes request 100m of CPU and 128Mi of memory and set no limits; the production values and the multi-replica overlay set limits. Without a CPU limit the server sizes its stills lane and its default source buffer budget from the node's cores, so on a large node set a limit, or `CRABCROP_SOURCE_BUFFER_MAX_MB`.

#### Rotating the signing secret

Rotation never invalidates a URL that is already in the wild: during a rotation window the server verifies the outgoing secret alongside the current one, each named by its key ID. See [Rotating the secret](configuration.md#rotating-the-secret) under Configuration for the three steps, using `CRABCROP_SECRET_KEY_ID`, `CRABCROP_SECRET_PREVIOUS`, and `CRABCROP_SECRET_PREVIOUS_KEY_ID`.

## Building from source

Beyond the Rust toolchain, a source build needs a C compiler (the tree vendors C libraries), nasm on x86_64 (the AVIF encoder's assembly; its build script fails without it), and, only for the vendored AVIF decode route (`--features avif-decode`), meson and ninja, or a system libdav1d 1.3 or newer found through pkg-config instead. The prebuilt routes (the installer, the Docker images, the release binaries) need none of this.

AVIF source decoding is behind the `avif-decode` cargo feature (off by default, on in the Docker image and the release builds; see [Source images](url-grammar.md#source-images)). Building with it needs dav1d 1.3 or newer reachable through pkg-config, or a vendored build:

```bash
SYSTEM_DEPS_DAV1D_BUILD_INTERNAL=always cargo build --features avif-decode
