# Configuration

All configuration comes from environment variables. Invalid values are startup errors, booleans included, the server refuses to start rather than run with a wrong port, cache budget, or safety flag. Boolean variables accept `1`, `true`, `yes`, `on` (any case) for on and `0`, `false`, `no`, `off` for off; anything else fails the boot with the variable named. Names follow one pattern: `*_MODEL` is an AI model artifact, `*_FILE` is a file read at boot, `*_DIR` is a directory, and `*_MAX_MB` is a size budget in megabytes.

| Variable | Default | Description |
| --- | --- | --- |
| `CRABCROP_SECRET` | required | The HMAC secret used to verify signed URLs, at least 16 bytes. The server will not start without it. Generate it, for example with `openssl rand -hex 32`. A placeholder published in crabcrop's docs or recipes (such as `your-secret-change-me` or `REPLACE_ME`, in any letter case) stops the boot with an error that names the variable. |
| `CRABCROP_SECRET_KEY_ID` | `current` | The current secret's key ID, named by keyed signature segments (`<key-id>:<tag>`). |
| `CRABCROP_SECRET_PREVIOUS` | unset | The outgoing secret during a rotation window; the server verifies it alongside the current one. Same minimum length, and the same placeholders stop the boot. |
| `CRABCROP_SECRET_PREVIOUS_KEY_ID` | `previous` | The previous secret's key ID. Must differ from the current one. |
| `CRABCROP_METRICS_TOKEN` | unset | Bearer token for `GET /metrics`. Unset, `/metrics` answers `403` to everyone; set, the request must carry `Authorization: Bearer <token>` (the scheme name in any letter case, as HTTP allows), and a missing or wrong token answers `401`. It must be at least 16 bytes, for example `openssl rand -hex 32`: a shorter token stops the boot with an error that names its length, never the token, and so does a placeholder published in crabcrop's docs or recipes, as for `CRABCROP_SECRET`. |
| `CRABCROP_LOG_SYNC` | off | Whether each line of the log on standard output is written before the server goes on (for the boolean spellings, see above). Off, an image request's line is queued and one thread writes the queue, within about a millisecond, so no response waits for a write to standard output. Set `1` when every request's line must be on standard output before the request is answered: each request then writes its own line, one write per request, as in releases through 0.12, and the boot output says `request log: synchronous`. There is then no queue, so `/health` never answers `request_log_stalled` and `/metrics` has no `crabcrop_request_log_*` series: a standard output nobody reads holds each request in its own write. See [The request log](deployment.md#the-request-log). |
| `CRABCROP_DEFAULT_OPS` | unset | Operations prepended to every request (a house format, quality, or watermark), validated at boot. See [Server-wide default operations](#server-wide-default-operations). |
| `PORT` | `3000` | Listen port. `CRABCROP_PORT` is the namespaced alias and wins when both are set. `0` binds a free port, which the boot output's `crabcrop listening on port N` line names. |
| `CRABCROP_BIND` | `0.0.0.0` | The IP address the server listens on. The default is every IPv4 interface. Set `127.0.0.1` when the only client is a proxy on the same host, as the VM recipe does, so other hosts cannot reach the port. `::` listens on every IPv6 interface and on every IPv4 interface too, with `IPV6_V6ONLY` off whatever the host's default (an IPv4 client shows as an IPv4-mapped address); where the host has no IPv6 it stops the boot with an error that says to set an IPv4 address instead. In a container keep the default: the published port, a proxy in another container, and platform probes (Kubernetes, Cloud Run, ECS, Container Apps) connect to the container's own address, not its loopback. A value that is not an IP address (a host name, an address with a port, an empty value) stops the boot. The boot output's `connections:` line names the address. [`crabcrop health`](endpoints.md#command-line) probes this address, or loopback when it is `0.0.0.0` or `::`. |
| `CRABCROP_SHUTDOWN_GRACE_SECS` | `8` | How long the server drains after `SIGTERM` or Ctrl-C before it exits, 1 to 600 seconds, counted from the signal. It stops accepting connections, lets the requests in flight finish, then waits for the background work they left (renders whose client disconnected after the render started, shared-tier write-throughs, purges whose caller disconnected); at the deadline, or at a second signal, it exits with whatever is still running. The default stays under the 10 seconds `docker stop` and Cloud Run allow; keep the platform's stop timeout above the grace. See [Shutting down](deployment.md#shutting-down). |
| `CRABCROP_HEADER_TIMEOUT_SECS` | `30` | How long a client has to send a whole request head, 1 to 600 seconds. A new connection must send its first request head within it. On HTTP/1 each later request head on the connection must arrive within it too, counted from its first byte. Bytes that keep arriving do not extend it. On HTTP/2, and for a partial head sent behind a request still in flight (pipelined), the idle timeout bounds the later heads instead. The server closes a connection that misses it, with no answer. It does not bound a request body, or the time the server spends on a request. See [Lock down the edge](deployment.md#lock-down-the-edge). |
| `CRABCROP_IDLE_TIMEOUT_SECS` | `3900` | How long a connection may stay open with no request running and no bytes moving, 1 to 86400 seconds. It closes a keep-alive connection between requests, and a response whose client stopped reading it. On HTTP/2, pings and other frames between requests do not count as bytes moving, so the timeout runs from the end of the last response. Keep it above the time your proxy or load balancer keeps an idle connection to the server in its pool. By default that is 60 seconds for AWS load balancers and for nginx, 2 minutes for Caddy, 10 minutes for Google Cloud load balancers, and 1 hour for Envoy (Istio, Container Apps) unless its `idle_timeout` is set; the default of 65 minutes is above all of them. An AWS load balancer can be set to keep one up to 4000 seconds: raise this above what your edge uses. When the server closes a pooled connection first, the edge can send a request on it as it closes, and some edges answer that request with a `502`. With nothing in front of the server, a minute is plenty. |
| `CRABCROP_MAX_CONNECTIONS` | three quarters of the open-file limit | The most connections open at once, 1 to 1000000. At the cap the server stops accepting: a new connection waits in the kernel's listen queue until an open one closes, and is then served. Health checks wait in the same queue. The default is three quarters of the process's open-file limit (`ulimit -n`) at boot, 768 under the common limit of 1024, so connections never take the file descriptors the server needs for source fetches, its stores, and its workers. Raise the open-file limit (`LimitNOFILE=` in a systemd unit, `--ulimit nofile=` for Docker) and the default rises with it. The boot output's `connections:` line prints the cap in force. |
| `CRABCROP_MAX_CONNECTIONS_PER_CLIENT` | `0` (no share) | How many of those connections one client may hold at once, 0 to 1000000, for a server that clients reach directly. A client is an IPv4 address, or the /64 an IPv6 address is in, since a host is usually given a whole /64; an IPv4 client that reaches an IPv6 listener counts as its IPv4 address. A connection past its client's share is closed as soon as it is accepted, with no answer, so one client cannot take the whole cap while other clients wait in the listen queue. `0`, the default, sets no share, and a share at or above the cap changes nothing. Keep it at `0` behind a reverse proxy, a load balancer or a CDN: every connection then comes from their few addresses, and a share would close your own traffic. When it is set, the `connections:` line names it, and stderr says how many connections it closed, at most one line every 10 seconds; the line names no address. |
| `CRABCROP_ALLOW_UNSAFE` | off | Honors `unsafe` URLs (for the boolean spellings, see above). |
| `CRABCROP_PURGE_REQUIRE_EXPIRY` | off | Whether the purge endpoints take only purge URLs that carry an expiry (for the boolean spellings, see above). Off, a purge or purge-group URL with no `exp:` segment purges, as it always has. Set `1` when you mint only [expiring purge URLs](endpoints.md#purge-a-cached-result): a purge or purge-group URL without one then answers `403 expiry_required` once its signature verifies, and purges nothing, so every purge URL the server takes stops working at its expiry. The boot output says `purges: expiring URLs only`. A URL with a bad signature still answers `403 bad_signature`. |
| `CRABCROP_CACHE_MAX_MB` | `256` | Result cache budget in megabytes. Each entry counts its body, its cache key (held twice), its ETag and cache group names, and a fixed allowance of a few hundred bytes for its bookkeeping, so the budget bounds the memory the cache holds. `0` disables the cache. |
| `CRABCROP_SSIM_TARGET` | `75` | SSIMULACRA2 target (0 to 100) that `quality(auto)` verifies against for JPEG and JPEG XL output of up to 4 megapixels. |
| `CRABCROP_METADATA` | `strip` | `preserve` copies source EXIF/XMP (and IPTC for JPEG) into JPEG and PNG outputs, without the EXIF and Photoshop thumbnails; see [Color management and metadata](responses.md#color-management-and-metadata). |
| `CRABCROP_META_MODE` | off | Meta mode: the JSON document a signed URL answers when the request sends `Accept: application/json`. Set `1` to enable it; while it is off, meta requests answer `403 meta_disabled` before any fetch or render, and the image itself serves as usual. Meta mode bypasses every cache tier and runs a fresh fetch, render, and annotation inferences on every request, so any viewer of a signed URL can trigger the most expensive request shape it has; enable it only on deployments that use meta. See [Meta responses](meta.md#meta-responses). |
| `CRABCROP_CLIENT_HINTS` | on | Whether image requests read the client hint headers `DPR`, `Sec-CH-DPR`, `Sec-CH-Width`, `Width`, `Sec-CH-Viewport-Width`, `Viewport-Width` and `Save-Data` (for the boolean spellings, see above). On, a response a hint applies to is served `Cache-Control: private`, so no shared cache stores it. Off, every one of them is ignored: each URL answers with the same bytes whatever hints a request sends, responses vary on `Accept` alone, and no `Accept-CH` is sent. Set `0` behind a CDN that does not put these headers in its cache key, as the CDN recipes do. See [Client hints and shared caches](responses.md#client-hints-and-shared-caches). |
| `CRABCROP_EXPLAIN` | on | Whether the server answers [`/explain/...`](endpoints.md#self-explaining-urls), the report on a URL (for the boolean spellings, see above). The report shows the presets a URL references and the default operations in full, watermark and overlay URLs included, to anyone who holds a signed URL. Set `0` to turn the route off: every `GET` or `HEAD` to it then answers `404 not_found`, before the signature is checked and with no source fetch. Image requests are unchanged. |
| `CRABCROP_WIDTH_STEP` | `100` | Quantization step in pixels for width client hints, 1 to 2000: hinted widths round up to a multiple of this, stopping at 3840, and never enlarge a raster source past its own size (see [Client hints](filters.md#client-hints)). |
| `CRABCROP_AVIF_SPEED` | `9` | ravif speed tier for AVIF encodes, 1 (slowest, smallest output) to 10 (fastest). At 800w and quality 80, the default speed 9 encodes about 1.8x faster than speed 8 for about 15% more bytes; speed 10 is roughly 3x quicker than speed 8 for about 44% more bytes. Set 8 for the smallest files of the fast tiers. |
| `CRABCROP_AVIF_TILES` | `4` | How many tiles an AVIF is written in: `1`, `2`, `4`, `8` or `16`, or fewer when the frame is too small for that many. More tiles make one AVIF encode faster on a host with a core for each, and the file larger. The count is part of the configuration fingerprint, so give every replica the same value. See [AVIF tiles](#avif-tiles). |
| `CRABCROP_JXL_SPEED` | `fastest` | jixel speed tier for JPEG XL encodes: `ultrafast`, `fastest`, `fast`, `medium`, `slow`, or `extraslow`. The default `fastest` encodes about 2x faster than `fast` for about 18% more bytes at 800w. Slower tiers shrink output with steep latency costs (`slow` is about 8x the latency of `fast` for about 18% fewer bytes at 800w). |
| `CRABCROP_PRESETS_FILE` | unset | Path to a presets file. See [Presets](operations.md#presets). |
| `CRABCROP_ONLY_PRESETS` | off | Rejects free-form operations in requests; only preset references (and `exp:` / `maxage:` metadata) are allowed. Requires at least one preset. |
| `CRABCROP_SOURCE_ROOTS_FILE` | unset | Path to a source roots file. See [Source roots](url-grammar.md#source-roots). |
| `CRABCROP_ALLOWED_SOURCES` | unset (no allowlist) | Comma-separated host suffixes the loader may fetch from. A suffix matches the host itself or any subdomain of it; an IP address entry matches only itself. A listed host is exempt from the non-public address refusal in the next row, unless `CRABCROP_CHECK_ALLOWED_SOURCES` is on, and while it is exempt, so is every name under it; the boot posture line then reads `private-address check: on, allowlisted hosts exempt`. A set value must name at least one host: one that names none (empty, blank, or only commas and dots, as a template with an empty variable renders) stops the boot. Unset it for no allowlist. Blank entries next to a host are ignored. In unsafe and presets-only mode, set it to the hosts your images come from, and keep the host names the server itself answers on off it (see [Loop detection](#loop-detection)). |
| `CRABCROP_BLOCK_PRIVATE_SOURCES` | on | Refuses sources whose host is, or resolves to, a non-public address: loopback, private, link-local, unspecified, shared (CGNAT), reserved, multicast, broadcast, documentation, benchmarking, and the other special-purpose ranges, including IPv4-mapped, IPv4-compatible, and 6to4 spellings of them. Checked before connecting and again on every redirect hop. Allowlisted hosts are exempt, unless `CRABCROP_CHECK_ALLOWED_SOURCES` is on. A non-public IP literal answers `403`; a host name that resolves to a non-public address answers `502`, the same as a name that does not resolve (see [Source images](url-grammar.md#source-images)). |
| `CRABCROP_ALLOW_ANY_SOURCE` | off | Deliberately allows every source: switches the non-public address refusal off. A configured allowlist still applies. |
| `CRABCROP_CHECK_ALLOWED_SOURCES` | off | Applies the non-public address refusal, and the connection pinning that comes with it, to the hosts in `CRABCROP_ALLOWED_SOURCES` too, so the allowlist only narrows what may be fetched. A listed host that is, or resolves to, a non-public address is then refused like any other, and listed host names are fetched pinned, which means directly and not through a proxy (see below). Off by default: listing a host is how a deployment reaches a loopback or internal source, and that keeps working. Turn it on when a listed name covers names that others can create or point, such as a shared hosting or CDN domain. Boot refuses it together with `CRABCROP_BLOCK_PRIVATE_SOURCES=0` or `CRABCROP_ALLOW_ANY_SOURCE`, which switch the refusal off. |
| `CRABCROP_S3_ENDPOINT` | unset (AWS) | Base URL of an S3-compatible store for `s3://` sources, path-style; it must be an `http` or `https` URL. Unset means AWS S3 itself, virtual-hosted. `CRABCROP_S3_REGION` sets the AWS region (default `us-east-1`). Signing credentials come from `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`, read once at startup and used as they are; the key ID and secret are set together or not at all. With those unset, they come from the container credentials endpoint when the environment names one, as ECS does for a task role and EKS Pod Identity for a pod: `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI`, a path on ECS's agent at `169.254.170.2`, or else `AWS_CONTAINER_CREDENTIALS_FULL_URI`, over `https`, or over plain `http` only to `169.254.170.2`, `169.254.170.23`, `fd00:ec2::23` or a loopback address (any other is a startup error). Each fetch sends the token in the file `AWS_CONTAINER_AUTHORIZATION_TOKEN_FILE` names, read afresh every time, or else `AWS_CONTAINER_AUTHORIZATION_TOKEN`, as its `Authorization` header. The server fetches them before its first AWS request and prints an `aws credentials:` line, then fetches the next set 15 minutes before they expire. A fetch that fails is logged and retried every 30 seconds, and requests keep signing with the last set meanwhile (unsigned before the first, so the bucket refuses them). No other part of the AWS credential chain is consulted: not web identity tokens (IRSA), EC2 instance metadata or profile files. The same credentials sign uploads and the shared result tier. Container credentials do not trip the `CRABCROP_ALLOWED_BUCKETS` boot check, since the platform sets them for every task with a role, but they sign every bucket fetch the allowlist lets through. `CRABCROP_S3_CONTAINER_CREDENTIALS=off` keeps the role out of the server's requests. With no credentials at all, fetches go unsigned (public buckets). |
| `CRABCROP_S3_CONTAINER_CREDENTIALS` | on | Whether the container credentials endpoint signs the server's AWS requests when `AWS_ACCESS_KEY_ID` is unset (see `CRABCROP_S3_ENDPOINT`). Off, the endpoint variables are ignored, so with no static keys the requests go unsigned, for a store that allows anonymous access. Emptying the endpoint variable is not a way to turn them off: ECS sets `AWS_CONTAINER_CREDENTIALS_RELATIVE_URI` for every task with a role, over any value the task definition gives it. The static keys are used either way. |
| `CRABCROP_GCS_ENDPOINT` | `https://storage.googleapis.com` | Base URL of the GCS XML API for `gs://` sources; it must be an `http` or `https` URL. `CRABCROP_GCS_REGION` (default `auto`) is the signing region; the HMAC pair is `CRABCROP_GCS_ACCESS_KEY` / `CRABCROP_GCS_SECRET_KEY`, set together or not at all. |
| `CRABCROP_ALLOWED_BUCKETS` | unset | Comma-separated bucket names the `s3://` and `gs://` schemes may read; `*` allows all. Unset refuses every bucket fetch, with or without credentials; with bucket keys configured (`AWS_ACCESS_KEY_ID` or `CRABCROP_GCS_ACCESS_KEY`, not container credentials) the server also refuses to boot without it. The allowed buckets are read with whatever credentials the server signs with, container credentials included, so with `*` a URL can name any bucket they can read. |
| `CRABCROP_FILE_ROOT` | unset | Directory that `file://` sources must stay under, canonicalized at boot and per request. Unset disables file sources. |
| `CRABCROP_SOURCE_MAX_MB` | `10` | Cap on one source body in megabytes, 1 to 1024, for every source kind (HTTP, bucket, and file) and every source type (image, video, and PDF), watermark images included. A larger source answers `502 source_too_large`. Raise it to serve `frame:` from longer clips or `page:` from larger PDFs. The upload cap (`CRABCROP_UPLOAD_MAX_MB`) defaults to it and may not pass it, and the default source buffer budget (`CRABCROP_SOURCE_BUFFER_MAX_MB`) is four of it per processing lane permit, so raising the cap raises the default budget with it: set the budget yourself to keep memory where it was. Watermark and overlay images have two fixed limits of their own, which no variable changes: a request may name at most 16 distinct watermark and overlay URLs, and their decoded images may hold at most 512 MiB together. A request past either answers `400 unsupported_operation` (see [Errors](responses.md#errors)). |
| `CRABCROP_SOURCE_TIMEOUT_SECS` | `10` | Total time one source fetch may take in seconds, 1 to 600: one budget spans the whole redirect chain and the body read, so a chain of fast hops cannot stretch a fetch past it. A fetch that runs past it answers `504 source_timeout`. The source, a fallback image fetched in its place (`CRABCROP_FALLBACK_IMAGE` as a URL), and each watermark image are separate fetches with a budget each, and `CRABCROP_PROCESS_TIMEOUT_SECS` starts only once they are done, so one request can take their sum; keep it under your proxy's or CDN's upstream timeout. It bounds source fetches only: requests to the upload bucket and the shared result store have their own bound, which grows with the bytes they move (see [Bucket request timeouts](#bucket-request-timeouts)). |
| `CRABCROP_REMOVEBG_MODEL` | unset | Path to a U²-Net-family ONNX model for the `removebg` filter. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_BRAND_COLOR` | unset | Brand color for `studio(...)` composites, six hex digits (a leading `#` is allowed). An unnamed backdrop and `bg:brand` resolve to it; unset means white. Changing it starts a fresh cache epoch, like the other output-shaping settings. See [Studio mode](filters.md#studio-mode). |
| `CRABCROP_UPSCALE_MODEL` | unset | Path to a super-resolution ONNX model for the `upscale` filter. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_INPAINT_MODEL` | unset | Path to a LaMa-family ONNX model (image plus mask inputs, fixed 512×512) for the `remove_region` filter. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_SEGMENT_ENCODER_MODEL` / `CRABCROP_SEGMENT_DECODER_MODEL` | unset | A MobileSAM ONNX pair (image encoder, box-prompt decoder) for mask-tight class operations. Both paths are required together; a partial set is a startup error. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_FACE_MODEL` | unset | Path to a YuNet ONNX model for face-aware `smart` crops, `crop:...:face`, and the face redaction filters. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_CLIP_IMAGE_MODEL` / `CRABCROP_CLIP_TEXT_MODEL` | unset | A CLIP ONNX model pair for meta `tags` and `alt_text`. All four CLIP paths are required together; a partial set is a startup error. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_CLIP_TOKENIZER` | unset | The CLIP export's `tokenizer.json`. |
| `CRABCROP_CLIP_LABELS` | unset | Text file with one tag label per line. |
| `CRABCROP_CLIP_THRESHOLD` | `0.05` | Minimum zero-shot score for a label to appear in `tags`. |
| `CRABCROP_MODERATION_MODEL` | unset | Path to a ViT classifier ONNX model (the Falconsai nsfw_image_detection shape) for meta moderation verdicts. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_MODERATION_LABELS` | unset | Text file with one label per line: the verdict model's output names (in output order) when a model is set, or zero-shot prompt labels for the CLIP fallback when it is not. |
| `CRABCROP_AESTHETIC_HEAD` | unset | Path to a LAION-style linear aesthetic head (the PyTorch save) scored against the CLIP embedding in meta. Requires the `CRABCROP_CLIP_*` set. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_OCR_DETECT_MODEL` / `CRABCROP_OCR_RECOGNIZE_MODEL` | unset | A PP-OCR-family ONNX model pair (DB detection plus CTC recognition) for meta OCR text. All three OCR paths are required together; a partial set is a startup error. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_OCR_DICT` | unset | The recognition model's character dictionary: one character per line, in class order. |
| `CRABCROP_OCR_LANGUAGE` | `und` | The language tag the recognition model serves, echoed in meta OCR responses. |
| `CRABCROP_DETECT_MODEL` | unset | Path to a YOLOv8-family ONNX model for `blurclass` / `pixelateclass` / `recolorclass` and meta detections. Operator-supplied; Ultralytics' own YOLO weights are AGPL-3.0. See [AI features](ai-features.md#ai-features). |
| `CRABCROP_DETECT_LABELS` | unset | Class names file (one per line, in index order) for detection exports that carry no `names` metadata. |
| `CRABCROP_DETECT_THRESHOLD` | `0.5` | Minimum detection score. |
| `CRABCROP_DETECTORS_FILE` | unset | Path to a JSON file declaring additional detectors (`boxes` and `focal` contracts) from your own models. See [Declared detectors](ai-features.md#declared-detectors). |
| `CRABCROP_ORT_DYLIB` | unset | Path to the ONNX Runtime shared library, when it is not on the library search path. |
| `CRABCROP_FONT_PATH` | unset | Path to a TTF/OTF font for the `text(...)` overlay filter, loaded at startup. Unset disables the filter. |
| `CRABCROP_VIDEO_ENCODER` | unset | Path to the external video encoder program for `format(mp4)` / `format(webm)`, validated at startup. Unset disables video output. See [Video output](media.md#video-output). |
| `CRABCROP_VIDEO_DECODER` | unset | Path to the external video decoder program for `frame:` extraction from video sources, validated at startup (it must exist and be executable). It must be FFmpeg 6.0 or newer, because the source arrives through its `fd` protocol; the version is not checked at startup, and an older build answers every `frame:` request with `502`. Unset disables frame selection. See [Video frames](media.md#video-frames). |
| `CRABCROP_PROCESS_TIMEOUT_SECS` | `30` | Hard wall-clock limit on processing one request, 1 to 600 seconds. The limit starts when the process phase does, before the gate waits, so time spent waiting at a gate comes out of the run's budget. The waits themselves are not cut short by the limit: each gate has its own fixed wait (5 seconds for the stills lane, 10 seconds for the slow lane and for the AI, video, and animation gates), a wait that runs out answers `503` even when that is past the limit, and a run that starts after the limit has passed answers `504`. Once the run is going, a request that exceeds the limit answers `504`, at the limit plus a two-second grace at the latest; animated sources check the limit between the frames they decode, chunked encode loops (animated frames, quality ladders) check it inside the encode, `text` checks it between glyphs, the blurs (the `blur` filter, a `pad` blur fill, the face, region, and class blurs, and the studio shadow) check it before each row at every bit depth, class redaction checks it before each segmentation decode, a scaled `overlay(...,width)` checks it before each row it scales and scales only the part that lands, and a single call that cannot be interrupted is detached and aborts at the first check after it returns. Such a call is a decode (a still's, or one frame of an animation's), a resize of the image, a still encode, an animated WebP encode, an AI inference, or a video encode. Detached work keeps every gate slot it holds (processing lane, AI, video, animation) until it actually finishes, so the gates count work still executing and not only requests still waiting: new work sheds at a gate while a detached run drains instead of stacking onto capacity that is still busy. The drain is bounded by the limit plus the longest single call, because the detached work checks the limit at the first opportunity after that call returns. An SVG source parses and renders in a worker process that is killed at the limit, so an SVG render never runs past it. |
| `CRABCROP_SLOW_LANE_PERMITS` | `1` | Size of the slow lane, 1 to 64: how many long-running renders may run at once on permits stills never use. Animated WebP encodes (from an animated WebP or GIF source, with WebP named in the URL or negotiated from `Accept`) and the external-tool work behind the video gate (video encodes, `frame:` extractions, `page:` renders) draw from this lane instead of the stills process gate, so a saturated slow lane cannot slow or shed a still render at all; slow-lane overflow waits up to 10 seconds, then sheds with a `503` and `Retry-After`, and never spills onto the stills lane. Animated GIF output stays in the stills lane on one permit, and prepares its frames on up to two threads (the host's cores, two at most, never more than the frames, and one for a single frame or an animation under 64x64 pixels), so one such render can keep up to two cores busy for the length of its encode. The default 1 suits a small host (one long encode at a time, a core and the whole stills lane left for stills); raise it on larger hosts that run video or animation traffic in parallel. `/metrics` reports both lanes as `crabcrop_lane_in_use` against `crabcrop_lane_capacity` (`lane="process"` and `lane="slow"`). |

With `CRABCROP_BLOCK_PRIVATE_SOURCES` on, the loader resolves each host that is not on the allowlist (and each one that is, with `CRABCROP_CHECK_ALLOWED_SOURCES`) to check its addresses and pins the connection to the validated address, so the address that was checked is the address that gets connected (no DNS-rebinding gap). Source URLs with userinfo (`http://user:pass@host/...`) are always refused: the loader never presents Basic credentials to an origin.

Pinned fetches connect directly and never go through a proxy: a proxy resolves the host again on its own, so it could connect to an address the check never saw. Every other fetch (allowlisted hosts, IP-literal sources, bucket sources, and every source when the private-address check is off) honours `HTTPS_PROXY`, `HTTP_PROXY`, and `ALL_PROXY`, in either case. On a network whose only way out is a proxy, pinned fetches therefore fail. With no allowlist every hostname source is pinned, so boot prints a warning when a proxy variable is set under that policy. To fetch through the proxy, list your source hosts in `CRABCROP_ALLOWED_SOURCES`: listed hosts are fetched unpinned, through the proxy, and every other host is refused. Listing a host also exempts it from the non-public address refusal, so list only hosts you trust. With `CRABCROP_CHECK_ALLOWED_SOURCES` on, listed host names are checked and pinned too, so they do not go through the proxy either, and boot prints the proxy warning when a proxy variable is set.

Boot prints the request and source posture on one line, for example `request mode: signed; source allowlist: none; private-address check: on`. The mode is `signed`, `unsafe` (`CRABCROP_ALLOW_UNSAFE`), `presets-only` (with `CRABCROP_ONLY_PRESETS` too) or `signed presets-only` (`CRABCROP_ONLY_PRESETS` alone). The allowlist shows its host count, or `none`. The check reads `on` or `off`; with an allowlist set it reads `on, allowlisted hosts exempt` by default, or `on, allowlisted hosts included` with `CRABCROP_CHECK_ALLOWED_SOURCES`. When unsigned URLs are on and no allowlist is set, boot also prints a warning on stderr: in unsafe mode anyone can run any operations on images from any host the loader may fetch, and in presets-only mode anyone can render the presets on them (see [Presets](operations.md#presets)). The server still starts.

### Changing the source policy

A change to the source policy applies to the results the cache tiers already hold. The policy is not part of the configuration fingerprint (see [Caching](responses.md#caching)), so a change starts no new cache epoch. Instead, before the disk tier or the shared bucket answers a request, the server runs the checks that the request's source URL, and each watermark URL it names, decide on their own:

- the host allowlist, `CRABCROP_ALLOWED_SOURCES`;
- an IP address against the non-public address refusal (`CRABCROP_BLOCK_PRIVATE_SOURCES`, `CRABCROP_ALLOW_ANY_SOURCE` and `CRABCROP_CHECK_ALLOWED_SOURCES`);
- the bucket allowlist, `CRABCROP_ALLOWED_BUCKETS`, and the bucket naming rules;
- whether file sources are configured, by `CRABCROP_FILE_ROOT` (or `CRABCROP_UPLOAD_DIR` without it).

Those two tiers may hold results that an earlier process or another replica stored under another policy. Memory holds only results this process stored, or read from those tiers, after its own policy admitted their sources, so a memory hit runs no check. A request the checks refuse reads neither tier: it gets the answer a render of its source gets, `403 source_forbidden`, whatever a tier holds for it. So a stored result stops serving, on every replica that runs the new policy, once the policy refuses a URL the result names: a source or a watermark on a host, or in a bucket, dropped from its list; a `file://` source once file sources are off; or an IP address in a non-public range once the non-public address refusal covers it, as it covers a listed one when `CRABCROP_CHECK_ALLOWED_SOURCES` is turned on. A host name stays admitted whatever it resolves to, as the next paragraph says. The results themselves stay in the tiers, and serve again if the policy admits their URLs again. To remove them, purge them (see [Purge a cached result](endpoints.md#purge-a-cached-result)).

The checks read only the URLs a request names: they look no host name up and replay no redirect, so a hit costs no lookup. A result whose fetch went through a host the policy now refuses therefore keeps serving from the tiers until it is purged. That is a host a redirect led to that the allowlist no longer lists, a host name that now resolves to a non-public address, or a listed host name that resolves to one once `CRABCROP_CHECK_ALLOWED_SOURCES` is on. Only a request that misses reaches such a host, and it is refused there: on the redirect hop with `403 source_forbidden`, or with `502 source_fetch_failed` for a name that resolves to a non-public address, as a name that does not resolve answers. Memory and the disk tier drop such a result when they evict it; the shared bucket keeps it until a lifecycle rule expires it (see [Bounding the shared tier](deployment.md#bounding-the-shared-tier)).

Moving `CRABCROP_FILE_ROOT` (or `CRABCROP_UPLOAD_DIR` without it), or changing `CRABCROP_S3_ENDPOINT`, `CRABCROP_S3_REGION`, `CRABCROP_GCS_ENDPOINT` or `CRABCROP_GCS_REGION`, re-keys no stored result either: a `file://`, `s3://` or `gs://` result rendered before the change keeps serving, so purge the result tiers after such a move, either the URLs it concerns or, with every replica stopped, the disk tier's directory and the result prefix.

### Loop detection

Every request the server sends on behalf of a request it serves carries a `CDN-Loop` header (RFC 8586) that names the deployment: `crabcrop; id=<token>`. That covers the source, each watermark and overlay image, a fallback image fetched in its place (`CRABCROP_FALLBACK_IMAGE` as a URL), the explain report's probe, every redirect hop, and `s3://` and `gs://` fetches. The token is 32 hex digits, the first 16 bytes of the SHA-256 of a key derived from `CRABCROP_SECRET`: every replica that shares the secret sends the same token (two deployments that share a secret count as one), and the token reveals nothing about the secret or the keys the server signs with. The `CDN-Loop` entries the incoming request carried go first, as they came, so a fetch that comes back through a CDN or through another crabcrop deployment still names the deployment it left. When those entries come to more than 2 KiB, the fetch carries the deployment's entry alone.

An image, meta or explain request that carries the deployment's own entry answers `508 loop_detected`, with `Cache-Control: no-store`, before its signature is checked, before any cache lookup and before any fetch. A source, watermark, overlay or fallback URL that leads back to the server, directly, through a redirect, or through a CDN or proxy that keeps the header, therefore stops at its first nested request, and the request that named it answers as it does for any source that answers with an error status: `502 source_bad_status`, or the fallback image in place of a source when one is configured. During a rotation window the token of `CRABCROP_SECRET_PREVIOUS` counts as the deployment's own too, so a replica on the new secret refuses the fetches of a replica still on the old one. A replica still on the old secret does not know the new token, but its own fetch carries the new entry on, ahead of its own, and the next hop refuses that: a loop through replicas on both secrets ends within two nested requests. A request whose entries name another deployment or a CDN is served as usual.

Keep the host names the server answers on, its CDN hostname included, out of `CRABCROP_ALLOWED_SOURCES`, so a URL on them is refused as a source before any fetch. A listed suffix covers every name under it: list `media.example.com` rather than `example.com` when the server answers on `images.example.com`.

### AVIF tiles

`CRABCROP_AVIF_TILES` sets how many tiles an AVIF is written in: `1`, `2`, `4`, `8` or `16`, and `4` when it is unset. Any other value stops the boot with an error that names the variable. A frame too small for that many tiles gets fewer: at the default speed and quality a tile takes at least 128x128 pixels, so a 256x256 frame has room for four and an 800x533 one for 26. Below quality 80 a tile takes at least 256x256 pixels, so an 800x533 frame has room for six, and eight or sixteen tiles write the same file as six.

The encoder writes one tile per thread, so every AVIF encode runs in a pool of that many threads, and the server keeps one pool for every that many cores, rounded up. The file depends on the count and the image, never on the host: every replica with the same count writes the same bytes for the same URL. A host with more cores than the count runs several AVIF encodes side by side, each at full speed. A count above the host's core count is allowed, and makes one pool whose threads share the cores.

More tiles let one encode use more cores, and each tile is compressed on its own, so the file grows with the count. Measured on a shared 4-core VM, release build, at the default speed and quality, as the median of three rounds of 25 encodes (7 at 2400x1600); four at once is four encodes started together, timed until the last one ends:

| Tiles | 800x533 photograph | 800x533, four at once | 2400x1600 photograph | 2400x1600, four at once |
| --- | --- | --- | --- | --- |
| `1` | 99 ms, 24,183 bytes | 117 ms | 811 ms, 145,862 bytes | 880 ms |
| `2` | 56 ms, 24,315 bytes | 129 ms | 473 ms, 146,384 bytes | 982 ms |
| `4` | 39 ms, 24,435 bytes | 108 ms | 306 ms, 146,811 bytes | 853 ms |
| `8` | 42 ms, 24,732 bytes | 112 ms | 305 ms, 147,560 bytes | 891 ms |
| `16` | 39 ms, 25,113 bytes | 113 ms | 285 ms, 148,081 bytes | 889 ms |

Compared with four tiles, one encode alone took about two and a half times as long in one tile and 1.4 to 1.5 times as long in two, for files 0.3% to 1.0% smaller. A flatter image loses more to tiling: the benchmark mix's source at 800x533 is 11,472 bytes in one tile, 11,844 in four, 12,107 in eight and 12,687 in sixteen. On four cores, eight and sixteen tiles cannot use more cores than four do: alone they took about the time four took (sixteen 7% less at 2400x1600), for files 0.5% to 2.8% larger. With four encodes at once the cores are busy whatever the count: no count was faster than four, and the others took 1% to 19% longer, in rounds that spread by up to 22%. A host with eight or more cores was not available, so what eight and sixteen tiles save there is not measured: on such a host one encode can use that many cores, which four tiles cannot.

The count is part of what a URL renders to, so it is in the configuration fingerprint (see [Caching](responses.md#caching)): replicas set to different counts keep separate cache entries instead of serving each other's files, and print different fingerprints at boot. Give every replica the same value. Four adds nothing to the fingerprint, so a server that leaves the variable unset, or sets it to `4`, keeps the fingerprint and the cache epoch it had.

### Tool address-space caps

On Linux the external tools and the SVG worker each run under a kernel limit on their address space (`RLIMIT_AS`), a backstop behind their wall-clock limits: an allocation past it fails in the tool, the request it was working for answers with an error, and the server goes on. One variable sets each tool's cap, in megabytes:

| Tool | Cap | Default | Least |
| --- | --- | --- | --- |
| The video encoder, for each encode | `CRABCROP_VIDEO_ENCODER_ADDRESS_SPACE_MAX_MB` | 8192 | 1024 |
| The video decoder, for each frame probe and extraction | `CRABCROP_VIDEO_DECODER_ADDRESS_SPACE_MAX_MB` | 3072 | 1024 |
| The PDF renderer and its `pdfinfo` probe, for each run and the boot check | `CRABCROP_PDF_RENDERER_ADDRESS_SPACE_MAX_MB` | 3072 | 256 |
| The SVG worker, for each SVG render and AVIF decode | `CRABCROP_SVG_WORKER_ADDRESS_SPACE_MAX_MB` | 4096 | 512 |

The defaults are sized for the most work crabcrop's budgets allow (see [Video output](media.md#video-output), [Video frames](media.md#video-frames), [PDF pages](media.md#pdf-pages) and [Source images](url-grammar.md#source-images)). A cap may be set from its least to 65536. A value under the least stops the boot with an error that names the variable: the least is what the tool needs to start, with room for other builds. With FFmpeg 6.1, Poppler 24.02 and glibc 2.39, small jobs needed 568 MB in the encoder (ten 64x48 frames to MP4), 601 MB in the decoder (one frame of a 64x48 H.264 clip, on two threads), 47 MB in the PDF tools (a letter page of text) and 141 MB in the worker (a line of SVG text, in the release build). A cap between the least and the default boots, and work that needs more than the cap fails in the tool. The boot output's `video encoder:`, `video decoder:` and `PDF renderer:` lines name a cap that is set to anything but its default, as in `video decoder: /usr/bin/ffmpeg (timeout 30s, address space 1536 MB)`; at the defaults they read as they did before the caps were settings.

An address-space cap is not a limit on resident memory: it also counts what a tool reserves and never touches, such as each thread's stack and malloc arena, so a tool can need far more address space than memory, and no cap follows the container's memory limit. Two encodes at the default may reserve 16 GB between them in a container that holds 4; the kernel's OOM killer, which ends a tool before the server (every tool runs with `oom_score_adj` 1000), stays the bound on the memory they use. The video decoder runs one thread more than the cores the server may use, up to 16, for frames up to 4096x2160, and each thread takes address space: an extraction of one frame of a 64x48 H.264 clip ran in 531 to 822 MB on 2 to 12 decoder threads, and needed 1.6 GB on 16.

A cap other than the default is part of the configuration fingerprint (see [Caching](responses.md#caching)), because what a tool returns can depend on its cap: the PDF renderer leaves out of a page an image it cannot decode under it. Give every replica the same caps. On other platforms no tool has an address-space limit (macOS accepts the SVG worker's and does not enforce it), and the PDF renderer's cap still sizes the JPEG 2000 check.

### Bucket request timeouts

Requests to the upload bucket (`CRABCROP_UPLOAD_BUCKET`) and the shared result store (`CRABCROP_RESULT_BUCKET`) are bounded by the bytes they move, not by `CRABCROP_SOURCE_TIMEOUT_SECS`, and no setting changes the rule:

- Connecting may take 5 seconds.
- A write (an upload, a shared-tier entry, a purge tombstone) may take 10 seconds plus one second per MiB of its body, the store's answer included. A store that takes the body in at 1 MiB a second or faster always finishes in time. A 16 MiB upload gets 26 seconds, one at the 1024 MB cap 17 minutes 14 seconds, and the largest shared-tier entry (512 MiB) 8 minutes 42 seconds. A store that stops reading the body fails the write at that bound.
- A read of an object (a shared-tier lookup, a purge's header read, a tombstone) must start to answer within 10 seconds, and no stretch of its body may go 10 seconds without a byte. The whole read must end within 10 seconds plus one second per MiB of the length the store declares, counted from the request; when the store declares no length, the bound grows with the bytes that have arrived, so the store must keep up 1 MiB a second.
- Every other request (a `HEAD`, a `DELETE`, a listing page) must be done within 10 seconds.

A request past its bound fails like any other store error. An upload answers `502 upload_store_unavailable`. A shared-tier lookup that runs out is a miss and a write that runs out is dropped, and both count in `crabcrop_cache_tier_errors_total`, as does a purge scan read that runs out, which keeps the purge's tombstone in force. An error status that does not say there is nothing to act on (a `404`, or a `412` on a conditional delete) is a failure too: a `5xx`, `429` or `408` counts as one the store did not answer, and any other, such as the `403` of credentials the bucket does not honor, as a refusal. Neither bucket's requests follow a redirect: a `3xx` is a refusal too, and nothing is sent to the host it names. A refused shared-tier lookup, purge scan read or purge scan delete also counts in `crabcrop_cache_shared_refused_total`, by request, and an upload's existence check that fails in any of these ways counts in `crabcrop_upload_exists_checks_failed_total` (see [Deployment](deployment.md#the-cache-tiers-and-what-replicas-change)).

Reading the purge tombstones has one more bound on top: one refresh, its listing, its reads (16 at a time) and its deletes of expired or superseded tombstones together, ends within 10 seconds. A replica answers its first request only after its first refresh, so a slow or hanging bucket holds that back by 10 seconds at most. [Deployment](deployment.md#the-cache-tiers-and-what-replicas-change) says what happens to a tombstone a refresh cannot read in time, and [what a replica that has never read one serves](deployment.md#a-replica-that-cannot-read-the-purge-tombstones).

### Server-wide default operations

`CRABCROP_DEFAULT_OPS` holds an operations string (the same grammar as a URL's operations, `preset:` references included) that the server prepends to every request, for a house format, quality, or watermark you do not want baked into every URL. The decisions, once:

- **The signature never covers the defaults.** They are operator configuration, applied after verification, like preset expansion.
- **Defaults sit before the URL's own operations**, and for the singleton directives (format, quality, fill, dpr, max_bytes) the URL wins by the default being dropped from the merged list. A bare request under defaults and the same request spelled out in full therefore produce the same operations and share a cache entry. Everything else (sizes, filters, watermarks) applies from both, in order: a default blur and a URL blur stack.
- **Defaults are operations only.** `exp:` and `maxage:` are per-request metadata, so a defaults string that carries either refuses the boot with `invalid CRABCROP_DEFAULT_OPS`, as a preset definition carrying them does. Set a shorter cache lifetime on the URLs that need it.
- **Defaults count against the 100-operation cap** together with each URL's own operations, after the merge: a default the URL overrides is dropped and does not count (see [the URL grammar](url-grammar.md#how-requests-work)). A defaults string that alone runs past the cap refuses the boot, since every request under it would answer `400`.
- **Cache entries key on the merged operations**, exactly like presets, so changing the defaults changes the keys and old entries age out unused. Purges account for the merge too: purging a URL removes its merged entry.
- **Presets-only mode is unaffected in what it rejects** (the URL's own operations), and the defaults still apply: they are not URL content.
- Cache groups stay the URL's own presets; a preset referenced only by the defaults does not join entries to its group.
- [`/explain`](endpoints.md#self-explaining-urls) forecasts from the merged operations, so its forecast matches what the image request serves; its operation list stays the URL's own, and the defaults appear in its canonical form. They appear in full, watermark and overlay URLs included, so keep tokens and internal hosts out of those URLs, or set `CRABCROP_EXPLAIN=0`.
- **A default `dpr(...)` is an explicit factor, not a hint.** It beats the `DPR` client hint, as a URL's own `dpr(...)` does, and it is never stepped down: a size it pushes past the [output limits](url-grammar.md#output-size) answers `400`, where a factor from the hint alone steps down to the largest one that fits (see [Client hints](filters.md#client-hints)).

### Rotating the secret

Rotation never invalidates a URL that is already in the wild, in three steps:

1. **Open the window.** Generate the new secret. Set `CRABCROP_SECRET` to it with `CRABCROP_SECRET_KEY_ID` naming it (say `2026-10`), and move the outgoing secret to `CRABCROP_SECRET_PREVIOUS` with `CRABCROP_SECRET_PREVIOUS_KEY_ID` naming it (say `2026-08`). Restart. The server now verifies both keys: a URL whose signature segment carries a key ID (`2026-08:<tag>`) is checked against that key only, and a URL with no ID is checked against both, so everything minted before key IDs existed keeps working too. Purge signatures route the same way. The source fetches name the new secret's token, and a request that names either secret's is refused (see [Loop detection](#loop-detection)), so while the restart rolls out a replica on the new secret refuses the fetches of one still on the old secret, and a loop through both ends within two nested requests.
2. **Mint with the new key.** Point your builders at the new secret and stamp its ID: `buildURL(..., { keyId: "2026-10" })` in TypeScript, `build_url(..., key_id="2026-10")` in Python, `sign_with_key_id` / `build_url_with_key_id` in Rust, or `crabcrop sign --key-id 2026-10` on the CLI. New cache entries accumulate under the new key from here on.
3. **Close the window.** When the old key's URLs have aged out of your caches and pages (the result cache's `max-age` is one year, but in practice your own TTLs and page lifetimes govern), remove `CRABCROP_SECRET_PREVIOUS` and restart. From that moment the old secret verifies nothing: its remaining URLs answer `403`, which is the point of rotating.

An unknown key ID is indistinguishable from a bad signature, by design: `403`, no hint about which IDs exist.

### Diagnostics

`CRABCROP_STUDIO_TIMING`, set to any value, prints the elapsed time of each `studio(...)` pipeline stage to stderr, one `[studio-timing] <stage>: <ms> ms` line per stage. It is a profiling aid, read once per process: responses, cache keys, and the configuration fingerprint are unchanged. Leave it unset in production.

### Allocator

The server links jemalloc as its global allocator (issue #801). This is where its cache-hit throughput comes from: under many concurrent hits, jemalloc's per-thread caches avoid the contention on glibc's malloc arenas, and it returns freed render buffers to the OS for a leaner resident footprint. It is a build-time choice — the default `jemalloc` feature — not a runtime setting, and it changes no output byte. The shipped Docker images, release binaries and Homebrew install all carry it. Build with `--no-default-features` (plus the features you need, for example `--features avif-decode`) to drop jemalloc and use the system allocator instead; on glibc that restores the `raise_malloc_thresholds` startup step (issue #690).
