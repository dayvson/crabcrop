# Configuration

All configuration comes from environment variables. Invalid values are startup errors, booleans included, the server refuses to start rather than run with a wrong port, cache budget, or safety flag. Boolean variables accept `1`, `true`, `yes`, `on` (any case) for on and `0`, `false`, `no`, `off` for off; anything else fails the boot with the variable named. Names follow one pattern: `*_MODEL` is an AI model artifact, `*_FILE` is a file read at boot, `*_DIR` is a directory, and `*_MAX_MB` is a size budget in megabytes.

| `CRABCROP_SECRET_PREVIOUS` | unset | The outgoing secret during a rotation window; the server verifies it alongside the current one. Same minimum length. |
| `CRABCROP_SECRET_PREVIOUS_KEY_ID` | `previous` | The previous secret's key ID. Must differ from the current one. |
| `CRABCROP_METRICS_TOKEN` | unset | Bearer token for `GET /metrics`. Unset, `/metrics` answers `403` to everyone; set, the request must carry `Authorization: Bearer <token>` (the scheme name in any letter case, as HTTP allows), and a missing or wrong token answers `401`. |

With `CRABCROP_BLOCK_PRIVATE_SOURCES` on, the loader resolves each host that is not on the allowlist to check its addresses and pins the connection to the validated address, so the address that was checked is the address that gets connected (no DNS-rebinding gap). Source URLs with userinfo (`http://user:pass@host/...`) are always refused: the loader never presents Basic credentials to an origin.

Pinned fetches connect directly and never go through a proxy: a proxy resolves the host again on its own, so it could connect to an address the check never saw. Every other fetch (allowlisted hosts, IP-literal sources, bucket sources, and every source when the private-address check is off) honours `HTTPS_PROXY`, `HTTP_PROXY`, and `ALL_PROXY`, in either case. On a network whose only way out is a proxy, pinned fetches therefore fail. With no allowlist every hostname source is pinned, so boot prints a warning when a proxy variable is set under that policy. To fetch through the proxy, list your source hosts in `CRABCROP_ALLOWED_SOURCES`: listed hosts are fetched unpinned, through the proxy, and every other host is refused. Listing a host also exempts it from the non-public address refusal, so list only hosts you trust.

### Bucket request timeouts

Requests to the upload bucket (`CRABCROP_UPLOAD_BUCKET`) and the shared result store (`CRABCROP_RESULT_BUCKET`) are bounded by the bytes they move, not by `CRABCROP_SOURCE_TIMEOUT_SECS`, and no setting changes the rule:

- Connecting may take 5 seconds.
- A write (an upload, a shared-tier entry, a purge tombstone) may take 10 seconds plus one second per MiB of its body, the store's answer included. A store that takes the body in at 1 MiB a second or faster always finishes in time. A 16 MiB upload gets 26 seconds, one at the 1024 MB cap 17 minutes 14 seconds, and the largest shared-tier entry (512 MiB) 8 minutes 42 seconds. A store that stops reading the body fails the write at that bound.
- A read of an object (a shared-tier lookup, a purge's header read, a tombstone) must start to answer within 10 seconds, and no stretch of its body may go 10 seconds without a byte. The whole read must end within 10 seconds plus one second per MiB of the length the store declares, counted from the request; when the store declares no length, the bound grows with the bytes that have arrived, so the store must keep up 1 MiB a second.
- Every other request (a `HEAD`, a `DELETE`, a listing page) must be done within 10 seconds.

A request past its bound fails like any other store error. An upload answers `502 upload_store_unavailable`. A shared-tier lookup that runs out is a miss and a write that runs out is dropped, and both count in `crabcrop_cache_tier_errors_total`, as does a purge scan read that runs out, which keeps the purge's tombstone in force.

Reading the purge tombstones has one more bound on top: one refresh, its listing, its reads (16 at a time) and its deletes of expired or superseded tombstones together, ends within 10 seconds. A replica answers its first request only after its first refresh, so a slow or hanging bucket holds that back by 10 seconds at most. [Deployment](deployment.md#the-cache-tiers-and-what-replicas-change) says what happens to a tombstone a refresh cannot read in time.

### Server-wide default operations

`CRABCROP_DEFAULT_OPS` holds an operations string (the same grammar as a URL's operations, `preset:` references included) that the server prepends to every request, for a house format, quality, or watermark you do not want baked into every URL. The decisions, once:

- **The signature never covers the defaults.** They are operator configuration, applied after verification, like preset expansion.
- **Defaults sit before the URL's own operations**, and for the singleton directives (format, quality, fill, dpr, max_bytes) the URL wins by the default being dropped from the merged list. A bare request under defaults and the same request spelled out in full therefore produce the same operations and share a cache entry. Everything else (sizes, filters, watermarks) applies from both, in order: a default blur and a URL blur stack.
- **Defaults are operations only.** `exp:` and `maxage:` are per-request metadata, so a defaults string that carries either refuses the boot with `invalid CRABCROP_DEFAULT_OPS`, as a preset definition carrying them does. Set a shorter cache lifetime on the URLs that need it.
- **Defaults count against the 100-operation cap** together with each URL's own operations, after the merge: a default the URL overrides is dropped and does not count (see [the URL grammar](url-grammar.md#how-requests-work)). A defaults string that alone runs past the cap refuses the boot, since every request under it would answer `400`.
- **Cache entries key on the merged operations**, exactly like presets, so changing the defaults changes the keys and old entries age out unused. Purges account for the merge too: purging a URL removes its merged entry.
- **Presets-only mode is unaffected in what it rejects** (the URL's own operations), and the defaults still apply: they are not URL content.
- Cache groups stay the URL's own presets; a preset referenced only by the defaults does not join entries to its group.
- [`/explain`](endpoints.md#self-explaining-urls) forecasts from the merged operations, so its forecast matches what the image request serves; its operation list stays the URL's own, and the defaults appear in its canonical form.
- **A default `dpr(...)` is an explicit factor, not a hint.** It beats the `DPR` client hint, as a URL's own `dpr(...)` does, and it is never stepped down: a size it pushes past the [output limits](url-grammar.md#output-size) answers `400`, where a factor from the hint alone steps down to the largest one that fits (see [Client hints](filters.md#client-hints)).

### Rotating the secret

Rotation never invalidates a URL that is already in the wild, in three steps:

1. **Open the window.** Generate the new secret. Set `CRABCROP_SECRET` to it with `CRABCROP_SECRET_KEY_ID` naming it (say `2026-10`), and move the outgoing secret to `CRABCROP_SECRET_PREVIOUS` with `CRABCROP_SECRET_PREVIOUS_KEY_ID` naming it (say `2026-08`). Restart. The server now verifies both keys: a URL whose signature segment carries a key ID (`2026-08:<tag>`) is checked against that key only, and a URL with no ID is checked against both, so everything minted before key IDs existed keeps working too. Purge signatures route the same way.
2. **Mint with the new key.** Point your builders at the new secret and stamp its ID: `buildURL(..., { keyId: "2026-10" })` in TypeScript, `build_url(..., key_id="2026-10")` in Python, `sign_with_key_id` / `build_url_with_key_id` in Rust, or `crabcrop sign --key-id 2026-10` on the CLI. New cache entries accumulate under the new key from here on.
3. **Close the window.** When the old key's URLs have aged out of your caches and pages (the result cache's `max-age` is one year, but in practice your own TTLs and page lifetimes govern), remove `CRABCROP_SECRET_PREVIOUS` and restart. From that moment the old secret verifies nothing: its remaining URLs answer `403`, which is the point of rotating.

An unknown key ID is indistinguishable from a bad signature, by design: `403`, no hint about which IDs exist.

### Diagnostics

`CRABCROP_STUDIO_TIMING`, set to any value, prints the elapsed time of each `studio(...)` pipeline stage to stderr, one `[studio-timing] <stage>: <ms> ms` line per stage. It is a profiling aid, read once per process: responses, cache keys, and the configuration fingerprint are unchanged. Leave it unset in production.
