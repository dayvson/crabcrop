# Releasing crabcrop

One version number covers every artifact: the server binaries and container images, the `crabcrop-url` crate (crates.io), `@crabcrop/url` (npm), `crabcrop_url` (PyPI), the MCP server package, the framework loaders, and the Helm chart. Releases are driven by git tags (`vX.Y.Z`).

## The pipeline

Pushing a tag like `v0.2.0` runs `.github/workflows/release.yml`:

1. **cargo-dist** builds the server for Linux and macOS on both architectures, plus the shell installer and SHA-256 checksums, and attaches them to a GitHub Release whose notes come from CHANGELOG.md.
2. **Container images** are built from `Dockerfile` and `Dockerfile.ai` and pushed to GHCR as `ghcr.io/dayvson/crabcrop` and `ghcr.io/dayvson/crabcrop-ai`, tagged with the version and `latest`.
3. **Registry publishing** (`cargo publish` for the crate, `npm publish` for the SDK, `twine upload` for the Python package) runs as separate jobs gated on the `release` GitHub Environment, so a human approves them in the Actions UI after inspecting the built artifacts. The jobs need the `CARGO_REGISTRY_TOKEN`, `NPM_TOKEN`, and `PYPI_TOKEN` repository secrets.
4. **The Homebrew formula** is generated from the release checksums and uploaded to the release as `crabcrop.rb`:

   ```bash
   gh release download v0.2.0 --pattern sha256.sum
   python3 scripts/release_formula.py 0.2.0 sha256.sum > crabcrop.rb
   gh release upload v0.2.0 crabcrop.rb
   ```

   Moving it into a `homebrew-tap` repository is a separate, later step.

The workflow file is generated by cargo-dist (`cargo dist generate`) plus the image and publishing jobs maintained in this repo. Because the automation credential cannot push workflow files, the complete workflow lives at `docs/release-workflow.yml`; land it at `.github/workflows/release.yml` through the GitHub web UI (the same route as the rust.yml gates in #36) before the first tag.

## Cutting a release

1. Update CHANGELOG.md: move the Unreleased entries into a new `## [X.Y.Z] - YYYY-MM-DD` section.
2. Bump every version site and verify they agree:

   ```bash
   python3 scripts/bump_version.py X.Y.Z
   python3 scripts/check_versions.py
   export PATH="$HOME/.cargo/bin:$PATH"
   cargo update -w   # refresh the lockfiles to the new versions
   cargo test && (cd sdks/typescript && npm test) && (cd sdks/python && python3 -m unittest discover -s tests)
   ```

3. Commit ("Release vX.Y.Z"), push, and tag: `git tag vX.Y.Z` on the release commit (the local master and the remote main carry the same tree, as usual).
4. Land `docs/release-workflow.yml` at `.github/workflows/release.yml` if it is not already there, then push the tag and watch the run. Approve the `release` environment jobs when the artifacts look right.
5. Smoke test the published artifacts in a clean environment: `cargo add crabcrop-url`, `npm install @crabcrop/url`, `pip install crabcrop-url`, `docker pull ghcr.io/dayvson/crabcrop:X.Y.Z`, and the shell installer from the GitHub Release.

## Version policy

Semantic Versioning, applied to the public contract: the URL grammar and signing scheme in `spec/url-signing.md`, the configuration surface, and the client libraries' APIs. A breaking change to the URL grammar would arrive as the spec describes (a new leading segment), never as a silent reinterpretation of existing URLs.
